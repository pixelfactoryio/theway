The configuration lives in `<home>/config.yaml`, where `<home>` is the data home: `~/.theway` by default, or the folder chosen at install (with `--home` or the install question) or set by `THEWAY_HOME` (see [Locations](./cli.mdx#locations); `theway path` prints it). Install writes it once and keeps your copy on later installs; the shipped version is always written to `<home>/config.default.yaml`, so you can compare the two.

A project can have its own `<home>/projects/<key>/config.yaml`, where `<key>` is the [project key](./concepts/changes.mdx#project-key) that `theway project` prints. It takes the same keys as the global file and can override any of them; install never writes it. `/theway:engineering`, with or without `--light`, does not read either file itself: it runs [`theway context <phase>`](./cli.mdx#context) and takes its keys from the `config` it prints. `/theway:workflow` takes its `workflow.defaults` through [`theway workflow`](./cli.mdx#workflow), which fills every step param a workflow file leaves out. When the global `config.yaml` is missing, it fails and the commands tell you to run [`npx --yes @pixelfactoryio/theway@latest install`](./installation.mdx#install-and-update), then `/reload-plugins`. The `standards` keys reach the commands through the `standards` list of the same output, which applies the same layers. `/theway:document`, `/theway:archive` and `/theway:list` read no other key.

A `config.yaml` written by an earlier install may still have `changes:` and `templates:` sections, and `file` and `description` keys: each one gives an `unknown key` warning from `theway config`. It may also have `interaction`, `develop` and `tamm_framework` entries under `standards:`: those standards cannot be switched, and each entry gives a `cannot be switched` warning. You can delete them all.

## Layering

`theway config` builds the effective config key by key: the defaults below, then the global `config.yaml`, then the project's `config.yaml`. For each key it takes the project file's value when it is present and valid, else the global file's value when it is present and valid, else the default. A section the project file leaves out keeps the global values, and so does every key it leaves out of a section it sets.

An invalid value is ignored with a warning on stderr, so the layer below applies: an invalid project value falls back to the global value, and an invalid global value to the default. Each warning names the file relative to the home:

```text
theway: warning: <file>: <key> must be <rule>; ignored
theway: warning: <file>: unknown key <key>; ignored
theway: warning: <file>: <key> must be a map; ignored
theway: warning: <file>: not a map; ignored
theway: warning: <file>: standards.<key> has no standard file; ignored
theway: warning: <file>: standards.<key> cannot be switched; ignored
```

`<rule>` is `a non-negative integer`, `true or false`, `opus, sonnet or haiku`, or, for a `workflow.defaults` param, `a string, an integer, a boolean or a non-empty list of names without duplicates`. An unknown key is reported once, at its highest unknown level: an unknown section `changes:` gives `unknown key changes`, not one warning per entry. A section, `review`, `defaults` or a step under `defaults` that is not a map contributes nothing below it, and a file whose root is not a map contributes nothing. An empty or comment-only file contributes nothing, without a warning. The global file's warnings come first, then the project file's, each in file order. Invalid YAML is an error, not a warning: see [`theway config`](./cli.mdx#config).

For example, with the shipped global `config.yaml`, this `<home>/projects/-home-you-code-my-api/config.yaml` of the project at `/home/you/code/my-api`:

```yaml
engineering:
  review:
    rounds: 0
workflow:
  defaults:
    implement:
      model: sonnet
    review: 2
```

makes `theway config`, run in `my-api`, print this, with one warning on stderr, `theway: warning: projects/-home-you-code-my-api/config.yaml: workflow.defaults.review must be a map; ignored`:

```yaml
standards:
  core_principles:
    enabled: false
  sre:
    enabled: false
  web_development:
    enabled: false
  quality:
    enabled: false
engineering:
  review:
    rounds: 0
    model: opus
workflow:
  defaults:
    implement:
      model: sonnet
```

## standards

`standards.<key>.enabled` switches any standard: the four opt-in standards theway ships and your own [user standards](./concepts/standards.mdx). The key is the file stem with `-` turned into `_`: `web-development.md` is `standards.web_development`, `tdd.md` is `standards.tdd`. Both the global and the project `config.yaml` take it, so a project can switch a global standard off, or an opt-in one on, for itself only (see [Switching a standard](./concepts/standards.mdx#switching-a-standard)).

- The four opt-in standards default to `false`. The commands that read standards, `/theway:engineering`, `/theway:workflow` and `/theway:document`, read one only when its `enabled` is `true`.
- User standards default to `true`.
- `theway config` prints the four opt-in keys first, in the order below, then the key of every user standard of the project, sorted, each with its effective `enabled`.
- A key with no standard file behind it, in either file, is ignored with a `has no standard file` warning.

The other shipped standards are always read and have no switch: `interaction.md` by `/theway:engineering`, `/theway:workflow`, `/theway:document` and `/theway:archive`; `develop.md` by `/theway:workflow`, inline or through its implementer agent; `tamm-framework.md` by `/theway:engineering`; `spec-review.md` and `spec-investigation.md` by `/theway:engineering`, and `spec-review.md` also by `/theway:workflow`. Their keys, `interaction`, `develop`, `tamm_framework`, `spec_review` and `spec_investigation`, give a `cannot be switched` warning, unless the project holds a file with that name in `<home>/projects/<key>/standards/`: that file is a user standard with its own switch. `commits.md` and `git-host.md`, the [convention standards](./concepts/standards.mdx#convention-standards) `/theway:workflow` follows, have no switch either: `standards.commits` and `standards.git_host` always give a `cannot be switched` warning, and a project file with either name overrides the global one instead of being a user standard.

| Standard | `enabled` | File | Used for |
|----------|-----------|--------|----------|
| `standards.core_principles` | `false` | `<home>/standards/core-principles.md` | Architecture philosophy (simplicity, security, pragmatic technology) |
| `standards.sre` | `false` | `<home>/standards/sre.md` | SRE operational excellence (reliability, observability, automation) |
| `standards.web_development` | `false` | `<home>/standards/web-development.md` | Frontend, API and backend standards with web performance targets |
| `standards.quality` | `false` | `<home>/standards/quality.md` | Testing, deployment, monitoring and security expectations |

A `config.yaml` written by an earlier install has `standards.architecture` instead of these four entries. `standards.architecture` gives a `has no standard file` warning from `theway config`, and the four stay off until you copy them from `config.default.yaml` and set `enabled: true` on the ones you want.

[User standards](./concepts/standards.mdx), your own files in `<home>/standards/` and `<home>/projects/<key>/standards/`, need no config entry: they are on until a `standards.<key>.enabled: false` switches them off.

## engineering

The spec review of [`/theway:engineering`](./commands/engineering.mdx#steps) (step 6). A key that is absent or invalid takes the value of the layer below (see [Layering](#layering)).

| Key | Default | Meaning |
|-----|---------|---------|
| `engineering.review.rounds` | `1` | Maximum review rounds per scaffold. A non-negative integer; `0` skips the review. |
| `engineering.review.model` | `opus` | Model of `/theway:engineering`'s critic agents (two, one with `--light`): `opus`, `sonnet` or `haiku`. Any other value is ignored with a warning. |

Each round spawns two critics. [`/theway:engineering --light`](./commands/engineering.mdx#light) reads the same keys and runs up to `engineering.review.rounds` rounds, with one grounding critic. To lower the cost, put `engineering.review.model` on `sonnet`, or set `engineering.review.rounds: 0` to skip the review.

## workflow

`workflow.defaults.<step>.<param>` sets a param of a [step](./concepts/workflows.mdx#step-files) for every workflow: an entry of that step that leaves the param out takes its value from the project file, then the global file, then the step file's default. A value written in the workflow entry wins. [`theway workflow`](./cli.mdx#workflow) applies them, prints each param's value and where it came from, and [`/theway:workflow`](./commands/workflow.mdx) runs what it prints. The shipped `config.yaml` sets none, `defaults: {}`: the step files hold the defaults, and [`theway steps`](./cli.mdx#steps) lists every step with its params and their effective values.

```yaml
workflow:
  defaults:
    review: {rounds: 2, model: sonnet}
    pr: {ci_attempts: 3}
```

- Defaults are keyed by step name and apply to every entry of that step (`review` and `review-2` alike); a value for one entry goes in the workflow entry.
- A param value is a string, an integer, a boolean or a non-empty list of names without duplicates; `theway config` warns about any other value and drops it.
- `theway workflow` and `theway steps` check each value against its step: a value of another kind than the param's default (`workflow.defaults.<step>.<param> must be <kind>`) or a param the step does not declare (`workflow.defaults.<step>.<param> is not a param of <step>`) is warned about and dropped, and the next source applies.
- A step name that resolves to no step file gives `workflow.defaults.<step>: no step '<step>' in <dirs>`, with a did-you-mean suggestion, from `theway config`, `theway workflow` and `theway steps`.
- A param that sets an agent's model is ignored for an inline step (`agents: false`), which takes no model.

The shipped steps' params:

| Step | Param | Default | Used by |
|---|---|---|---|
| `implement` | `model` | `opus` | the implementer |
| `review` | `rounds` | `1` | maximum review rounds |
| | `lenses` | `[conformance, correctness]` | one reviewer per lens, by prompt name |
| | `model` | `opus` | the reviewers, the triage and the fix check |
| | `fix_model` | `opus` | the fix agent of each round |
| `pr` | `ci_attempts` | `2` | CI attempts to reach green, re-runs included |
| | `model` | `sonnet` | the push and PR agent, CI polling and log fetching |
| | `fix_model` | `opus` | the CI fix agent |

To lower the cost of a run, put `implement.model`, `review.fix_model` and `pr.fix_model` on `sonnet` and keep `review.model` on `opus`, so the review still catches what a cheaper implementer misses.

A `config.yaml` written by an earlier install has its caps and models directly under `workflow:`, outside `defaults`: each of those keys gives an `unknown key` warning and is ignored. To skip the review or the PR, leave the `review` or `pr` step out of the workflow file.
