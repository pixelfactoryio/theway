title: Configuration
description: Every key of <home>/config.yaml and <home>/<project>/config.yaml, with its default and meaning.

The configuration lives in `<home>/config.yaml`, where `<home>` is the data home: `~/.theway` by default, or the folder chosen at install (with `--home` or the install question) or set by `THEWAY_HOME` (see [Locations](./cli.mdx#locations); `theway path` prints it). Install writes it once and keeps your copy on later installs; the shipped version is always written to `<home>/config.default.yaml`, so you can compare the two.

A project can have its own `<home>/<project>/config.yaml`, where `<project>` is the project directory name. It takes the same keys as the global file and can override any of them; install never writes it. `/theway:engineering` and `/theway:engineering-light` do not read either file themselves: they run [`theway context <project> <phase>`](./cli.mdx#context) and take their keys from the `config` it prints. `/theway:workflow` takes its `workflow.defaults` through [`theway workflow <project>`](./cli.mdx#workflow), which fills every field a workflow file leaves out. When the global `config.yaml` is missing, it fails and they tell you to run [`npx --yes @pixelfactoryio/theway@latest install`](./installation.mdx#install-and-update), then `/reload-plugins`. The `standards` keys reach the commands through the `standards` list of the same output, which applies the same layers. `/theway:document`, `/theway:archive` and `/theway:list` read no other key.

A `config.yaml` written by an earlier install may still have `changes:` and `templates:` sections, and `file` and `description` keys: each one gives an `unknown key` warning from `theway config`. It may also have `interaction`, `develop` and `tamm_framework` entries under `standards:`: those standards cannot be switched, and each entry gives a `cannot be switched` warning. You can delete them all.

## Layering

`theway config <project>` builds the effective config key by key: the defaults below, then the global `config.yaml`, then the project's `config.yaml`. For each key it takes the project file's value when it is present and valid, else the global file's value when it is present and valid, else the default. A section the project file leaves out keeps the global values, and so does every key it leaves out of a section it sets.

An invalid value is ignored with a warning on stderr, so the layer below applies: an invalid project value falls back to the global value, and an invalid global value to the default. Each warning names the file relative to the home:

```text
theway: warning: <file>: <key> must be <rule>; ignored
theway: warning: <file>: unknown key <key>; ignored
theway: warning: <file>: <key> must be a map; ignored
theway: warning: <file>: not a map; ignored
theway: warning: <file>: standards.<key> has no standard file; ignored
theway: warning: <file>: standards.<key> cannot be switched; ignored
```

`<rule>` is `a non-negative integer`, `a positive integer`, `true or false`, `opus, sonnet or haiku` or `a non-empty list of names without duplicates`. An unknown key is reported once, at its highest unknown level: an unknown section `changes:` gives `unknown key changes`, not one warning per entry. A section, `models`, `defaults` or a step under it that is not a map contributes nothing below it, and a file whose root is not a map contributes nothing. An empty or comment-only file contributes nothing, without a warning. The global file's warnings come first, then the project file's, each in file order. Invalid YAML is an error, not a warning: see [`theway config`](./cli.mdx#config).

For example, with the shipped global `config.yaml`, this `<home>/my-site/config.yaml`:

```yaml
engineering:
  review_rounds: 0
workflow:
  defaults:
    implement:
      model: sonnet
    pr:
      model: gpt
```

makes `theway config my-site` print this, with one warning on stderr, `theway: warning: my-site/config.yaml: workflow.defaults.pr.model must be opus, sonnet or haiku; ignored`:

```yaml
standards:
  core_principles:
    enabled: false
  sre:
    enabled: false
  web_development:
    enabled: false
  quality:
    enabled: false
engineering:
  review_rounds: 0
  models:
    critic: opus
workflow:
  defaults:
    implement:
      model: sonnet
    review:
      rounds: 1
      lenses:
        - conformance
        - correctness
      model: opus
      fix_model: opus
    pr:
      ci_attempts: 2
      model: sonnet
      fix_model: opus
    agent:
      model: sonnet
```

## standards

`standards.<key>.enabled` switches any standard: the four opt-in standards theway ships and your own [user standards](./concepts/standards.mdx). The key is the file stem with `-` turned into `_`: `web-development.md` is `standards.web_development`, `tdd.md` is `standards.tdd`. Both the global and the project `config.yaml` take it, so a project can switch a global standard off, or an opt-in one on, for itself only (see [Switching a standard](./concepts/standards.mdx#switching-a-standard)).

- The four opt-in standards default to `false`. The commands that read standards, `/theway:engineering`, `/theway:engineering-light`, `/theway:workflow` and `/theway:document`, read one only when its `enabled` is `true`.
- User standards default to `true`.
- `theway config <project>` prints the four opt-in keys first, in the order below, then the key of every user standard of the project, sorted, each with its effective `enabled`.
- A key with no standard file behind it, in either file, is ignored with a `has no standard file` warning.

The other shipped standards are always read and have no switch: `interaction.md` by `/theway:engineering`, `/theway:engineering-light`, `/theway:workflow`, `/theway:document` and `/theway:archive`; `develop.md` by `/theway:workflow`, inline or through its implementer agent; `tamm-framework.md` by `/theway:engineering` and `/theway:engineering-light`; `spec-review.md` and `spec-investigation.md` by `/theway:engineering` and `/theway:engineering-light`, and `spec-review.md` also by `/theway:workflow`. Their keys, `interaction`, `develop`, `tamm_framework`, `spec_review` and `spec_investigation`, give a `cannot be switched` warning, unless the project holds a file with that name in `<home>/<project>/standards/`: that file is a user standard with its own switch. `commits.md` and `git-host.md`, the [convention standards](./concepts/standards.mdx#convention-standards) `/theway:workflow` follows, have no switch either: `standards.commits` and `standards.git_host` always give a `cannot be switched` warning, and a project file with either name overrides the global one instead of being a user standard.

| Standard | `enabled` | File | Used for |
|----------|-----------|--------|----------|
| `standards.core_principles` | `false` | `<home>/standards/core-principles.md` | Architecture philosophy (simplicity, security, pragmatic technology) |
| `standards.sre` | `false` | `<home>/standards/sre.md` | SRE operational excellence (reliability, observability, automation) |
| `standards.web_development` | `false` | `<home>/standards/web-development.md` | Frontend, API and backend standards with web performance targets |
| `standards.quality` | `false` | `<home>/standards/quality.md` | Testing, deployment, monitoring and security expectations |

A `config.yaml` written by an earlier install has `standards.architecture` instead of these four entries. `standards.architecture` gives a `has no standard file` warning from `theway config`, and the four stay off until you copy them from `config.default.yaml` and set `enabled: true` on the ones you want.

[User standards](./concepts/standards.mdx), your own files in `<home>/standards/` and `<home>/<project>/standards/`, need no config entry: they are on until a `standards.<key>.enabled: false` switches them off.

## engineering

The spec review of [`/theway:engineering`](./commands/engineering.mdx#steps) (step 6). A key that is absent or invalid takes the value of the layer below (see [Layering](#layering)).

| Key | Default | Meaning |
|-----|---------|---------|
| `engineering.review_rounds` | `1` | Maximum review rounds per scaffold. A non-negative integer; `0` skips the review. |
| `engineering.models.critic` | `opus` | Model of the engineering commands' critic agents (two in `/theway:engineering`, one in `/theway:engineering-light`): `opus`, `sonnet` or `haiku`. Any other value is ignored with a warning. |

Each round spawns two critics. [`/theway:engineering-light`](./commands/engineering-light.mdx) reads the same keys and runs up to `engineering.review_rounds` rounds, with one grounding critic. To lower the cost, put `engineering.models.critic` on `sonnet`, or set `review_rounds: 0` to skip the review.

## workflow

`workflow.defaults` holds the default of every field of a [workflow](./concepts/workflows.mdx) step: a field a step of a workflow file leaves out takes its value here, from the project file, then the global file, then the default below (see [Layering](#layering)). [`theway workflow <project>`](./cli.mdx#workflow) applies them, and [`/theway:workflow`](./commands/workflow.mdx) runs what it prints. A key that is absent or invalid takes the value of the layer below. Whether a step runs inline or through agents is the workflow file's `agents` field, not a default here; an inline step takes no model.

| Key | Default | Meaning |
|-----|---------|---------|
| `workflow.defaults.implement.model` | `opus` | The implementer |
| `workflow.defaults.review.rounds` | `1` | Maximum review rounds of a `review` step. A positive integer; leave the `review` step out of a workflow to skip the review. |
| `workflow.defaults.review.lenses` | `[conformance, correctness]` | The lenses of a `review` step, one reviewer each: a non-empty list of names without duplicates. Whether each has a lens file is checked by `theway workflow`, not here. |
| `workflow.defaults.review.model` | `opus` | The reviewers, the triage agent and the fix check |
| `workflow.defaults.review.fix_model` | `opus` | The fix agent of each round |
| `workflow.defaults.pr.ci_attempts` | `2` | CI attempts to reach green, re-runs included. A positive integer. |
| `workflow.defaults.pr.model` | `sonnet` | The push and PR agent, CI polling and log fetching |
| `workflow.defaults.pr.fix_model` | `opus` | The CI fix agent |
| `workflow.defaults.agent.model` | `sonnet` | An `agent` step |

Each model is `opus`, `sonnet` or `haiku`; any other value is ignored with a warning. To lower the cost of a run, put `implement.model`, `review.fix_model` and `pr.fix_model` on `sonnet` and keep `review.model` on `opus`, so the review still catches what a cheaper implementer misses.

A `config.yaml` written by an earlier install has its caps and models directly under `workflow:`, outside `defaults`: each of those keys gives an `unknown key` warning and is ignored. To skip the review or the PR, leave the `review` or `pr` step out of the workflow file.
