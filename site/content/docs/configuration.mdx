The configuration lives in `<home>/config.yaml`, where `<home>` is the data home: `~/.theway` by default, or the folder `THEWAY_HOME` named at install (see [Locations](./cli.mdx#locations); `theway path` prints it). Install writes it once and keeps your copy on later installs; the shipped version is always written to `<home>/config.default.yaml`, so you can compare the two.

A project can have its own `<home>/<project>/config.yaml`, where `<project>` is the project directory name. It takes the same keys as the global file and can override any of them; install never writes it. `/theway:engineering`, `/theway:engineering-light`, `/theway:develop-workflow` and `/theway:document` do not read either file themselves: they run [`theway config <project>`](./cli.mdx#config) and take their keys from what it prints. When the global `config.yaml` is missing, it fails and they tell you to run [`/theway:setup`](./commands/setup.mdx). `/theway:develop`, `/theway:archive` and `/theway:list` read no key.

A `config.yaml` written by an earlier install may still have `changes:` and `templates:` sections, `interaction`, `develop` and `tamm_framework` entries under `standards:`, and `file` and `description` keys. Each one gives an `unknown key` warning from `theway config`, and you can delete them.

## Layering

`theway config <project>` builds the effective config key by key: the defaults below, then the global `config.yaml`, then the project's `config.yaml`. For each key it takes the project file's value when it is present and valid, else the global file's value when it is present and valid, else the default. A section the project file leaves out keeps the global values, and so does every key it leaves out of a section it sets.

An invalid value is ignored with a warning on stderr, so the layer below applies: an invalid project value falls back to the global value, and an invalid global value to the default. Each warning names the file relative to the home:

```text
theway: warning: <file>: <key> must be <rule>; ignored
theway: warning: <file>: unknown key <key>; ignored
theway: warning: <file>: <key> must be a map; ignored
theway: warning: <file>: not a map; ignored
```

`<rule>` is `a non-negative integer`, `a positive integer`, `true or false` or `opus or sonnet`. An unknown key is reported once, at its highest unknown level: an unknown section `changes:` gives `unknown key changes`, not one warning per entry. A section or `models` that is not a map contributes nothing below it, and a file whose root is not a map contributes nothing. An empty or comment-only file contributes nothing, without a warning. The global file's warnings come first, then the project file's, each in file order. Invalid YAML is an error, not a warning: see [`theway config`](./cli.mdx#config).

For example, with the shipped global `config.yaml`, this `<home>/my-site/config.yaml`:

```yaml
engineering:
  review_rounds: 0
workflow:
  open_pr: false
  models:
    implementer: sonnet
    ci: haiku
```

makes `theway config my-site` print this, with one warning on stderr, `theway: warning: my-site/config.yaml: workflow.models.ci must be opus or sonnet; ignored`:

```yaml
standards:
  core_principles:
    enabled: false
  sre:
    enabled: false
  web_development:
    enabled: false
  quality:
    enabled: false
engineering:
  review_rounds: 0
  models:
    critic: opus
workflow:
  review_rounds: 1
  ci_attempts: 2
  open_pr: false
  models:
    implementer: sonnet
    reviewer: opus
    fix: opus
    ci: sonnet
```

## standards

Four standards are opt-in, each with a single `enabled` key: `/theway:engineering` and `/theway:document` read a standard's file only when its `enabled` is `true`. The other standards are always read and have no key: `interaction.md` by `/theway:engineering`, `/theway:develop`, `/theway:develop-workflow`, `/theway:document` and `/theway:archive`; `develop.md` by `/theway:develop` and `/theway:develop-workflow`; `tamm-framework.md` by `/theway:engineering`.

| Standard | `enabled` | File | Used for |
|----------|-----------|--------|----------|
| `standards.core_principles` | `false` | `<home>/standards/core-principles.md` | Architecture philosophy (simplicity, security, pragmatic technology) |
| `standards.sre` | `false` | `<home>/standards/sre.md` | SRE operational excellence (reliability, observability, automation) |
| `standards.web_development` | `false` | `<home>/standards/web-development.md` | Frontend, API and backend standards with web performance targets |
| `standards.quality` | `false` | `<home>/standards/quality.md` | Testing, deployment, monitoring and security expectations |

A `config.yaml` written by an earlier install has `standards.architecture` instead of these four entries. `standards.architecture` gives an `unknown key` warning from `theway config`, and the four stay off until you copy them from `config.default.yaml` and set `enabled: true` on the ones you want.

[User standards](./concepts/standards.mdx), your own files in `<home>/standards/` and `<home>/<project>/standards/`, need no config key.

## engineering

The spec review of [`/theway:engineering`](./commands/engineering.mdx#steps) (step 6). A key that is absent or invalid takes the value of the layer below (see [Layering](#layering)).

| Key | Default | Meaning |
|-----|---------|---------|
| `engineering.review_rounds` | `1` | Maximum review rounds per scaffold. A non-negative integer; `0` skips the review. |
| `engineering.models.critic` | `opus` | Model of the two critic agents: `opus` or `sonnet`. Any other value is ignored with a warning; `haiku` is never used. |

Each round spawns two critics. [`/theway:engineering-light`](./commands/engineering-light.mdx) reads the same keys but runs at most one round, with one grounding critic. To lower the cost, put `engineering.models.critic` on `sonnet`, or set `review_rounds: 0` to skip the review.

## workflow

Caps for [`/theway:develop-workflow`](./commands/develop-workflow.mdx). A key that is absent or invalid takes the value of the layer below (see [Layering](#layering)).

| Key | Default | Meaning |
|-----|---------|---------|
| `workflow.review_rounds` | `1` | Review rounds per change. A non-negative integer; `0` skips the local review. A light change (`**Mode:** light`) runs at most one round. |
| `workflow.ci_attempts` | `2` | CI attempts per change to reach green, re-runs included. A positive integer. |
| `workflow.open_pr` | `true` | After the local review, push the branch, open the PR and drive CI. `false` stops at the reviewed local branch: nothing is pushed, and a series stacks each change on a local branch created from the previous one. |

### workflow.models

The model each agent role of `/theway:develop-workflow` runs on. Each value is `opus` or `sonnet`; any other value is ignored with a warning. `haiku` is never used.

| Key | Default | Agents |
|-----|---------|--------|
| `workflow.models.implementer` | `opus` | Implementers. When `opus`, `sonnet` is still allowed for mechanical tasks. |
| `workflow.models.reviewer` | `opus` | Adversarial reviewers and the fix check |
| `workflow.models.fix` | `opus` | Fix agents |
| `workflow.models.ci` | `sonnet` | CI polling and log fetching |

To lower the cost of a run, put `implementer`, `fix` and `ci` on `sonnet` and keep `reviewer` on `opus`, so the review still catches what a cheaper implementer misses. `review_rounds: 0` lowers it further by skipping the local review.
