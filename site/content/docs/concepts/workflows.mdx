---
title: Workflows
description: The YAML files that list the steps /theway:workflow runs, the lenses its reviewers follow, and how both are found.
---

A workflow is a YAML file that lists the steps [`/theway:workflow`](../commands/workflow.mdx) runs for each change, in order: implement, review, any agent of your own, and the PR. Each step runs through agents or inline, in your session. A lens is a Markdown brief for one reviewer of a `review` step. theway ships two workflows, `develop` and `agents`, and two lenses, `conformance` and `correctness`; you add your own next to them, globally or for one project.

## Files and layering

| What | Global | Project (wins by name) | Shipped |
|---|---|---|---|
| Workflows | `<home>/workflows/<name>.yaml` | `<home>/projects/<key>/workflows/<name>.yaml` | `develop.yaml`, `agents.yaml` |
| Lenses | `<home>/lenses/<name>.md` | `<home>/projects/<key>/lenses/<name>.md` | `conformance.md`, `correctness.md` |

- A workflow's name is its file stem; the file has no `name` key. A name is lowercase letters and digits in words separated by single hyphens (`develop-secure`).
- A project file wins over a global file of the same name.
- Install writes the shipped files into `<home>/workflows/` and `<home>/lenses/` and treats them as it treats the shipped [standards](./standards.mdx): it updates a file you have not edited, keeps one you have and writes the shipped version next to it as `<name>.default.yaml` or `<lens>.default.md`, keeps your own file when theway starts shipping one with its name, and removes an unedited file theway stops shipping. A `*.default.yaml` or `*.default.md` file is never a workflow or a lens.

## The shipped workflows

`develop.yaml`, the default when no file sets `default: true`:

```yaml
# The workflow /theway:workflow runs when no file sets default: true: the tasks done inline in your session, nothing committed.
agents: false
steps:
  - implement:
```

It implements the tasks inline, in your session, following `develop.md`, and verifies them. It creates no branch and commits nothing: the change stays in your working tree for you to review. It runs one change at a time; a series needs a workflow that commits.

`agents.yaml`:

```yaml
# Implement, review and open the PR through agents. Fields left out come from workflow.defaults in config.yaml.
steps:
  - implement:
  - review:
  - pr:
```

It implements the change with one agent on a feature branch, reviews it locally with the `conformance` and `correctness` lenses for one round, then pushes the branch, opens the PR and drives CI to green. Run it with `/theway:workflow --workflow agents <change-id>`, or copy it under another name with `default: true`.

## Steps

Each entry of `steps` is a map with exactly one key, the step type, whose value is a map of fields or nothing (`- implement:` and `- implement: {}` are the same). A field left out takes its value from [`workflow.defaults`](../configuration.mdx#workflow), except `agents` (see [Inline or through agents](#inline-or-through-agents)).

| Step | Field | Rule | Default | Used by |
|---|---|---|---|---|
| every step | `agents` | `true` or `false` | the top-level `agents`, else `true` | `false` runs the step inline, in your session |
| `implement` | `model` | `opus`, `sonnet` or `haiku` | `opus` | the implementer |
| `review` | `rounds` | a positive integer | `1` | the maximum review rounds |
| | `lenses` | a non-empty list of names, no duplicates | `[conformance, correctness]` | one reviewer per lens |
| | `model` | a model | `opus` | the reviewers, the triage agent and the fix check |
| | `fix_model` | a model | `opus` | the fix agent of each round |
| `agent` | `name` | a name, required | none | its label and its report |
| | `prompt` | a non-empty string, required | none | the agent's task |
| | `model` | a model | `sonnet` | the agent |
| `pr` | `ci_attempts` | a positive integer | `2` | CI attempts, re-runs included |
| | `model` | a model | `sonnet` | the push and PR agent, CI polling and log fetching |
| | `fix_model` | a model | `opus` | the CI fix agent |

- **`implement`:** one implementer follows `develop.md`, commits locally on the feature branch and verifies its work. It stops with a blocker when the spec does not fit the code.
- **`review`:** each round, one reviewer per lens reviews the branch diff, a triage agent gives each finding a verdict of `spec-review.md`, one fix agent fixes the confirmed findings, and a fix check marks each one `resolved` or `not resolved`. A round with no confirmed finding ends the step.
- **`agent`:** one agent runs your `prompt` after the fixed rules every agent gets. It may commit on the feature branch and does not push. When it reports that it could not do the task, the change fails.
- **`pr`:** pushes the branch once, opens the PR and drives CI until it is green or `ci_attempts` is used up.

These describe a step through agents; with `agents: false`, your session does the same work itself.

## Inline or through agents

`agents` is a boolean, at the top level of the file and on any step. A step's value is its own `agents`, else the top-level one, else `true`.

- **`agents: true`:** the step runs through agents in the plugin workflow `theway:run-pipeline`, with the models of its fields. Consecutive steps with `agents: true` run as one segment: one Workflow call.
- **`agents: false`:** your session does the step itself, under the same rules the script gives that step's agents. An inline step takes no model: setting `model` or `fix_model` on it is an error, `steps[<i>].<type>.<field> has no effect when the step runs inline (agents: false)`, and `theway workflow` prints no model for it.
- An inline `implement` followed by other steps commits on the feature branch, and the later segments start from its head. An inline `implement` that is the only step commits nothing and creates no branch.
- An inline `review` is a self-check: the session reviews its own diff through each lens, one after the other, triages, fixes and checks its fixes, and the report says "review ran inline". It is not the independent review that separate reviewer agents give.

```yaml
# Implement inline, then review and open the PR through agents.
steps:
  - implement: {agents: false}
  - review:
  - pr:
```

The first Workflow call of a run shows Claude Code's permission prompt for `theway:run-pipeline`: approve it once, or choose "don't ask again" for `theway:run-pipeline`. A workflow whose steps all run inline makes no Workflow call.

Every agent gets the same fixed rules first, which no field changes: the `## Authority` section of `interaction.md`, commits only on the feature branch, no force-push, no push of the default branch, no merge, and the change files read-only. How the branch, commits and PR are named, and the git host's commands, come from the [convention standards](./standards.mdx#convention-standards) `commits.md` and `git-host.md`, which every step follows.

## Rules

- The top-level keys are `default`, `agents` and `steps`; any other key is an error.
- `default` and `agents` are `true` or `false`.
- `steps` is a non-empty list. The first step is `implement`, inline or not, and `implement` appears once; `pr` appears at most once, as the last step; `review` and `agent` appear any number of times.
- A workflow with no `pr` step pushes nothing and opens no PR. To skip the review, leave out the `review` step: `rounds` has no `0`.
- Every lens of a `review` step must have a file.

[`theway workflow`](../cli.mdx#workflow) checks every rule and exits 1 on the first error, so a run never starts on a workflow it does not fully understand.

## Lenses

A lens is the brief of one reviewer: what to look for in the diff. The reviewer reads it and follows it, on top of the fixed rules every reviewer gets (refute or break the diff, check it against the standards, change nothing). Its findings are triaged with the other lenses' findings.

- `conformance.md`: checks the diff against `spec.md`: each Success Criterion met, nothing outside Scope or in Out of Scope, nothing the spec did not ask for; for a light spec, against its Change section.
- `correctness.md`: checks correctness, edge cases and convention violations; for a `fix-` change, that the diff fixes the root cause the spec names and that the regression test would fail without the fix.

Write a new lens as `<home>/lenses/<name>.md`, or `<home>/projects/<key>/lenses/<name>.md` for one project, and name it in a `review` step's `lenses`. A project lens replaces the global lens of the same name for that project.

## Which workflow runs

- `/theway:workflow --workflow <name> <change-id>` runs the workflow `<name>`: the project file, else the global one.
- Without `--workflow`, it runs the default: the project's file that sets `default: true`, else the global file that sets it (one no project file of the same name shadows), else `develop`, the inline one. Two files of the same folder that both set `default: true` are an error.

There is no config key for the default workflow: mark the file with `default: true`.

## Example: a security review

A global `<home>/workflows/develop-secure.yaml` that adds a third lens, two review rounds and a changelog entry before the PR:

```yaml
default: true
steps:
  - implement: {model: opus}
  - review: {rounds: 2, lenses: [conformance, correctness, security], model: opus, fix_model: opus}
  - agent: {name: changelog, prompt: "Add an entry for this change to CHANGELOG.md under Unreleased.", model: sonnet}
  - pr: {ci_attempts: 2, model: sonnet, fix_model: opus}
```

with its lens, `<home>/lenses/security.md`:

```markdown
# Security

Check the diff for injection, missing input validation, secrets in code or logs, and authorization checks that a new path skips.
```

With `default: true`, every project without a default of its own runs it.

## Example: a project workflow without a PR

For a project whose changes you push yourself, `<home>/projects/-home-you-code-my-api/workflows/local.yaml` stops at the reviewed local branch, with cheaper models:

```yaml
default: true
steps:
  - implement: {model: sonnet}
  - review: {lenses: [correctness]}
```

`/theway:workflow add-rate-limiting` on `my-api` now implements and reviews the change and pushes nothing. In a series, each change's branch is created from the previous one and nothing is merged.
