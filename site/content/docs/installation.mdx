## Requirements

- `~/.local/bin` on your `PATH`, or another install folder that is (see [Other locations](#other-locations)). The commands call the CLI as plain `theway`, so they fail with `theway: command not found` when its folder is not on `PATH`. On macOS it is not there by default: add `export PATH="$HOME/.local/bin:$PATH"` to your shell profile, then start Claude Code from a new shell.
- Node.js 22.12 or later.
- macOS or Linux.
- Claude Code.

## Install and update

```bash
npx --yes @pixelfactoryio/theway@latest install
```

Every run fetches the latest release from npm, so running the command again updates theway. When it finishes, start a new Claude Code session or run `/reload-plugins`.

When the install folder is not on your `PATH`, install still finishes and exits 0, and prints the line to add:

```text
Add /home/you/.local/bin to your PATH, e.g.: export PATH="/home/you/.local/bin:$PATH"
```

From a session where theway is already loaded, `/theway:setup` runs the same command.

## Pin to a release

To install a specific release, add its version:

```bash
npx --yes @pixelfactoryio/theway@X.Y.Z install
```

The versions are listed on [npm](https://www.npmjs.com/package/@pixelfactoryio/theway?activeTab=versions).

## Uninstall

```bash
npx --yes @pixelfactoryio/theway@latest uninstall
```

Uninstall removes `~/.claude/skills/theway`, the `theway` binary when it is the one install wrote, the pointer file and the permission rules: those of `THEWAY_HOME`, of the home the pointer names and of `~/.theway`, and the rules of 0.2.0. The data home (`~/.theway`, or your custom home) is kept, with your changes and your config.

## What install writes

- **`~/.claude/skills/theway`:** the plugin, with its commands. Claude Code loads it as `theway@skills-dir`. Each install replaces this folder.
- **`~/.local/bin/theway`:** the [CLI](./cli.mdx) the commands call, a single executable file run by the `node` on your `PATH`. Install replaces a theway binary there, but not another program called `theway`: it then stops, changes nothing, and asks you to remove it or set `THEWAY_INSTALL_DIR`.
- **The data home, `~/.theway`** by default:
  - `config.yaml`: the [configuration](./configuration.mdx). An existing `config.yaml` is kept.
  - `config.default.yaml`: the shipped configuration, written on every install.
  - `standards/` and `templates/`: the standards and templates the commands read. Install updates the files you have not edited. A file you edited is kept, and the new shipped version is written next to it as `<name>.default.md`. `.shipped.json` records what install last shipped.
    - `standards/` also holds your [global user standards](./concepts/standards.mdx). When theway starts shipping a name you already use there, install keeps your file, writes its version as `<name>.default.md`, leaves the name out of `.shipped.json` so the file stays yours, and prints `Kept your standards/<name>: theway now ships a file with that name (its version: standards/<base>.default.md)` on every install while the clash lasts. When you have no `.shipped.json`, a differing file with a shipped name is treated as an edited shipped file instead.
    - A standard theway stops shipping is removed when you have not edited it (`Removed standards/<name>: theway no longer ships it`) and kept as one of your standards when you have (`Kept your edited standards/<name>: theway no longer ships it, so it is now one of your standards`). Install also removes a `standards/<name>.default.md` whose `<name>.md` it no longer ships.
    - A template theway no longer ships is left in `templates/` untouched. A differing template that `.shipped.json` does not list is backed up to `<name>.md.bak` and replaced.
  - `<project>/changes/`: the change folders, written by the commands.
- **`~/.config/theway/home`**, only for a custom `THEWAY_HOME`: the pointer file that holds the absolute data home, so the CLI finds it when `THEWAY_HOME` is not set. With the default home (`THEWAY_HOME` set to `~/.theway`, or neither `THEWAY_HOME` nor a pointer), install writes no pointer and removes an existing one.
- **Two permission rules**, added to `permissions.allow` in `~/.claude/settings.json` when they are missing:
  - `Bash(theway:*)`: runs the CLI without a prompt.
  - `Read(~/.theway/**)`: reads the data home.

  For a custom home, the `Read` rule names its absolute path, such as `Read(//data/tw/**)`.

  Writing change files (`spec.md`, `tasks.md`) goes through Claude Code's normal permission prompt. Earlier versions also added `Edit(~/.theway/*/changes/**)`; install and uninstall remove it.

If `~/.claude/settings.json` is not valid settings JSON, install stops and changes nothing.

`Bash(theway:*)` approves whichever `theway` comes first on your `PATH`, not only the copy install wrote. Install lists every `theway` on `PATH` and warns, naming it, when the first one is not its copy:

```text
theway: warning: /usr/local/bin/theway comes before /home/you/.local/bin/theway on PATH, so the commands run it; theway copies on PATH: …
```

### From the old layout

Earlier versions installed the standards in `data/standards/`. On its first run over such a home, install moves each standard `.shipped.json` lists from `data/standards/` to `standards/` as it is, edited or not, with its `.default.md` copy, and renames its `.shipped.json` key with the same hash. It leaves a file in place, with a line, when `standards/` already holds that name (`Left data/standards/<name>: standards/<name> already exists`) or theway no longer ships it (`Left data/standards/<name>: theway no longer ships it`); files `.shipped.json` does not list are never moved. It then removes `data/standards/` and `data/` when they are empty, and otherwise prints `Left data/: it still holds files theway does not ship`. An interrupted migration finishes on the next install.

### Other locations

- `CLAUDE_CONFIG_DIR` replaces `~/.claude` when it is set.
- `THEWAY_INSTALL_DIR` replaces `~/.local/bin` when it is set. Pick a folder already on your `PATH`, such as `/opt/homebrew/bin`. Set it again when you uninstall.
- `THEWAY_HOME` replaces `~/.theway` as the data home when it is set at install. Install records it in the pointer file, so nothing is written to `~/.theway` and the commands find the home without `THEWAY_HOME` in Claude Code's environment. `XDG_CONFIG_HOME` replaces `~/.config` for the pointer file.

The CLI looks for the data home in this order: `THEWAY_HOME` when it is set in its environment, then the pointer file, then `~/.theway`. After changing `THEWAY_HOME`, run install again with the new value: it rewrites the pointer, adds the rules of the new home and drops the `Read` and `Edit` rules of the previous one. Until then, `theway path` warns that `THEWAY_HOME` and the pointer differ.

Install refuses a data home that is your home folder or one of its parents, or a custom home that contains a glob character (`*?[]{}`) or a line break: the permission rules it writes would cover far more than theway's files. It exits 1 and changes nothing.

Install finds the data home the same way. Without `THEWAY_HOME`, it updates the home the pointer names, so `/theway:setup`, which sees `THEWAY_HOME` only when it is exported in the shell that started Claude Code, keeps a custom home. To go back to `~/.theway`, run install with `THEWAY_HOME=~/.theway`.

## Upgrading from 0.2.0

theway 0.2.0 installed the CLI in the data home, as `bin/theway` and `bin/theway.js`, with the rule `Bash(~/.theway/bin/theway:*)` (or the absolute path for a custom home). Installing this version over it removes those two files when they are the ones 0.2.0 wrote, the `bin/` folder when nothing else is in it, and the old rule. Your config and change folders stay where they are.
