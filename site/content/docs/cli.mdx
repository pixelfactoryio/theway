The `theway` program has twelve subcommands: `install`, `uninstall`, `list`, `archive`, `path`, `config`, `standards`, `context`, `workflow`, `authority`, `validate-id` and `next-id`. Install writes it to `~/.local/bin/theway` (or `$THEWAY_INSTALL_DIR/theway`), and the slash commands call it as plain `theway`, so its folder must be on your `PATH`. See [Installation](./installation.mdx#requirements).

```text
theway install [--home <path>] [--standards <keys>]
theway uninstall
theway list <project>
theway archive <project> <change-id> [--force]
theway path [<project> [<change-id>]] [--verbose]
theway config <project>
theway standards <project> <engineering|develop|document>
theway context <project> <engineering|develop|document> [<change-id>]
theway workflow <project> [<name>]
theway authority
theway validate-id <id> [--series]
theway next-id <project> <series-id> [--count <n>]
```

It needs Node.js 22.12 or later and exits 1 with a message on older versions.

## Locations

The data home holds the config, the standards, the templates and the change folders. The CLI resolves it on every run, in this order:

1. `THEWAY_HOME`, when it is set and not empty.
2. The pointer file `${XDG_CONFIG_HOME:-~/.config}/theway/home`, when it exists and is not empty. Install writes it whenever the resulting home is not the default: one chosen with `--home` or the install question, one set by `THEWAY_HOME`, or the custom home an earlier pointer names on a reinstall.
3. `~/.theway`.

[`theway path --verbose`](#path) says which one it used.

[User standards](./concepts/standards.mdx) live in `<home>/standards/` (every project) and `<home>/<project>/standards/` (one project). Install never touches them.

Other environment variables:

- `CLAUDE_CONFIG_DIR` replaces `~/.claude`.
- `THEWAY_INSTALL_DIR` replaces `~/.local/bin`, for install and uninstall.

## install

```bash
npx --yes @pixelfactoryio/theway@latest install
```

Copies the plugin to `~/.claude/skills/theway`, the CLI to `~/.local/bin/theway`, sets up the data home (`--home`, else `THEWAY_HOME`, else the home the pointer names, else `~/.theway`), writes or removes the pointer file and adds the two permission rules to `~/.claude/settings.json`, always dropping the `Edit` rules earlier versions added, and dropping the previous home's `Read` rule when the home changed. It stops and changes nothing when `~/.local/bin/theway` is another program, not a theway binary. It also stops and changes nothing when the data home is your home folder or one of its parents, or a custom home containing a glob character or a line break. It prints the `export PATH=…` line when the install folder is not on `PATH`, and warns when another `theway` comes first on `PATH`. Run it through `npx`, which carries the plugin files; the installed `theway install` exits 1 and prints the `npx` command. See [What install writes](./installation.mdx#what-install-writes).

On a first install from a terminal (stdin and stdout), it asks where to keep the data home, only when theway was never installed, then which opt-in standards to enable, only when the data home has no `config.yaml`. The options answer without a question:

- `--home <path>`: the data home, an absolute path or one starting with `~/`.
- `--standards <keys>`: the opt-in standards to enable in a new `config.yaml`, comma-separated (`core_principles`, `sre`, `web_development`, `quality`), or `none`.

It exits 1 and changes nothing when:

- `--home` is not an absolute path and does not start with `~/`: `theway: invalid --home '<value>': must be an absolute path or start with ~/; nothing was changed`;
- `--home` and a set `THEWAY_HOME` name different paths: `theway: --home <a> and THEWAY_HOME <b> differ; unset THEWAY_HOME or drop --home; nothing was changed`;
- `--standards` names an unknown key: `theway: unknown standard '<element>' in --standards; valid: core_principles, sre, web_development, quality, or none`;
- `--standards` combines `none` with a key: `theway: --standards none cannot be combined with other standards`;
- `--standards` is given and the data home already has a `config.yaml`: `theway: --standards applies only to a first install; <home>/config.yaml exists, so set standards.<key>.enabled there instead; nothing was changed`;
- you cancel a question: `theway: install cancelled; nothing was changed`.

With no terminal and no `--standards`, a first install leaves the opt-in standards off and prints the line that says how to enable one.

## uninstall

```bash
npx --yes @pixelfactoryio/theway@latest uninstall
```

Removes `~/.claude/skills/theway`, `~/.local/bin/theway` when it is a theway binary, the pointer file and the permission rules of `THEWAY_HOME`, of the home the pointer names and of `~/.theway`. The data home is kept.

## list

```bash
theway list <project>
```

Prints the active changes of `<project>`, each with its number of `.md` files and its ticked numbered tasks out of all numbered tasks, then the archived change folders and a summary line. Only numbered checkbox lines in `tasks.md` (`N.` or `Na.`) count as tasks. Used by [`/theway:list`](./commands/list.mdx) and [`/theway:archive`](./commands/archive.mdx).

`<project>` must follow the same rule as for [`path`](#path); otherwise it exits 1 with one reason on stderr.

## archive

```bash
theway archive <project> <change-id> [--force]
```

Moves `<home>/<project>/changes/<change-id>` to `<home>/<project>/changes/archive/YYYY-MM-DD-<change-id>`, with today's local date, and prints `Archived: <path>`.

It exits 1 and moves nothing when:

- `<project>` or `<change-id>` does not follow the rules of [`path`](#path);
- the change folder does not exist;
- the archive folder already exists;
- `tasks.md` has unticked numbered tasks. It prints each one with its line number.

`--force` archives despite unticked numbered tasks and prints them as a warning.

## path

```bash
theway path
theway path <project>
theway path <project> <change-id>
```

Prints one line on stdout:

- `theway path`: the data home, such as `/home/you/.theway`.
- `theway path <project>`: `<home>/<project>`.
- `theway path <project> <change-id>`: `<home>/<project>/changes/<change-id>`, whether or not the folder exists yet.

The slash commands run it to find the home (for the config, standards and templates) and the change folder they read and write.

`--verbose` adds one line on stderr naming where the home came from:

```text
theway: home /data/tw (from pointer)
```

The source is `env`, `pointer` or `default`. When `THEWAY_HOME` is set and differs from the pointer file, it prints the `THEWAY_HOME` value and one warning on stderr that names both values and their sources. Run install again with the new `THEWAY_HOME` to update the pointer.

A change id must be lowercase letters and digits in words separated by single hyphens (as `validate-id` produces); a project must be letters, digits, `.`, `_` or `-`, not starting with `.` or `-`; both at most 200 characters. Any other value exits 1 with one reason on stderr:

```text
theway: invalid change id '..': must be lowercase letters and digits in words separated by single hyphens
```

## config

```bash
theway config <project>
```

Prints the effective [configuration](./configuration.mdx) of `<project>` as YAML on stdout: the defaults, then `<home>/config.yaml`, then `<home>/<project>/config.yaml` when it exists, merged key by key (see [Layering](./configuration.mdx#layering)). It prints every key, sections in the order `standards`, `engineering`, `workflow`, without comments, and every value it prints is valid. `/theway:engineering`, with or without `--light`, takes its keys from the same config, through [`context`](#context), and [`workflow`](#workflow) takes `workflow.defaults` from it.

The `standards` section lists every switchable [standard](./concepts/standards.mdx#switching-a-standard) of the project, each as `<key>:` with its effective `enabled`: the four opt-in keys `core_principles`, `sre`, `web_development` and `quality` first, then the keys of the user standards of `<home>/standards/` and `<home>/<project>/standards/`, sorted. For a project named `data`, `templates`, `standards`, `workflows` or `lenses`, only the global ones are listed.

```text
standards:
  core_principles:
    enabled: false
  ...
workflow:
  defaults:
    ...
    pr:
      ci_attempts: 2
      model: sonnet
      fix_model: opus
```

An invalid value, an unknown key, a section that is not a map or a file whose root is not a map is ignored with a warning on stderr, the global file's first, and the exit code stays 0. `<file>` is the path relative to the home, `config.yaml` or `<project>/config.yaml`:

```text
theway: warning: <file>: <key> must be <rule>; ignored
theway: warning: <file>: unknown key <key>; ignored
theway: warning: <file>: <key> must be a map; ignored
theway: warning: <file>: not a map; ignored
theway: warning: <file>: standards.<key> has no standard file; ignored
theway: warning: <file>: standards.<key> cannot be switched; ignored
```

The last two name a `standards` key that no standard file of the project gives, and the key of a standard that is always read (`interaction`, `develop`, `tamm_framework`, `spec_review`, `spec_investigation`).

It exits 1 and prints nothing on stdout when:

- `<project>` does not follow the rule of [`path`](#path), with the same reason on stderr;
- `<home>/config.yaml` is missing:

  ```text
  theway: config.yaml not found in <home>; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins
  ```

- either file exists but cannot be read:

  ```text
  theway: <file>: cannot be read
  ```

- either file is not valid YAML, duplicate keys included:

  ```text
  theway: <file>: invalid YAML: Map keys must be unique at line 3, column 3
  ```

## standards

```bash
theway standards <project> engineering
theway standards <project> develop
theway standards <project> document
```

Prints the absolute path of every enabled [standard](./concepts/standards.mdx) that applies to the phase, one per line: the regular `.md` files directly in `<home>/standards/`, then directly in `<home>/<project>/standards/`, each group sorted by name. Subfolders and other files are ignored. In `<home>/standards/`, `interaction.md`, `develop.md`, `tamm-framework.md`, `spec-review.md` and `spec-investigation.md` are never listed; `commits.md` and `git-host.md`, the [convention standards](./concepts/standards.mdx#convention-standards), are never listed from either folder; `core-principles.md`, `sre.md`, `web-development.md` and `quality.md` are the opt-in standards; the other files that `.shipped.json` lists as `standards/<name>`, and any `*.default.md` copy there, belong to theway and are not listed. A project file with the same name as a global one replaces it for the phases the project file applies to; for the other phases, the global file is printed as usual.

- A standard, opt-in or yours, applies to the phases its `applies_to` frontmatter lists (`engineering`, `develop` and/or `document`), or to all three without one.
- A standard is printed only when its effective `standards.<key>.enabled` is `true`: it computes the project's config as [`config`](#config) does, without printing its warnings. A missing `<home>/config.yaml` counts as empty, so the defaults apply: opt-in standards off, user standards on.
- For a project named `data`, `templates`, `standards`, `workflows` or `lenses`, the project's `standards/` folder is not read: those folders of the home hold theway's own files, and `data/` can still hold the standards of an [older layout](./installation.mdx#from-the-old-layout). The global standards are still listed.

With nothing to print, it prints nothing and exits 0.

```text
/home/you/.theway/standards/tdd.md
/home/you/.theway/my-repo/standards/review.md
```

An enabled file whose `applies_to` has any other value or form is skipped for every phase, with a warning on stderr; the exit code stays 0:

```text
theway: warning: <path>: applies_to must list engineering, develop and/or document; skipped
```

A file that cannot be read is skipped, with a warning on stderr; the others are still listed and the exit code stays 0:

```text
theway: warning: <path>: cannot be read; skipped
```

It exits 1 and prints nothing on stdout when:

- `<project>` does not follow the rule of [`path`](#path), with the same reason on stderr;
- the phase is not `engineering`, `develop` or `document`:

  ```text
  theway: invalid phase '<value>': must be engineering, develop or document
  ```

- either `config.yaml` cannot be read or is not valid YAML, with the message of [`config`](#config).

The commands get the same list through [`context`](#context).

## context

```bash
theway context <project> <engineering|develop|document>
theway context <project> <engineering|develop|document> <change-id>
```

Prints what a command loads in its first step, as one YAML document with these keys, in this order:

- `home`: the data home, as [`path`](#path) prints it;
- `change_dir`: only with `<change-id>`, the folder `theway path <project> <change-id>` prints;
- `standards`: the paths [`standards`](#standards) prints for the phase, as a list, `[]` when there are none;
- `config`: the effective config [`config`](#config) prints.

```text
home: /home/you/.theway
change_dir: /home/you/.theway/my-repo/changes/add-redis-cache
standards:
  - /home/you/.theway/standards/tdd.md
config:
  standards:
    ...
```

It writes the warnings of `config` to stderr once. It exits 1 and prints nothing on stdout when `<project>` or `<change-id>` does not follow the rule of [`path`](#path), when the phase is invalid (the message of [`standards`](#standards)), or when `<home>/config.yaml` is missing or a config file cannot be read or is not valid YAML (the messages of [`config`](#config)).

`/theway:engineering`, with or without `--light`, runs it with `engineering`, `/theway:document` with `document`, and `/theway:workflow` with `develop` and the change ID, taking `change_dir` as the change folder.

## workflow

```bash
theway workflow <project>
theway workflow <project> <name>
```

Resolves one [workflow](./concepts/workflows.mdx), validates it, fills every field its steps leave out from [`workflow.defaults`](./configuration.mdx#workflow), and prints it as JSON on stdout. [`/theway:workflow`](./commands/workflow.mdx) runs it once per run and passes the result to its pipeline.

Which file:

- **With `<name>`:** `<home>/<project>/workflows/<name>.yaml` when it is a file, else `<home>/workflows/<name>.yaml`.
- **Without `<name>`, the default:**
  1. The project's folder: every workflow file in it is validated, in file-name order, and the one that sets `default: true` is the default.
  2. Only when the project has none, the global folder: the same, over the global files that no project file of the same name shadows. A shadowed global file is not read.
  3. When neither has one, `develop` (the shipped one runs a single inline `implement`), looked up as with `<name>`.
- A `<name>` matches `^[a-z0-9]+(-[a-z0-9]+)*$`; the workflow's name is its file stem. A `*.default.yaml` file is the shipped copy install writes next to an edited file, never a workflow. While it scans a folder for the default, a `.yaml` file whose stem is not a valid name is skipped with `theway: warning: <file>: not a valid workflow name; ignored`.
- Each lens of a `review` step is `<home>/<project>/lenses/<lens>.md` when it is a file, else `<home>/lenses/<lens>.md`. For a project named `data`, `templates`, `standards`, `workflows` or `lenses`, no project folder is read.

`theway workflow my-api agents`, with the shipped `agents.yaml`:

```json
{
  "name": "agents",
  "file": "/home/you/.theway/workflows/agents.yaml",
  "commits": "/home/you/.theway/standards/commits.md",
  "git_host": "/home/you/.theway/standards/git-host.md",
  "steps": [
    { "step": "implement", "agents": true, "model": "opus" },
    { "step": "review", "agents": true, "rounds": 1, "lenses": [{ "name": "conformance", "path": "/home/you/.theway/lenses/conformance.md" }, { "name": "correctness", "path": "/home/you/.theway/lenses/correctness.md" }], "model": "opus", "fix_model": "opus" },
    { "step": "pr", "agents": true, "ci_attempts": 2, "model": "sonnet", "fix_model": "opus" }
  ]
}
```

`commits` and `git_host` are the paths of the [convention standards](./concepts/standards.mdx#convention-standards): `<home>/<project>/standards/commits.md` and `git-host.md` when they are files (not for a project named `data`, `templates`, `standards`, `workflows` or `lenses`), else the global ones. The global files must exist, even when the project overrides them: checked after the workflow file is validated, a missing one exits 1 with `theway: <home>/standards/commits.md not found; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins` (or `git-host.md`).

Every field of every step is printed, `step` first, then `agents`: the step's own value, else the file's top-level `agents`, else `true`. A step with `agents: false` runs inline and has no `model` or `fix_model`; the shipped `develop` prints `"steps": [{ "step": "implement", "agents": false }]`. It writes the warnings of [`config`](#config) to stderr. Any error writes one line on stderr, prints nothing on stdout and exits 1: the messages of `config` for a missing or invalid config file, the rule of [`path`](#path) for `<project>`, and these, where `<file>` is the path relative to the home:

```text
theway: invalid workflow name '<name>'
theway: no workflow '<name>' in <home>/<project>/workflows or <home>/workflows
theway: workflows/a.yaml and workflows/b.yaml both set default: true
theway: <file>: steps[1]: pr must be the last step
theway: <file>: steps[0].implement.model has no effect when the step runs inline (agents: false)
```

A workflow file error is the first one found: the file cannot be read or is not valid YAML; the root is not a map, has a key other than `default`, `agents` and `steps`, `default` or `agents` is not `true` or `false`, or `steps` is not a non-empty list; then, step by step, a step that is not one of `implement`, `review`, `agent`, `pr`, a field its type does not have, a value that breaks its rule, a `model` or `fix_model` on an inline step, a missing `agent` `name` or `prompt`, a step out of order, and a lens with no file. [Workflows](./concepts/workflows.mdx#rules) lists each rule.

## authority

```bash
theway authority
```

Prints the `## Authority` section of `<home>/standards/interaction.md`: from its heading up to the next `## ` heading or the end of the file, without trailing blank lines. When that file is missing or has no such section (an edited copy that install kept), it prints the section of `<home>/standards/interaction.default.md`. When neither has it, it exits 1:

```text
theway: no ## Authority section in <home>/standards/interaction.md or interaction.default.md; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins
```

The commands that spawn agents quote its output verbatim in every agent prompt.

## validate-id

```bash
theway validate-id <id>
theway validate-id <id> --series
```

Checks a [change ID](./concepts/changes.mdx#change-ids). It exits 0 when the ID is valid. Otherwise it exits 1 and prints one line on stderr:

```text
invalid change id '<id>': <reason>
```

Every ID must be lowercase kebab-case (`[a-z0-9]` segments joined by single hyphens) and start with `add-`, `update-`, `refactor-`, `remove-` or `fix-`. Any other start is rejected with:

```text
invalid change id '<id>': must start with a verb prefix: add-, update-, refactor-, remove- or fix-
```

- **Without `--series`** (a standalone change): the ID must not end in a one- or two-digit number.
- **With `--series`** (a series member): the ID must end in a two-digit ordinal from `01`, such as `add-user-auth-01`. Letter suffixes, `-00` and double ordinals are rejected.

`/theway:engineering`, with or without `--light`, runs it before it writes a standalone change folder; [`next-id`](#next-id) validates the members of a series.

## next-id

```bash
theway next-id <project> <series-id>
theway next-id <project> <series-id> --count <n>
```

Prints the next `<n>` free member IDs of a [series](./concepts/changes.mdx#series), one per line (`--count` defaults to 1):

```text
add-user-auth-04
add-user-auth-05
```

- A trailing `-NN` is removed from `<series-id>` first, so `add-user-auth-07` gives the same IDs as `add-user-auth`. The rest must fit the [`validate-id`](#validate-id) format and must not end in a one- or two-digit number; when it is invalid, it exits 1 with an `invalid change id '<id>': <reason>` line, `<id>` being the series ID without its ordinal, for example:

  ```text
  invalid change id 'add-thing-01': ends in a number (-01); a series id cannot end in a number
  ```

- It counts the folders `<home>/<project>/changes/<series-id>-NN` and the archived `<home>/<project>/changes/archive/YYYY-MM-DD-<series-id>-NN`, and continues after the highest `NN`, or from `01` when there is none.
- A `--count` that is not a positive integer is rejected with `must be a positive integer`. When the last ID would be past `-99`, it exits 1:

  ```text
  theway: series <series-id> would go past -99
  ```

`/theway:engineering` runs it to name the members of a new series.
