The `theway` program has fifteen subcommands: `install`, `uninstall`, `list`, `archive`, `path`, `project`, `config`, `standards`, `context`, `workflow`, `steps`, `authority`, `validate-id`, `next-id` and `dashboard`. Install writes it to `~/.local/bin/theway` (or `$THEWAY_INSTALL_DIR/theway`), and the slash commands call it as plain `theway`, so its folder must be on your `PATH`. See [Installation](./installation.mdx#requirements).

```text
theway install [--home <path>] [--standards <keys>]
theway uninstall
theway list [--project <key>]
theway archive <change-id> [--force] [--project <key>]
theway path [<change-id>] [--verbose] [--project <key>]
theway project [--project <key>]
theway config [--project <key>]
theway standards <engineering|develop|document> [--project <key>]
theway context <engineering|develop|document> [<change-id>] [--project <key>]
theway workflow [<name>] [--project <key>]
theway steps [<name>] [--project <key>]
theway authority
theway validate-id <id> [--series]
theway next-id <series-id> [--count <n>] [--project <key>]
theway dashboard [--port <n>]
```

It needs Node.js 22.12 or later and exits 1 with a message on older versions.

## Locations

The data home holds the config, the standards, the templates and the change folders. The CLI resolves it on every run, in this order:

1. `THEWAY_HOME`, when it is set and not empty.
2. The pointer file `${XDG_CONFIG_HOME:-~/.config}/theway/home`, when it exists and is not empty. Install writes it whenever the resulting home is not the default: one chosen with `--home` or the install question, one set by `THEWAY_HOME`, or the custom home an earlier pointer names on a reinstall.
3. `~/.theway`.

[`theway path --verbose`](#path) says which one it used.

Every subcommand that uses a project derives its key from the current directory (see [`project`](#project)); `--project <key>` replaces it. A project's files live in `<home>/projects/<key>/`.

[User standards](./concepts/standards.mdx) live in `<home>/standards/` (every project) and `<home>/projects/<key>/standards/` (one project). Install never touches them.

Other environment variables:

- `CLAUDE_CONFIG_DIR` replaces `~/.claude`.
- `THEWAY_INSTALL_DIR` replaces `~/.local/bin`, for install and uninstall.

## install

```bash
npx --yes @pixelfactoryio/theway@latest install
```

Copies the plugin to `~/.claude/skills/theway`, the CLI to `~/.local/bin/theway`, sets up the data home (`--home`, else `THEWAY_HOME`, else the home the pointer names, else `~/.theway`), writes or removes the pointer file and adds the two permission rules to `~/.claude/settings.json`, always dropping the `Edit` rule earlier versions added for the new and the previous home, and dropping the previous home's `Read` rule when the home changed. It stops and changes nothing when `~/.local/bin/theway` is another program, not a theway binary. It also stops and changes nothing when the data home is your home folder or one of its parents, or a custom home containing a glob character or a line break. It prints the `export PATH=…` line when the install folder is not on `PATH`, and warns when another `theway` comes first on `PATH`. Run it through `npx`, which carries the plugin files; the installed `theway install` exits 1 and prints the `npx` command. See [What install writes](./installation.mdx#what-install-writes).

On a first install from a terminal (stdin and stdout), it asks where to keep the data home, only when theway was never installed, then which opt-in standards to enable, only when the data home has no `config.yaml`. The options answer without a question:

- `--home <path>`: the data home, an absolute path or one starting with `~/`.
- `--standards <keys>`: the opt-in standards to enable in a new `config.yaml`, comma-separated (`core_principles`, `sre`, `web_development`, `quality`), or `none`.

It exits 1 and changes nothing when:

- `--home` is not an absolute path and does not start with `~/`: `theway: invalid --home '<value>': <reason>; nothing was changed`, with `<reason>` `must be an absolute path or start with ~/`, or `must not be empty` for a value of only spaces (an empty `--home ''` is refused by the argument parser);
- `--home` and a set `THEWAY_HOME` name different paths: `theway: --home <a> and THEWAY_HOME <b> differ; unset THEWAY_HOME or drop --home; nothing was changed`;
- `--standards` names an unknown key: `theway: unknown standard '<element>' in --standards; valid: core_principles, sre, web_development, quality, or none`;
- `--standards` combines `none` with a key: `theway: --standards none cannot be combined with other standards`;
- `--standards` is given and the data home already has a `config.yaml`: `theway: --standards applies only to a first install; <home>/config.yaml exists, so set standards.<key>.enabled there instead; nothing was changed`;
- you cancel a question: `theway: install cancelled; nothing was changed`.

With no terminal and no `--standards`, a first install leaves the opt-in standards off and prints the line that says how to enable one.

## uninstall

```bash
npx --yes @pixelfactoryio/theway@latest uninstall
```

Removes `~/.claude/skills/theway`, `~/.local/bin/theway` when it is a theway binary, the pointer file and the permission rules of `THEWAY_HOME`, of the home the pointer names and of `~/.theway`. The data home is kept.

## list

```bash
theway list
```

Prints a header line, `theway changes — <key>`, then the active changes of the project, each with its number of `.md` files and its ticked numbered tasks out of all numbered tasks, then the archived change folders and a summary line. Only numbered checkbox lines in `tasks.md` (`N.` or `Na.`) count as tasks. Used by [`/theway:list`](./commands/list.mdx) and [`/theway:archive`](./commands/archive.mdx).

A `--project` value must follow the rule of [`project`](#project), and a derived key must be at most 200 characters; otherwise it exits 1 with one line on stderr.

## archive

```bash
theway archive <change-id> [--force]
```

Moves `<home>/projects/<key>/changes/<change-id>` to `<home>/projects/<key>/changes/archive/YYYY-MM-DD-<change-id>`, with today's local date, and prints `Archived: <path>`.

It exits 1 and moves nothing when:

- the key is invalid (see [`project`](#project)) or `<change-id>` does not follow the rule of [`path`](#path);
- the change folder does not exist;
- the archive folder already exists;
- `tasks.md` has unticked numbered tasks. It prints each one with its line number.

`--force` archives despite unticked numbered tasks and prints them as a warning.

## path

```bash
theway path
theway path <change-id>
```

Prints one line on stdout:

- `theway path`: the data home, such as `/home/you/.theway`. It derives no key; a given `--project` is still validated.
- `theway path <change-id>`: `<home>/projects/<key>/changes/<change-id>`, whether or not the folder exists yet, such as `/home/you/.theway/projects/-home-you-code-my-api/changes/add-x` in `/home/you/code/my-api`. A single argument is always a change ID.

The slash commands run it to find the home (for the config, standards and templates) and the change folder they read and write.

`--verbose` adds one line on stderr naming where the home came from:

```text
theway: home /data/tw (from pointer)
```

The source is `env`, `pointer` or `default`. When `THEWAY_HOME` is set and differs from the pointer file, it prints the `THEWAY_HOME` value and one warning on stderr that names both values and their sources. Run install again with the new `THEWAY_HOME` to update the pointer.

A change id must be lowercase letters and digits in words separated by single hyphens (as `validate-id` produces), at most 200 characters. Any other value exits 1 with one reason on stderr:

```text
theway: invalid change id '..': must be lowercase letters and digits in words separated by single hyphens
```

The key is checked first, as [`project`](#project) says.

## project

```bash
theway project
theway project --project <key>
```

Prints the project key and the project folder, in `/home/you/code/my-api`:

```text
key: -home-you-code-my-api
dir: /home/you/.theway/projects/-home-you-code-my-api
```

The key is the project root's absolute path with every character outside `[A-Za-z0-9]` replaced by `-`, as Claude Code names its `~/.claude/projects/` folders. The project root is:

- in a git repository, any of its subfolders or a linked worktree: the main repository's root (git's common directory, `.git`, without its last segment), so every worktree shares one key;
- in a bare repository or one with a separate git dir: the worktree root (`git rev-parse --show-toplevel`), else the current directory;
- outside git, or without `git` on `PATH`: the current directory.

The root is resolved to its physical path (symlinks followed) before the key is built. A linked worktree of a `--separate-git-dir` repository and a submodule get their own worktree root, so they do not share the main repository's key. See [Project key](./concepts/changes.mdx#project-key).

`--project <key>` replaces the derived key; no git command runs. Every subcommand that uses a project takes it: `list`, `archive`, `path`, `project`, `config`, `standards`, `context`, `workflow`, `steps` and `next-id`. It exits 1 with one line on stderr when:

- the `--project` value is not letters, digits and `-`, 1 to 200 characters:

  ```text
  theway: invalid project 'a/b': must be letters, digits and "-", at most 200 characters
  ```

- the derived key is longer than 200 characters:

  ```text
  theway: project key for <root> is longer than 200 characters; pass --project <key>
  ```

Every subcommand checks the key first, then its other arguments; an empty `<change-id>` for `archive` and an invalid `--count` for `next-id` are refused by the argument parser before it.

## config

```bash
theway config
```

Prints the effective [configuration](./configuration.mdx) of the project as YAML on stdout: the defaults, then `<home>/config.yaml`, then `<home>/projects/<key>/config.yaml` when it exists, merged key by key (see [Layering](./configuration.mdx#layering)). It prints every key, sections in the order `standards`, `engineering`, `workflow`, without comments, and every value it prints is valid. `/theway:engineering`, with or without `--light`, takes its keys from the same config, through [`context`](#context), and [`workflow`](#workflow) takes `workflow.defaults` from it.

The `standards` section lists every switchable [standard](./concepts/standards.mdx#switching-a-standard) of the project, each as `<key>:` with its effective `enabled`: the four opt-in keys `core_principles`, `sre`, `web_development` and `quality` first, then the keys of the user standards of `<home>/standards/` and `<home>/projects/<key>/standards/`, sorted.

```text
standards:
  core_principles:
    enabled: false
  ...
workflow:
  defaults: {}
```

`workflow.defaults` is printed as the files merge it, per step and param, the project file over the global one, and `{}` when no file sets any. An entry that names no step is left out, with the `workflow.defaults.<step>` warning below.

An invalid value, an unknown key, a section that is not a map or a file whose root is not a map is ignored with a warning on stderr, the global file's first, and the exit code stays 0. `<file>` is the path relative to the home, `config.yaml` or `projects/<key>/config.yaml`:

```text
theway: warning: <file>: <key> must be <rule>; ignored
theway: warning: <file>: unknown key <key>; ignored
theway: warning: <file>: <key> must be a map; ignored
theway: warning: <file>: not a map; ignored
theway: warning: <file>: standards.<key> has no standard file; ignored
theway: warning: <file>: standards.<key> cannot be switched; ignored
theway: warning: <file>: workflow.defaults.<step>: no step '<step>' in <home>/projects/<key>/steps or <home>/steps; did you mean '<x>'?; ignored
```

The `standards` warnings name a `standards` key that no standard file of the project gives, and the key of a standard that cannot be switched: one that is always read (`interaction`, `develop`, `tamm_framework`, `spec_review`, `spec_investigation`), unless the project's `<home>/projects/<key>/standards/` holds a file with that name, or a convention standard (`commits`, `git_host`).

It exits 1 and prints nothing on stdout when:

- the key is invalid, with the line of [`project`](#project) on stderr;
- `<home>/config.yaml` is missing:

  ```text
  theway: config.yaml not found in <home>; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins
  ```

- either file exists but cannot be read:

  ```text
  theway: <file>: cannot be read
  ```

- either file is not valid YAML, duplicate keys included:

  ```text
  theway: <file>: invalid YAML: Map keys must be unique at line 3, column 3
  ```

## standards

```bash
theway standards engineering
theway standards develop
theway standards document
```

Prints the absolute path of every enabled [standard](./concepts/standards.mdx) that applies to the phase, one per line: the regular `.md` files directly in `<home>/standards/`, then directly in `<home>/projects/<key>/standards/`, each group sorted by name. Subfolders and other files are ignored. In `<home>/standards/`, `interaction.md`, `develop.md`, `tamm-framework.md`, `spec-review.md` and `spec-investigation.md` are never listed; `commits.md` and `git-host.md`, the [convention standards](./concepts/standards.mdx#convention-standards), are never listed from either folder; `core-principles.md`, `sre.md`, `web-development.md` and `quality.md` are the opt-in standards; the other files that `.shipped.json` lists as `standards/<name>`, and any `*.default.md` copy there, belong to theway and are not listed. A project file with the same name as a global one replaces it for the phases the project file applies to; for the other phases, the global file is printed as usual.

- A standard, opt-in or yours, applies to the phases its `applies_to` frontmatter lists (`engineering`, `develop` and/or `document`), or to all three without one.
- A standard is printed only when its effective `standards.<key>.enabled` is `true`: it computes the project's config as [`config`](#config) does, without printing its warnings. A missing `<home>/config.yaml` counts as empty, so the defaults apply: opt-in standards off, user standards on.

With nothing to print, it prints nothing and exits 0.

```text
/home/you/.theway/standards/tdd.md
/home/you/.theway/projects/-home-you-code-my-api/standards/review.md
```

An enabled file whose `applies_to` has any other value or form is skipped for every phase, with a warning on stderr; the exit code stays 0:

```text
theway: warning: <path>: applies_to must list engineering, develop and/or document; skipped
```

A file that cannot be read is skipped, with a warning on stderr; the others are still listed and the exit code stays 0:

```text
theway: warning: <path>: cannot be read; skipped
```

It exits 1 and prints nothing on stdout when:

- the key is invalid, with the line of [`project`](#project) on stderr;
- the phase is not `engineering`, `develop` or `document`:

  ```text
  theway: invalid phase '<value>': must be engineering, develop or document
  ```

- either `config.yaml` cannot be read or is not valid YAML, with the message of [`config`](#config).

The commands get the same list through [`context`](#context).

## context

```bash
theway context <engineering|develop|document>
theway context <engineering|develop|document> <change-id>
```

Prints what a command loads in its first step, as one YAML document with these keys, in this order:

- `home`: the data home, as [`path`](#path) prints it;
- `project`: the project key, as [`project`](#project) prints it;
- `project_dir`: the project folder, `<home>/projects/<key>`;
- `change_dir`: only with `<change-id>`, the folder `theway path <change-id>` prints;
- `standards`: the paths [`standards`](#standards) prints for the phase, as a list, `[]` when there are none;
- `config`: the effective config [`config`](#config) prints.

```text
home: /home/you/.theway
project: -home-you-code-my-api
project_dir: /home/you/.theway/projects/-home-you-code-my-api
change_dir: /home/you/.theway/projects/-home-you-code-my-api/changes/add-redis-cache
standards:
  - /home/you/.theway/standards/tdd.md
config:
  standards:
    ...
```

It writes the warnings of `config` to stderr once. It exits 1 and prints nothing on stdout when the key is invalid (see [`project`](#project)), when the phase is invalid (the message of [`standards`](#standards)), when `<change-id>` does not follow the rule of [`path`](#path), or when `<home>/config.yaml` is missing or a config file cannot be read or is not valid YAML (the messages of [`config`](#config)).

`/theway:engineering`, with or without `--light`, runs it with `engineering`, `/theway:document` with `document`, and `/theway:workflow` with `develop` and the change ID, taking `change_dir` as the change folder.

## workflow

```bash
theway workflow
theway workflow <name>
```

Resolves one [workflow](./concepts/workflows.mdx), its [steps](./concepts/workflows.mdx#step-files) and their prompts, applies each param (the workflow entry, else [`workflow.defaults`](./configuration.mdx#workflow), else the step file's default), expands every `foreach`, validates it all, and prints it as JSON on stdout. [`/theway:workflow`](./commands/workflow.mdx) runs it once per run and passes the result to its pipeline.

Which file:

- **With `<name>`:** `<home>/projects/<key>/workflows/<name>.yaml` when it is a file, else `<home>/workflows/<name>.yaml`.
- **Without `<name>`, the default:**
  1. The project's folder: every workflow file in it is validated, in file-name order, and the one that sets `default: true` is the default.
  2. Only when the project has none, the global folder: the same, over the global files that no project file of the same name shadows. A shadowed global file is not read.
  3. When neither has one, `develop` (the shipped one is a working-tree workflow), looked up as with `<name>`.
- A `<name>` matches `^[a-z0-9]+(-[a-z0-9]+)*$`; the workflow's name is its file stem. A `*.default.yaml` file is the shipped copy install writes next to an edited file, never a workflow. While it scans a folder for the default, a `.yaml` file whose stem is not a valid name is skipped with `theway: warning: <file>: not a valid workflow name; ignored`.
- Each step is `<home>/projects/<key>/steps/<name>.yaml` when it is a file, else `<home>/steps/<name>.yaml`; each prompt the same, under `prompts/` as `<name>.md`.

A named file whose `version` is `theway.workflow/v1beta` is read by the new language instead: one file, a flat list of steps, each naming a prompt (`uses`) and giving it values (`with`). `theway workflow <name>` checks it whole, prints every mistake as one line, `theway: <file>: <place>: <message>`, and exits 1, or prints its resolved document. `--input <name>=<value>`, repeatable, gives a workflow input its value: when every required input is given, the document says `"resolved": true` and every `${{ inputs.… }}` and `${{ matrix.… }}` reference is replaced in each run's prompt; without `--input`, a workflow that declares a required input keeps its workflow input references as written and says `"resolved": false`, while one with no required input resolves with each input's `default`, else the empty string. `--input` is refused for any other workflow, with `theway: --input needs a theway.workflow/v1beta workflow`, and so are an input the workflow does not declare, an invalid change ID for an input of `type: change`, and, once any `--input` is given, a required input that is not given or is given empty (`theway: --input <name>: required input is not given`). Without `<name>`, the default is chosen as above.

`theway workflow agents`, with the shipped `agents.yaml` (shortened):

```json
{
  "name": "agents",
  "description": "Implement, review and open the PR through agents",
  "file": "/home/you/.theway/workflows/agents.yaml",
  "input": "changes",
  "commits": "/home/you/.theway/standards/commits.md",
  "git_host": "/home/you/.theway/standards/git-host.md",
  "pushes": true,
  "working_tree": false,
  "steps": [
    {
      "id": "implement",
      "step": "implement",
      "agents": true,
      "file": "/home/you/.theway/steps/implement.yaml",
      "description": "Implement the change's tasks as its spec says",
      "params": { "model": { "value": "opus", "from": "steps/implement.yaml" } },
      "do": [
        {
          "agent": {
            "name": "implement",
            "label": "implement:implement",
            "prompt": ["/home/you/.theway/prompts/implement.md"],
            "returns": "work",
            "access": "commit",
            "model": "opus"
          }
        }
      ]
    },
    {
      "id": "review",
      "step": "review",
      "...": "...",
      "do": [
        {
          "loop": {
            "max": 1,
            "until": ["no-confirmed"],
            "exhausted": "continue",
            "do": [
              { "parallel": [ { "agent": { "name": "conformance", "label": "review:conformance", "...": "..." } }, "..." ] },
              { "when": ["findings"], "do": [ { "agent": { "name": "triage", "...": "..." } } ] },
              { "when": ["confirmed"], "do": [ "..." ] }
            ]
          }
        }
      ]
    },
    { "id": "pr", "step": "pr", "...": "..." }
  ]
}
```

- `commits` and `git_host` are the paths of the [convention standards](./concepts/standards.mdx#convention-standards): `<home>/projects/<key>/standards/commits.md` and `git-host.md` when they are files, else the global ones. The global files must exist, even when the project overrides them: checked after the workflow file is validated, a missing one exits 1 with `theway: <home>/standards/commits.md not found; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins` (or `git-host.md`).
- `input` is `changes` or `request` (see [Two kinds of workflow](./concepts/workflows.mdx#two-kinds-of-workflow)); an `input: request` workflow always prints `pushes: false` and `working_tree: false`.
- `pushes` is `true` when a step has an agent with `access: push`: it is what authorizes `/theway:workflow` to push and open the PR. `working_tree` is `true` for a workflow of one inline entry whose tree is one `work` agent with `access: commit`: it creates no branch and commits nothing.
- Each step entry has its `id` (`review`, `review-2` for a repeated one), `step`, `agents` (its own, else the top-level one, else `true`), `file`, `description`, `params` (each `value` and `from`: the workflow file and `steps[<i>]`, a config file, or the step file) and `do`. A gate entry is `{ "id": "gate", "gate": "<question>", "agents": false }`.
- In `do`, a sequential `foreach` is replaced by its copies and a parallel one becomes `{ "parallel": [ … ] }`; a `loop` prints `max`, `until`, `exhausted` and `do`; a `when` prints its conditions and `do`, `"fail": true`, or `"block"` (`true` or its message, a `${param}` already substituted). Every agent has `name`, `label`, `prompt` (absolute paths, read in order), `returns`, `access` and `model`; an inline step's agents have no `model`, and its params print none that sets one.
- The `version` key is not printed.

It writes the warnings of [`config`](#config) to stderr, and its own: a `workflow.defaults` value of another kind than its param, or for a param the step does not declare, a reserved `steps/gate.yaml`, and a loop with `exhausted: fail` whose fix is not guarded by `more`. Any error writes one line on stderr, prints nothing on stdout and exits 1: the messages of `config` for a missing or invalid config file, the lines of [`project`](#project) for the key, and these, where `<file>` is the path relative to the home:

```text
theway: invalid workflow name '<name>'
theway: no workflow '<name>' in <home>/projects/<key>/workflows or <home>/workflows
theway: workflows/a.yaml and workflows/b.yaml both set default: true
theway: workflows/w.yaml: version is required (theway.workflow/v1)
theway: workflows/w.yaml: steps[1]: no step 'reviews' in <home>/projects/<key>/steps or <home>/steps; did you mean 'review'?
theway: workflows/w.yaml: steps[0].implement.model has no effect when the step runs inline (agents: false)
theway: workflows/w.yaml: steps[1]: a pushing step must be the last step
theway: workflows/w.yaml: steps[0]: an input: request workflow starts with a step whose first agent returns scaffold
theway: workflows/w.yaml: steps[1]: do[0].agent: access commit is not allowed in an input: request workflow
theway: steps/review.yaml: do[0].loop.max must be a positive integer (value from workflows/w.yaml steps[1])
```

Only the first error is reported, in this order: the file cannot be read or is not valid YAML, its root is not a map, its `version` is missing or wrong, it has an unknown key, then the rest in document order, each step's own file included. [Workflows](./concepts/workflows.mdx#validation) describes every rule.

## steps

```bash
theway steps
theway steps <name>
```

- **Without `<name>`:** lists every step file of the project, the project's first and then the global ones no project file shadows, sorted by name, with its origin and description, then each param with its effective value (from `workflow.defaults`, else the step file) and description:

  ```text
  implement  global  Implement the change's tasks as its spec says
      model=opus  The implementer
  review  global  Review the diff through each lens, triage the findings, fix the confirmed ones and check the fixes
      rounds=1  Maximum review rounds
      lenses=conformance,correctness  One reviewer per lens, by prompt name
      model=opus  The reviewers, the triage and the fix check
      fix_model=opus  The fix agent of each round
  ```

  It reads only each file's `version`, `description` and `params`: a file it cannot read, or whose `version` or those keys are invalid, is skipped with a warning.
- **With `<name>`:** validates that step as `theway workflow` does and prints its step object as JSON, with `"id": "<name>"`, `"agents": true` and its params from `workflow.defaults` and the step file. An unknown step exits 1 with `theway: no step '<name>' in <home>/projects/<key>/steps or <home>/steps`, followed by a did-you-mean suggestion or the valid set, for example `(steps: implement, pr, review)`; an invalid step file exits 1 with its error line.

## authority

```bash
theway authority
```

Prints the `## Authority` section of `<home>/standards/interaction.md`: from its heading up to the next `## ` heading or the end of the file, without trailing blank lines. When that file is missing or has no such section (an edited copy that install kept), it prints the section of `<home>/standards/interaction.default.md`. When neither has it, it exits 1:

```text
theway: no ## Authority section in <home>/standards/interaction.md or interaction.default.md; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins
```

The commands that spawn agents quote its output verbatim in every agent prompt.

## validate-id

```bash
theway validate-id <id>
theway validate-id <id> --series
```

Checks a [change ID](./concepts/changes.mdx#change-ids). It exits 0 when the ID is valid. Otherwise it exits 1 and prints one line on stderr:

```text
invalid change id '<id>': <reason>
```

Every ID must be lowercase kebab-case (`[a-z0-9]` segments joined by single hyphens) and start with `add-`, `update-`, `refactor-`, `remove-` or `fix-`. An ID with uppercase letters is rejected with `uppercase letters are not allowed; use lowercase kebab-case`, one with underscores with `underscores are not allowed; use kebab-case (-)`; any other start is rejected with:

```text
invalid change id '<id>': must start with a verb prefix: add-, update-, refactor-, remove- or fix-
```

- **Without `--series`** (a standalone change): the ID must not end in a one- or two-digit number.
- **With `--series`** (a series member): the ID must end in a two-digit ordinal from `01`, such as `add-user-auth-01`. Letter suffixes, `-00` and double ordinals are rejected.

`/theway:engineering`, with or without `--light`, runs it before it writes a standalone change folder; [`next-id`](#next-id) validates the members of a series.

## next-id

```bash
theway next-id <series-id>
theway next-id <series-id> --count <n>
```

Prints the next `<n>` free member IDs of a [series](./concepts/changes.mdx#series), one per line (`--count` defaults to 1):

```text
add-user-auth-04
add-user-auth-05
```

- A trailing `-NN` is removed from `<series-id>` first, so `add-user-auth-07` gives the same IDs as `add-user-auth`. The rest must fit the [`validate-id`](#validate-id) format and must not end in a one- or two-digit number; when it is invalid, it exits 1 with an `invalid change id '<id>': <reason>` line, `<id>` being the series ID without its ordinal, for example:

  ```text
  invalid change id 'add-thing-01': ends in a number (-01); a series id cannot end in a number
  ```

- It counts the folders `<home>/projects/<key>/changes/<series-id>-NN` and the archived `<home>/projects/<key>/changes/archive/YYYY-MM-DD-<series-id>-NN`, and continues after the highest `NN`, or from `01` when there is none.
- A `--count` that is not a positive integer is rejected with `error: option '--count <n>' argument '<value>' is invalid. must be a positive integer`. When the last ID would be past `-99`, it exits 1:

  ```text
  theway: series <series-id> would go past -99
  ```

`/theway:engineering` runs it to name the members of a new series.

## dashboard

```text
theway dashboard [--port <n>]
```

Starts a local web view of the data home with two pages, Changes and Workflows. It prints one line with the address and runs until you stop it:

```text
theway dashboard: http://127.0.0.1:4870/
```

- It listens on `127.0.0.1` only, on port 4870 unless `--port` gives another. `--port 0` lets the system choose a free port, and the line shows the one bound.
- It reads the files on every request: coming back to the browser tab shows the files as they are now.
- It answers `403` to any request whose `Host` header is not `127.0.0.1:<port>` or `localhost:<port>`, so a web page cannot reach it through another host name. Its pages load no external script, style or font.
- A `--port` that is not an integer from 0 to 65535 is rejected with `error: option '--port <n>' argument '<value>' is invalid. must be an integer from 0 to 65535`. When the port is taken, it exits 1:

  ```text
  theway: port 4870 is in use; pass --port <n>
  ```

  Any other error starting the server exits 1 with a `theway: <message>` line. Ctrl-C (SIGINT) or SIGTERM stops it with exit 0.

### Changes

The Changes page, at `#/changes`, lists the active changes of every project on one page, one section per project. A series is one row with its progress, `<done> of <total> done`, counting its archived members and its active members whose tasks are all done; select it to show its active members. Every other change is a row with its tasks done. Archived adds each project's archived changes, and the project menu shows one project.

A change's page shows its tasks done, its PR link from the `**PR:**` line of its `tasks.md`, and, for a series member, every member of the series by ordinal, each linked to its page. Its `spec.md`, `tasks.md` and other Markdown files are rendered, one tab each.

### Workflows

The Workflows page, at `#/workflows`, lists the files where they live: the global files of `<home>/workflows/` and `<home>/prompts/`, then each project's own, marked `<project> only`. The list has three groups, each with its number of files: Workflows, Prompts (the prompt files a step can run: a header that passes the header rules) and Reference files (every other prompt file). The default workflow is marked `default`, and a workflow that does not resolve is marked `error`.

- A workflow's page draws its steps in order, as `theway workflow <name>` resolves them with no input: one numbered card per step with the prompt it runs (a link to its page), its model, or "your session" for a step that runs in your session, its matrix (`N copies at once` and each value), its on fail (the prompt it runs, then the step again, up to its tries) and its other inputs as written. Under the steps, one line says what every step answers: `pass`, `fail` or `blocked`; a fail with no on fail, and any blocked, stops the run. A workflow that does not resolve shows its error lines, each one that names a step under that step. The right column gives where it runs, its inputs and the file's path.
- A prompt's page shows "step prompt" for a step prompt and the model its header sets, its header errors when a step or an on fail uses it, its inputs (each required, or optional with its default), and its instructions, rendered. The right column gives the workflows that use it, with the step that does and how (`step N`, `on fail of step N`, `value in step N`), and the file's path.
- YAML, or Markdown for a prompt, shows the file's text.

### Editing a file

Edit, on a file's title row, opens it in edit mode at its page with `/edit`: the title row marks it `editing`, the centre shows the file as written, and the right column holds the settings.

- A workflow's steps are a timeline of cards, each with its prompt, `N copies at once` for a matrix, its on fail and tries, and its model or "your session". Drag a card by its handle to move the step. The `+` on the line between two cards, shown when you point at it, and the `+` after the last card open a menu of the step prompts the workflow can name (for a project workflow, the project's own, then the global ones it does not have); a new step writes each required input of its prompt as `""`, which the check reports until you set it.
- With no step selected, the right column holds the workflow's description, `default` and runs on, and its inputs: Add declares an optional input `input` (then `input2`, …) with the description "Describe this input.", to rename and rewrite. Select a step to remove it, move it up or down, change its prompt (the inputs the new prompt does not declare are dropped), set the inputs its prompt declares (the `{ }` menu inserts `${{ inputs.<name> }}`, or `${{ matrix.<key> }}` for a step with a matrix), its matrix (a key and one value per line), its on fail (a prompt, its inputs, its model, and tries) and its runs on and model. Turning on fail on writes `tries: 1` and the first step prompt by name that needs no input; turning it off removes both.
- A prompt's body is one text area; the right column holds its header's description, model and inputs. A file with no header, a reference file, has "Use as a step", which adds a header with an empty description to fill in.
- Ctrl or Cmd and Z undoes an edit, with Shift it redoes it.
- Your edits are kept while you move between pages, and the file list marks an edited file `edited`; they are lost on reload, which the browser asks you to confirm. A file with edits always opens in edit mode, and Close leaves edit mode while there is none.

New workflow and New prompt, above the list, open the New dialog: the kind, a name, a description, what to start from and where the file goes (all projects, or one project). Empty starts a workflow with `runs-on: agents` and one step on `prompts/implement.md` (or the first step prompt by name when there is no such prompt), and a prompt with `model: opus` and a one-line body; A copy of a file keeps its text and sets the description. The new file opens in edit mode and nothing is written until you save it. A project file may take the name of a global one: it then replaces it for that project.

The bar at the bottom counts your edits, gives the check's result and what a save reaches (for a prompt, the workflows that use it), and holds Diff, which shows the diff of your edits, Discard and Save. Each edit is checked 400 ms after you stop: the resolver of `theway workflow` runs over the edited text without writing it, in every context that reads the file. A project file is checked in its project; a global file is checked on its own and in every project that has no file of its name, and a line from a project is prefixed with its label. A prompt is checked through every workflow that names it. Each error line that names a step outlines its card, and selecting the line selects the card. Only the open file's edits are checked: a workflow that needs an unsaved prompt reports an error until that prompt is saved.

Save is enabled when the check passes, and writes that one file where it lives: `<home>/<kind>/<name><ext>` for a global file, `<home>/projects/<key>/<kind>/<name><ext>` for a project's. Discard drops your edits after a confirm. The server checks the text again before writing and refuses it with the error lines (`422`). A file already holding the text is not written.

Each workflow edit goes through the YAML document of the file, so the text of every comment is kept; a comment's place may change. A header edit leaves the body byte for byte, and a body edit the header.

The write requests need an `Origin` of `http://127.0.0.1:<port>` or `http://localhost:<port>` and an `X-Theway-Token` header holding a random token the server makes when it starts and puts in its page; any other request gets `403`.

When the file changed on disk since you opened it, Save gets `409` and writes nothing: the bar says "Changed on disk since you opened it.", and Reload drops your edits and loads the file as it is now.

### Versions

Before a save from the dashboard replaces a file, the text it held is kept as a version: under `<home>/history/global/<kind>/<name>/` for a global file, `<home>/history/projects/<key>/<kind>/<name>/` for a project's. A file keeps its 20 newest versions; a new file has none until its first save replaces it. Only dashboard saves are recorded: a file you change by hand, through an agent or with `theway install` gets no version, though the next dashboard save keeps whatever was on disk. Nothing else reads `<home>/history/`, so deleting it is safe and only drops the versions.

Versions, on a file's title row, lists them in the right column at its page with `/versions`: Current, then each version by its date and time, newest first, then As shipped for a global file that theway shipped and you edited, when the home holds its shipped text (`<name>.default.yaml` or `<name>.default.md`). Select a version to draw it as the file's page draws it, with the diff from it to the current file.

Restore puts the version's text, byte for byte, in the editor as your edits, after a confirm when the file already has edits; it is disabled when the version holds the current text. Nothing is written until you save it, through the same check as any edit, and that save keeps the replaced text as a version in turn.
