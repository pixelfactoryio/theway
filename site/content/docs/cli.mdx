The `theway` program has sixteen subcommands: `install`, `uninstall`, `list`, `archive`, `change`, `task done`, `path`, `project`, `config`, `standards`, `context`, `workflow`, `dashboard`, `authority`, `validate-id` and `next-id`. Install writes it to `~/.local/bin/theway` (or `$THEWAY_INSTALL_DIR/theway`), and the slash commands call it as plain `theway`, so its folder must be on your `PATH`. See [Installation](./installation.mdx#requirements).

```text
theway --version
theway install [--home <path>] [--standards <keys>]
theway uninstall
theway list [--project <key>]
theway archive <change-id> [--force] [--project <key>]
theway change <change-id> [--project <key>]
theway task done <change-id> <n>... [--project <key>]
theway path [<change-id>] [--verbose] [--project <key>]
theway project [--project <key>]
theway config [--project <key>]
theway standards <engineering|develop|document> [--project <key>]
theway context <engineering|develop|document> [<change-id>] [--project <key>]
theway workflow [<name>] [--input <name>=<value>]... [--compact] [--project <key>]
theway dashboard [--port <n>]
theway authority
theway validate-id <id> [--series]
theway next-id <series-id> [--count <n>] [--project <key>]
```

It needs Node.js 22.13 or later and exits 1 with a message on older versions. `theway --version` (or `-V`) prints its version.

## Locations

The data home holds the config, the standards, the templates and the change folders. The CLI resolves it on every run, in this order:

1. `THEWAY_HOME`, when it is set and not empty.
2. The pointer file `${XDG_CONFIG_HOME:-~/.config}/theway/home`, when it exists and is not empty. Install writes it whenever the resulting home is not the default: one chosen with `--home` or the install question, one set by `THEWAY_HOME`, or the custom home an earlier pointer names on a reinstall.
3. `~/.theway`.

[`theway path --verbose`](#path) says which one it used.

Every subcommand that uses a project derives its key from the current directory (see [`project`](#project)); `--project <key>` replaces it. A project's files live in `<home>/projects/<key>/`.

[User standards](./concepts/standards.mdx) live in `<home>/standards/` (every project) and `<home>/projects/<key>/standards/` (one project). Install never touches them.

Other environment variables:

- `CLAUDE_CONFIG_DIR` replaces `~/.claude`.
- `THEWAY_INSTALL_DIR` replaces `~/.local/bin`, for install and uninstall.

## install

```bash
npx --yes @pixelfactoryio/theway@latest install
```

Copies the plugin to `~/.claude/skills/theway`, the CLI to `~/.local/bin/theway` (and `theway.cmd` beside it on Windows), sets up the data home (`--home`, else `THEWAY_HOME`, else the home the pointer names, else `~/.theway`), writes or removes the pointer file and adds the two permission rules to `~/.claude/settings.json`, always dropping the `Edit` rule earlier versions added for the new and the previous home, and dropping the previous home's `Read` rule when the home changed. It stops and changes nothing when `~/.local/bin/theway` is another program, not a theway binary. It also stops and changes nothing when the data home is your home folder or one of its parents, or a custom home containing a glob character or a line break, or, on Windows, a home not on a drive letter. It prints the `export PATH=…` line (a PowerShell `$env:Path = …` line on Windows) when the install folder is not on `PATH`, and warns when another `theway` comes first on `PATH`. Run it through `npx`, which carries the plugin files; the installed `theway install` exits 1 and prints the `npx` command. See [What install writes](./installation.mdx#what-install-writes).

On a first install from a terminal (stdin and stdout), it asks where to keep the data home, only when theway was never installed, then which opt-in standards to enable, only when the data home has no `config.yaml`. The options answer without a question:

- `--home <path>`: the data home, an absolute path or one starting with `~/` (or `~\` on Windows).
- `--standards <keys>`: the opt-in standards to enable in a new `config.yaml`, comma-separated (`core_principles`, `sre`, `web_development`, `quality`), or `none`.

It exits 1 and changes nothing when:

- `--home` is not an absolute path and does not start with `~/`: `theway: invalid --home '<value>': <reason>; nothing was changed`, with `<reason>` `must be an absolute path or start with ~/`, or `must not be empty` for a value of only spaces (an empty `--home ''` is refused by the argument parser);
- `--home` and a set `THEWAY_HOME` name different paths: `theway: --home <a> and THEWAY_HOME <b> differ; unset THEWAY_HOME or drop --home; nothing was changed`;
- `--standards` names an unknown key: `theway: unknown standard '<element>' in --standards; valid: core_principles, sre, web_development, quality, or none`;
- `--standards` combines `none` with a key: `theway: --standards none cannot be combined with other standards`;
- `--standards` is given and the data home already has a `config.yaml`: `theway: --standards applies only to a first install; <home>/config.yaml exists, so set standards.<key>.enabled there instead; nothing was changed`;
- you cancel a question: `theway: install cancelled; nothing was changed`;
- `~/.claude/settings.json` is a symlink loop or its folder is not writable: `theway: cannot write <path>: <reason>; nothing was changed`;
- `~/.claude/settings.json` cannot be read: `theway: cannot read <path>: <reason>; nothing was changed`;
- `~/.claude/settings.json` is not valid settings JSON: `theway: <path> is not valid settings JSON; nothing was changed`;
- a target it writes into is not writable: `~/.claude`, `~/.claude/skills`, `~/.claude/skills/theway` and every folder below it, the install folder, the data home with its folders and `config.default.yaml`, the `bin/` folders of the 0.2.0 launcher, the pointer file and its folder, or for a target that does not exist yet the nearest existing folder above it: `theway: cannot write <path>: <reason>; nothing was changed`.

Install checks all of this before its first write. A failure while it writes (a full disk, a file where the data home needs a folder) stops it without undoing anything, with one line that names what it already wrote:

```text
theway: install stopped: <reason>; already written: the plugin in <path>, the theway binary at <path>
```

It ends with `; nothing was written` when it wrote nothing, and with `; the previous plugin is in <path>` when the previous plugin folder was moved aside and not removed. When the data home is the step that failed, its own `theway: <message>` line comes first and `<reason>` is `the data home could not be written`.

With no terminal and no `--standards`, a first install leaves the opt-in standards off and prints the line that says how to enable one.

## uninstall

```bash
npx --yes @pixelfactoryio/theway@latest uninstall
```

On Windows, run uninstall through `npx`, not the installed `theway.cmd`: see [Uninstall](./installation.mdx#uninstall).

Removes `~/.claude/skills/theway`, `~/.local/bin/theway` when it is a theway binary (and `theway.cmd` on Windows, each when it is theway's), the pointer file and the permission rules of `THEWAY_HOME`, of the home the pointer names and of `~/.theway`. The data home is kept.

Before it removes anything, it checks `~/.claude/settings.json` and that it can write the folders it removes from. It exits 1 and changes nothing when the settings file is not writable (`theway: cannot write <path>: <reason>; nothing was changed`), cannot be read (`theway: cannot read <path>: <reason>; nothing was changed`) or is not valid settings JSON (`theway: <path> is not valid settings JSON; nothing was changed`), and when `~/.claude/skills`, the plugin folder or a folder below it, the binary folder or the pointer folder is not writable (`theway: cannot write <path>: <reason>; nothing was changed`). A failure while it removes stops it without restoring anything, with one line that names what it already removed:

```text
theway: uninstall stopped: <reason>; already removed: the plugin in <path>, the theway binary at <path>
```

It ends with `; nothing was removed` when it removed nothing.

## list

```bash
theway list
```

Prints a header line, `theway changes — <key>`, then the active changes of the project, then the archived change folders and a summary line. An active change is one line, `  <change-id> <files> files   <done>/<total> tasks done`, the ID padded to 20 characters: `<files>` counts every regular, non-hidden file directly in the change folder, and the tasks are those of its [`change.yaml`](#change). A change whose `change.yaml` is missing or invalid shows its first error in place of the count: `invalid: not found`, `invalid: version: must be theway.change/v1beta1`. Used by [`/theway:list`](./commands/list.mdx) and [`/theway:archive`](./commands/archive.mdx).

A `--project` value must follow the rule of [`project`](#project), and a derived key must be at most 200 characters; otherwise it exits 1 with one line on stderr.

## archive

```bash
theway archive <change-id> [--force]
```

Moves `<home>/projects/<key>/changes/<change-id>` to `<home>/projects/<key>/changes/archive/YYYY-MM-DD-<change-id>`, with today's local date, and prints `Archived: <path>`.

It exits 1 and moves nothing when:

- the key is invalid (see [`project`](#project)) or `<change-id>` does not follow the rule of [`path`](#path);
- the change folder does not exist;
- the archive folder already exists;
- its `change.yaml` is invalid:

  ```text
  theway: <change-id> has an invalid change.yaml — not archiving.
  changes/<change-id>/change.yaml: <where>: <message>
  Fix it, or re-run with --force.
  ```

- a task of its `change.yaml` is open. It prints each one with its number and the first line of its text:

  ```text
  theway: <change-id> has open tasks — not archiving.
  2. Answer 429 with a `Retry-After` header when the bucket is empty
  Tick them with theway task done, or re-run with --force.
  ```

`--force` archives anyway and prints `theway: warning: archiving with an invalid change.yaml (--force)`, or `theway: warning: archiving with open tasks (--force):` followed by the open tasks.

## change

```bash
theway change <change-id>
```

Validates `<home>/projects/<key>/changes/<change-id>/change.yaml`, the file that holds a change's description and its tasks:

```yaml
version: theway.change/v1beta1
description: Limit requests per API key with a token bucket
tasks:
  - text: Add a token bucket per API key, kept in memory
    done: true
  - text: Answer 429 with a `Retry-After` header when the bucket is empty
  - text: Read the limit and the burst from the settings
```

| Where | Rule | Message |
|---|---|---|
| file | exists and is a YAML map | `not found` · `invalid YAML: <reason>` · `must be a map` |
| any node | no anchor (`&name`) and no alias (`*name`) | `anchors and aliases are not allowed` |
| `version` | required, exactly `theway.change/v1beta1` | `must be theway.change/v1beta1` |
| `description` | required, a non-empty string on one line | `must be a non-empty string on one line` |
| `tasks` | required, a list with at least one item | `must be a list with at least one task` |
| `tasks[i]` | a map | `must be a map` |
| `tasks[i].text` | required, a non-empty string | `must be a non-empty string` |
| `tasks[i].done` | optional, `true` or `false`; absent means `false` | `must be true or false` |
| any other key | at the root or in a task | `unknown key` |

A task's number is its position in the list, counted from 1; `tasks[i]` in an error is counted from 0. A missing required key is reported as `<key>: is required`. Every error is reported, in the file's key order, then the missing keys.

Anchors and aliases are checked first: each one gives its own line, in document order, and no other rule is checked. The line's `<where>` is the path of the node in the table above, never deeper: a map key takes the path of the map that holds it, and a node below a root key's value or below `tasks[i].<key>` the path of its nearest ancestor the table names (`description: [&a x]` gives `description`, `tasks[0].text: {k: &a v}` gives `tasks[0].text`). An anchor on the file's root map has no `<where>`: the line is `anchors and aliases are not allowed`.

When the file is valid, it prints the change as JSON on stdout and exits 0:

```json
{
  "id": "<change-id>",
  "dir": "<change folder>",
  "description": "…",
  "tasks": [
    {
      "n": 1,
      "text": "…",
      "done": true
    }
  ]
}
```

When it is not, it prints each error on stderr and exits 1, with nothing on stdout:

```text
theway: changes/<change-id>/change.yaml: not found
theway: changes/<change-id>/change.yaml: tasks[1].done: must be true or false
```

The scaffold and `fix-spec` run it after writing a `change.yaml`, and fix the file until it exits 0. The key and the change ID follow the rules of [`archive`](#archive).

## task done

```bash
theway task done <change-id> <n>...
```

Ticks the tasks numbered `<n>` of the change's `change.yaml`: it loads the file, sets `done: true` on each named task and prints the file again. Values, comments, line endings and the file's mode are kept. On other lines the layout may change, the values staying the same: a `>-` text is written on one line, several spaces before a trailing comment become one, indentation becomes two spaces, a final line break is added, and a flow list written over several lines is laid out again. A task already done stays done. It prints `<done>/<total> tasks done` and exits 0.

It exits 1 and writes nothing when the file is invalid (with the error lines of [`change`](#change)), or with one line per bad argument, in the order given, when an argument is not a task number (digits not starting with `0`) or is greater than the number of tasks:

```text
theway: changes/<change-id>/change.yaml: task 01: not a task number
theway: changes/<change-id>/change.yaml: task 9: no such task (1 to 3)
```

When the file or its folder cannot be written, it exits 1 with one line, the file left as it was:

```text
theway: changes/<change-id>/change.yaml: cannot write: EACCES: permission denied, access '<path>'
```

The implementer runs it when a task is finished. To undo a tick, edit `change.yaml`. `theway task` alone prints its help.

## path

```bash
theway path
theway path <change-id>
```

Prints one line on stdout:

- `theway path`: the data home, such as `/home/you/.theway`. It derives no key; a given `--project` is still validated.
- `theway path <change-id>`: `<home>/projects/<key>/changes/<change-id>`, whether or not the folder exists yet, such as `/home/you/.theway/projects/-home-you-code-my-api/changes/add-x` in `/home/you/code/my-api`. A single argument is always a change ID.

The slash commands run it to find the home (for the config, standards and templates) and the change folder they read and write.

`--verbose` adds one line on stderr naming where the home came from:

```text
theway: home /data/tw (from pointer)
```

The source is `env`, `pointer` or `default`. When `THEWAY_HOME` is set and differs from the pointer file, it prints the `THEWAY_HOME` value and one warning on stderr that names both values and their sources. Run install again with the new `THEWAY_HOME` to update the pointer.

A change id must be lowercase letters and digits in words separated by single hyphens (as `validate-id` produces), at most 200 characters. Any other value exits 1 with one reason on stderr:

```text
theway: invalid change id '..': must be lowercase letters and digits in words separated by single hyphens
```

The key is checked first, as [`project`](#project) says.

## project

```bash
theway project
theway project --project <key>
```

Prints the project key and the project folder, in `/home/you/code/my-api`:

```text
key: -home-you-code-my-api
dir: /home/you/.theway/projects/-home-you-code-my-api
```

The key is the project root's absolute path with every character outside `[A-Za-z0-9]` replaced by `-`, as Claude Code names its `~/.claude/projects/` folders. The project root is:

- in a git repository, any of its subfolders or a linked worktree: the main repository's root (git's common directory, `.git`, without its last segment), so every worktree shares one key;
- in a bare repository or one with a separate git dir: the worktree root (`git rev-parse --show-toplevel`), else the current directory;
- outside git, or without `git` on `PATH`: the current directory.

The root is resolved to its physical path (symlinks followed) before the key is built. A linked worktree of a `--separate-git-dir` repository and a submodule get their own worktree root, so they do not share the main repository's key. See [Project key](./concepts/changes.mdx#project-key).

`--project <key>` replaces the derived key; no git command runs. Every subcommand that uses a project takes it: `list`, `archive`, `change`, `task done`, `path`, `project`, `config`, `standards`, `context`, `workflow` and `next-id`. It exits 1 with one line on stderr when:

- the `--project` value is not letters, digits and `-`, 1 to 200 characters:

  ```text
  theway: invalid project 'a/b': must be letters, digits and "-", at most 200 characters
  ```

- the derived key is longer than 200 characters:

  ```text
  theway: project key for <root> is longer than 200 characters; pass --project <key>
  ```

- the derived key's folder is claimed by another root, recorded in its `root` file:

  ```text
  theway: project key <key> is used by <recorded root>; pass --project <key> to use another key for <root>
  ```

A derived key whose folder exists and has no `root` file claims it: the command writes the root's physical path to `<home>/projects/<key>/root`. When that write fails, the command goes on and writes `theway: warning: cannot record <dir>/root: <message>` to stderr. With no project folder, nothing is written. `--project` never reads or writes the `root` file. See [Project key](./concepts/changes.mdx#project-key).

Every subcommand checks the key first, then its other arguments; an empty `<change-id>` for `archive` and an invalid `--count` for `next-id` are refused by the argument parser before it.

## config

```bash
theway config
```

Prints the effective [configuration](./configuration.mdx) of the project as YAML on stdout: the defaults, then `<home>/config.yaml`, then `<home>/projects/<key>/config.yaml` when it exists, merged key by key (see [Layering](./configuration.mdx#layering)). It prints every key, without comments, and every value it prints is valid. `/theway:engineering`, with or without `--light`, takes its keys from the same config, through [`context`](#context).

The `standards` section lists every switchable [standard](./concepts/standards.mdx#switching-a-standard) of the project, each as `<key>:` with its effective `enabled`: the four opt-in keys `core_principles`, `sre`, `web_development` and `quality` first, then the keys of the user standards of `<home>/standards/` and `<home>/projects/<key>/standards/`, sorted.

```text
standards:
  core_principles:
    enabled: false
  ...
```

An invalid value, an unknown key, a section that is not a map or a file whose root is not a map is ignored with a warning on stderr, the global file's first, and the exit code stays 0. `<file>` is the path relative to the home, `config.yaml` or `projects/<key>/config.yaml`:

```text
theway: warning: <file>: <key> must be <rule>; ignored
theway: warning: <file>: unknown key <key>; ignored
theway: warning: <file>: <key> must be a map; ignored
theway: warning: <file>: not a map; ignored
theway: warning: <file>: standards.<key> has no standard file; ignored
theway: warning: <file>: standards.<key> cannot be switched; ignored
```

A `workflow` key, which earlier versions read for `workflow.defaults`, is an unknown key now: `theway: warning: config.yaml: unknown key workflow; ignored`. Set the value in the workflow file or in the prompt's header, and remove the key.

The `standards` warnings name a `standards` key that no standard file of the project gives, and the key of a standard that cannot be switched: one that is always read (`interaction`, `develop`, `authority`, `tamm_framework`, `spec_review`, `spec_investigation`), unless the project's `<home>/projects/<key>/standards/` holds a file with that name (or, for `authority`, unless the global `authority.md` is one `.shipped.json` does not list, which makes it a user standard), or a convention standard (`commits`, `git_host`).

It exits 1 and prints nothing on stdout when:

- the key is invalid, with the line of [`project`](#project) on stderr;
- `<home>/config.yaml` is missing:

  ```text
  theway: config.yaml not found in <home>; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins
  ```

- either file exists but cannot be read:

  ```text
  theway: <file>: cannot be read
  ```

- either file is not valid YAML, duplicate keys included:

  ```text
  theway: <file>: invalid YAML: Map keys must be unique at line 3, column 3
  ```

## standards

```bash
theway standards engineering
theway standards develop
theway standards document
```

Prints the absolute path of every enabled [standard](./concepts/standards.mdx) that applies to the phase, one per line: the regular `.md` files directly in `<home>/standards/`, then directly in `<home>/projects/<key>/standards/`, each group sorted by name. Subfolders and other files are ignored. In `<home>/standards/`, `interaction.md`, `develop.md`, `tamm-framework.md`, `spec-review.md` and `spec-investigation.md` are never listed, nor `authority.md` when `.shipped.json` lists `standards/authority.md` (one it does not list is your own standard, key `authority`, listed and switched like any other); `commits.md` and `git-host.md`, the [convention standards](./concepts/standards.mdx#convention-standards), are never listed from either folder; `core-principles.md`, `sre.md`, `web-development.md` and `quality.md` are the opt-in standards; the other files that `.shipped.json` lists as `standards/<name>`, and any `*.default.md` copy there, belong to theway and are not listed. A project file with the same name as a global one replaces it for the phases the project file applies to; for the other phases, the global file is printed as usual.

- A standard, opt-in or yours, applies to the phases its `applies_to` frontmatter lists (`engineering`, `develop` and/or `document`), or to all three without one.
- A standard is printed only when its effective `standards.<key>.enabled` is `true`: it computes the project's config as [`config`](#config) does, without printing its warnings. A missing `<home>/config.yaml` counts as empty, so the defaults apply: opt-in standards off, user standards on.

With nothing to print, it prints nothing and exits 0.

```text
/home/you/.theway/standards/tdd.md
/home/you/.theway/projects/-home-you-code-my-api/standards/review.md
```

An enabled file whose `applies_to` has any other value or form is skipped for every phase, with a warning on stderr; the exit code stays 0:

```text
theway: warning: <path>: applies_to must list engineering, develop and/or document; skipped
```

A file that cannot be read is skipped, with a warning on stderr; the others are still listed and the exit code stays 0:

```text
theway: warning: <path>: cannot be read; skipped
```

It exits 1 and prints nothing on stdout when:

- the key is invalid, with the line of [`project`](#project) on stderr;
- the phase is not `engineering`, `develop` or `document`:

  ```text
  theway: invalid phase '<value>': must be engineering, develop or document
  ```

- either `config.yaml` cannot be read or is not valid YAML, with the message of [`config`](#config).

The commands get the same list through [`context`](#context).

## context

```bash
theway context <engineering|develop|document>
theway context <engineering|develop|document> <change-id>
```

Prints what a command loads in its first step, as one YAML document with these keys, in this order:

- `home`: the data home, as [`path`](#path) prints it;
- `project`: the project key, as [`project`](#project) prints it;
- `project_dir`: the project folder, `<home>/projects/<key>`;
- `change_dir`: only with `<change-id>`, the folder `theway path <change-id>` prints;
- `standards`: the paths [`standards`](#standards) prints for the phase, as a list, `[]` when there are none;
- `config`: the effective config [`config`](#config) prints.

```text
home: /home/you/.theway
project: -home-you-code-my-api
project_dir: /home/you/.theway/projects/-home-you-code-my-api
change_dir: /home/you/.theway/projects/-home-you-code-my-api/changes/add-redis-cache
standards:
  - /home/you/.theway/standards/tdd.md
config:
  standards:
    ...
```

It writes the warnings of `config` to stderr once. It exits 1 and prints nothing on stdout when the key is invalid (see [`project`](#project)), when the phase is invalid (the message of [`standards`](#standards)), when `<change-id>` does not follow the rule of [`path`](#path), or when `<home>/config.yaml` is missing or a config file cannot be read or is not valid YAML (the messages of [`config`](#config)).

`/theway:document` runs it with `document`. The shipped prompts run it too: `prompts/change.md` with `develop` and the change ID, taking `change_dir` as the change folder, and `prompts/spec-review.md` with `engineering`.

## workflow

```bash
theway workflow
theway workflow <name>
theway workflow <name> --input <name>=<value> [--input <name>=<value>]...
theway workflow <name> --input <name>=<value> --compact
```

Reads one [workflow](./concepts/workflows.mdx) and every prompt its steps use, checks them, and prints the resolved document as JSON on stdout. [`/theway:workflow`](./commands/workflow.mdx) runs it first to read the workflow's inputs, then with `--input` and `--compact` to get the document it runs.

Which file:

- **With `<name>`:** `<home>/projects/<key>/workflows/<name>.yaml` when it is a file, else `<home>/workflows/<name>.yaml`. A `<name>` matches `^[a-z0-9]+(-[a-z0-9]+)*$`; the workflow's name is its file stem.
- **Without `<name>`:** the one workflow that sets `default: true`, among the project's workflow files and the global ones no project file of the same name hides. The shipped `develop` sets it. When none sets it, it exits 1 with `theway: no workflow sets default: true`; when several do, with a line naming them, for example `theway: workflows/agents.yaml and workflows/develop.yaml both set default: true`.
- Each prompt a step names, `prompts/<name>.md`, is `<home>/projects/<key>/prompts/<name>.md` when it is a file, else `<home>/prompts/<name>.md`.
- A `*.default.yaml` file is the shipped copy install writes next to an edited file, never a workflow.

`--input <name>=<value>`, repeatable, gives a workflow input its value. When every required input is given, the document says `"resolved": true` and every `${{ inputs.… }}` and `${{ matrix.… }}` reference is replaced in each run's prompt. Without `--input`, a workflow that declares a required input keeps its input references as written and says `"resolved": false`; one with no required input resolves with each input's `default`, else the empty string. Refused, each with one line: an input the workflow does not declare, an invalid change ID for an input of `type: change`, a value without `=`, a name given twice and, once any `--input` is given, a required input that is not given or is given empty (`theway: --input <name>: required input is not given`).

`theway workflow agents --input change=add-foo`, with the shipped `agents.yaml` (shortened):

```json
{
  "name": "agents",
  "version": "theway.workflow/v1beta1",
  "description": "Implement, review and open the PR through agents",
  "file": "/home/you/.theway/workflows/agents.yaml",
  "default": false,
  "inputs": {
    "change": { "description": "The change to implement", "required": true, "default": null, "type": "change", "value": "add-foo" }
  },
  "runs_on": "agents",
  "resolved": true,
  "steps": [
    {
      "index": 0,
      "uses": "prompts/branch.md",
      "file": "/home/you/.theway/prompts/branch.md",
      "description": "Sync the default branch and create or check out the change's feature branch",
      "runs_on": "session",
      "model": null,
      "matrix": null,
      "with": { "change": "${{ inputs.change }}" },
      "runs": [{ "label": "1.branch", "with": { "change": "add-foo" }, "prompt": "# Branch\n\nYou prepare the feature branch of the change `add-foo`. …" }],
      "on_fail": null,
      "tries": null
    },
    { "index": 1, "uses": "prompts/implement.md", "...": "..." },
    {
      "index": 2,
      "uses": "prompts/review.md",
      "runs_on": "agents",
      "model": "opus",
      "matrix": { "key": "lens", "values": ["prompts/conformance.md", "prompts/correctness.md"] },
      "runs": [
        { "label": "3.review[prompts/conformance.md]", "...": "..." },
        { "label": "3.review[prompts/correctness.md]", "...": "..." }
      ],
      "...": "..."
    },
    {
      "index": 3,
      "uses": "prompts/triage.md",
      "...": "...",
      "on_fail": { "uses": "prompts/fix-review.md", "model": "opus", "label": "4.fix-review", "prompt": "# Fix the Review\n\n…", "...": "..." },
      "tries": 1
    },
    { "index": 4, "uses": "prompts/open-pr.md", "...": "..." },
    { "index": 5, "uses": "prompts/ci.md", "...": "...", "tries": 2 }
  ]

```

- `inputs` holds each declared input with its `value`: the given one, else its `default`, else `""`; `null` while the document is not resolved.
- Each step has its `index`, `uses` and the prompt's absolute `file` and `description`, its effective `runs_on` (its own, else the workflow's) and `model` (its own, else its prompt's; `null` for a step that runs in your session), its `matrix`, its `with` as written, its `runs` and its `on_fail` and `tries`.
- A step has one run, or one per matrix value. Each run has its `label`, `<n>.<prompt>` (`<n>.<prompt>[<value>]` for a matrix copy), every input of its prompt with its final value, and the prompt's body with the values substituted.
- The `on_fail` has its own `label`, `<n>.<prompt>`, `model` and `prompt`.

`--compact` prints the same document without its bulky text, for a session to pass on whole. It checks the workflow the same way and fails with the same lines.

- The top level keeps `name`, `file`, `resolved`, `runs_on` and `inputs`, each with its `value`.
- Each step keeps `index`, `uses`, `file`, `runs_on`, `model`, `matrix`, `runs`, `on_fail` and `tries`; no `description` and no `with` as written.
- Each run keeps its `label` and its `with`, the final values; the `on_fail` its `uses`, `file`, `model`, `label` and `with`. Neither has a `prompt`: an agent reads the prompt's `file` and uses the `with` values where its text says `${{ inputs.<name> }}`.

A file whose `version` is `theway.workflow/v1` is no longer read:

```text
theway: workflows/<name>.yaml: theway.workflow/v1 is no longer read: rewrite it as theway.workflow/v1beta1
```

[Moving from v1](./concepts/workflows.mdx#moving-from-v1) says what replaces each of its parts.

Every mistake of the file and of the prompts it uses is one line on stderr, `theway: <file>: <place>: <message>`, in file order; it then prints nothing on stdout and exits 1. `<file>` is the path relative to the home, or the folder that holds it:

```text
theway: invalid workflow name '<name>'
theway: workflows/w.yaml: not found in <home>/projects/<key>/workflows or <home>/workflows
theway: workflows/w.yaml: version: must be theway.workflow/v1beta1
theway: workflows/w.yaml: steps[0].uses: prompts/nope.md not found in <home>/projects/<key>/prompts or <home>/prompts
theway: workflows/w.yaml: steps[1].with: required input change is not set
theway: workflows/w.yaml: steps[2].on-fail: needs tries (an integer from 1 to 10)
theway: prompts/open-pr.md: body: ${{ inputs.nope }} names no input of this prompt
theway: --input change: required input is not given
```

[Validation](./concepts/workflows.mdx#validation) describes every rule. It also exits 1 with the line of [`project`](#project) for an invalid key.

## dashboard

```bash
theway dashboard [--port <n>]
```

Serves a local web view of the data home: every project's changes, read and edited where they are shown, and the home's Workflows and Prompts. It prints one line with the address on stdout and runs until you stop it:

```text
theway dashboard: http://127.0.0.1:4870/
```

- It listens on `127.0.0.1` only, on port 4870 unless `--port` gives another. `--port 0` lets the system choose a free port, and the line shows the one bound.
- The page, its script, its stylesheet and its two fonts (Inter for the interface, Geist Mono for IDs and code) are built into the CLI: nothing is loaded from another host. It reads the home on every request.
- It answers `403 {"error":"forbidden host"}` to any request whose `Host` header is not `127.0.0.1:<port>` or `localhost:<port>` (on port 80, where a browser leaves the port out, `127.0.0.1` and `localhost` pass too), so a web page cannot reach it through another host name, and `404 {"error":"not found"}` to an unknown path. Every response carries a Content-Security-Policy that allows scripts, fonts, images and connections from the server itself only, and styles from it plus a nonce made for that response.
- Each request answered with a status of 400 or more writes one line to stderr: `theway: <METHOD> <path> <status> <ms>ms`. Successful requests write nothing. An error inside the server writes its message on a line before it.
- The window has the sidebar, on the window's ground, and the work area, one panel with rounded corners: across its top the page's header (its icon and path, its actions at the right, and its views as small tabs under it), then the page, and on a change, workflow or prompt page its panel at the right. A change's, a workflow's and a prompt's page are laid out alike: the header's path ends with the item's ID or file name in mono; under the views, the item's description is the page's title (none when it has none: its ID or file name then stands once, in the header's path), at the same place on every view, the view scrolling under it; the panel is a stack of cards that scroll together, the first giving the item's status. From 1280px wide the panel sits beside the page, can be resized, and the button at the right of the header hides it; the browser remembers its width and whether it is hidden. On a narrower window the button opens it over the page. While the panel is not shown, the header gives the item's status before its button. Text is 15px in the interface at a 1280px-wide window and grows with the window, to 16px at 1920 and 17px from 2560 (every size and space grows with it). Each project has a colour, its folder icon in the sidebar, in its rows and in the header of its pages and changes; a status shows its icon and label in its colour (amber in progress, green ready, red invalid), and blue marks primary actions, the selection, links and progress. When the command starts in a project's directory, that project is recorded as opened once per browser tab, so it shows under Recent unless it is pinned. When that directory's derived key is longer than 200 characters, or its folder is claimed by another root, the command writes a `theway: warning:` line to stderr before the address line: `theway: warning: project key <key> is used by <recorded root>; the dashboard has no start project for <root>`.
- The sidebar lists places, never changes: its top row holds Search and New (New workflow, New prompt); then Now and Search, **Pinned** (the projects and groups you pinned, in their order), **Recent** (the five you opened last that are not pinned), All projects, and **Library** (Workflows and Prompts, which are the home's own, with a red dot when a file has errors). Pinned, Recent and Library fold with the caret after their name, and this browser remembers it. Each project or group gives its number of changes still to do (Ready to archive left out). It opens from 1024px wide; Cmd/Ctrl+B or its button folds it to a rail of icons, and this browser remembers the choice. Open, drag its right edge (the grip between it and the page) to make it wider or narrower, from 13rem to 20rem, or give the grip the focus and use the arrow keys; this browser remembers its width. Its footer holds the version, `theway <version>`, to quote when you report a problem (or run `theway --version`), Documentation, Settings (the theme) and the button that folds the sidebar.
- Pins, groups, recents and dismissed suggestions are kept in `~/.theway/dashboard.json`, so every browser shows the same pins, groups and recents. Whether the sidebar is open, and which groups in it are expanded, is kept per browser.
- A page that fails to render shows the error in its place, with Try again, while the sidebar keeps working; going to another page clears it. If the sidebar itself fails, the whole dashboard shows the error with Reload.
- A `--port` that is not an integer from 0 to 65535 is rejected with `error: option '--port <n>' argument '<value>' is invalid. must be an integer from 0 to 65535`. When the port is taken, it exits 1 with one line on stderr:

  ```text
  theway: port 4870 is in use; pass --port <n>
  ```

  Any other error starting the server exits 1 with a `theway: <message>` line on stderr. Ctrl-C (SIGINT) or SIGTERM stops it with exit 0.

### Now

`#/`, the dashboard's address, opens Now: the open changes of every project, grouped as Invalid, In progress and Not started, each group newest first, then Ready to archive counted per project.

- Each group opens with a band: its status icon, its name and its number of rows, a series counting once (Ready to archive on Now gives its number of changes). The band stays at the top of the list, under the row of column titles, while you scroll through its group. A click on it (or Enter on it) collapses or expands the group, and Alt (Option on macOS) and a click does it for every group of the page. This browser remembers which groups are collapsed, per page; Ready to archive starts collapsed.
- **Invalid** (a `change.yaml` that does not validate), **In progress** and **Not started** list their rows, the most recently changed first, one line each. Each row gives the change's status icon, its description and then its ID in mono (its ID alone when it has no description or the description only repeats the ID), its project (from 1024px wide), its progress (`done/total` tasks, with a ring) and how long ago its `change.yaml` changed. A row that opens has its chevron in the margin before its icon, so every row's name starts on one edge. One row of column titles stands above the first group and stays at the top of the list; a list with no open change (only archived ones) has no progress column. Two or more active changes of one series (`<id>-01`, `<id>-02`, …) show as one row, its first member's description, then the series ID in mono and `series · N` (the ID alone when that member has no description), with their summed progress, that opens to list its members beneath it, indented, each like any other row; a series takes the status of the whole (Invalid when any member is, else Ready when all its members are, Not started when none has started, else In progress).
- **Ready to archive** gives one row per project with its number of changes, which opens that project's page.
- The filter bar above the list searches the changes' IDs and descriptions and filters them by **Project** and **Status**: see [Filters](#filters).
- **Status** is **Archived** lists the archived changes of every project too, one band per month as on a project's page (the latest month open, the older ones collapsed), each row with its ID, its project and its archive date. The search keeps the archived changes whose ID holds the text.

### Filters

Now, a project's or group's page, All projects, Workflows and Prompts share one filter bar:

- The search keeps the rows whose name (a change's ID) or description holds the text.
- **Filter** adds a filter: pick a field from its menu (type to search it), then **is** or **is not**, then one or more values. Each value of the menu gives the number of rows it would keep with the search and the other filters applied, a series counting once. A filter shows as a chip, `Status is In progress, Not started`, with a button that removes it; a click on its condition or its values changes them. **Clear** removes every filter.
- The filters are combined: a row is kept when it passes all of them.
- While the list is narrowed, the right of the bar gives `N of M <rows>`; on a list of changes it counts changes, a series counting its members. When nothing is kept, the list names the search and the filters in use, with Clear filters.
- The search and the filters are kept in the address, so a filtered list survives a reload, and Back and Forward step through its filters: `q=<text>`, `<field>=<value>,<value>` for **is**, `<field>!=<value>` for **is not**, as in `http://127.0.0.1:4870/?kind=step&status=error#/prompts`.
- Each list page (Now, each project's and group's page, All projects, Workflows and Prompts) remembers its last search and filters in this browser. Opened with none in the address (from the sidebar, a link or Back), it takes them back and writes them into the address. An address that holds a search or a filter wins, and becomes the one remembered. Once the search is emptied and the filters removed (**Clear**), nothing is remembered.

### Projects and groups

**All projects** (`#/projects`) lists every group and every project in no group, the most recently archived first, one line each: its name, then the project's path in mono, its numbers of rows In progress and Not started as Now counts them (a series counting once), and its last archive date. A group's line gives its number of projects and their totals, and opens to list its projects beneath it, indented, as a series opens on Now; this browser remembers which groups are open, and while the list is narrowed, a group you have not opened or closed yourself is open. The search keeps the projects whose name holds the text, and a group's projects when the group's name does; the filters are **Group** (Not in a group for a project in none) and **Pinned** (a project in a group is pinned through its group): see [Filters](#filters). On each line:

- The star pins it to the sidebar, or unpins it. A group's line has its star, and a button that opens the group's page.
- The "…" menu adds a project to a group or to a new one (it asks for the group's name), removes it from its group, or, on a group's line, renames the group or ungroups it. A project belongs to one group at most; ungrouping changes no change data, and a notice offers Undo, which puts the group back with its name, its projects and its pin.
- Above the list, the dashboard suggests grouping the projects in no group whose names share their first word ("Group `acme`, `acme-docs` and `acme-site`?"). Nothing is grouped until you press Group; Dismiss hides that suggestion for good.

A project's page (`#/<key>`) and a group's (`#/group/<id>`, its projects together) list the open changes as Now does, with Ready to archive as rows too, then the twelve newest archived changes (every matching one while a search or a filter is set), one band per month (the latest month open, the older ones collapsed; a band counts the month's archived changes, `12 of 98` when the page lists only some), newest first: by archive date, then, within one day, by when each archived `change.yaml` was last written, and a link to the whole archive (`?archive`), which the **Archive** tab under the header opens too (**Changes** comes back). The date column is titled **Updated**, or **Archived** when the list holds archived changes alone. The star after its name pins it to the sidebar, as on All projects (a project in a group has none: its group is pinned). The search keeps the changes whose ID or description holds the text (the ID only for archived ones); the filters are **Status** (Archived included) and, on a group's page, **Project**: see [Filters](#filters). Opening the page records it under Recent.

### Search

Cmd+K (Ctrl+K off macOS), Cmd/Ctrl+P, or Search in the sidebar, opens a palette that jumps to any change of any project, active or archived (each with its project), workflow, prompt or project, and runs actions: Go to Now, Go to All projects, show or hide the sidebar or the panel, New workflow, New prompt, the theme and the keyboard shortcuts. Each entry gives its description first and its ID or file name in mono after it (the ID alone when it has none; a project's name, then its path), with its project, where it applies, its archive date or a project's number of open changes (`5 open`, as the sidebar counts them) at the right; an ID, a project or a path too long for its room is cut in the middle, as lists cut it; an action gives its shortcut there. Type part of a name, description or ID, then choose an entry with the arrow keys and Enter; Esc closes it. Cmd/Ctrl+K again closes it. Inside a Markdown editor, Cmd/Ctrl+K inserts a link instead.

### Keyboard

Outside a text field or an editor: `?` shows the shortcuts; G then N, A, W or P goes to Now, All projects, Workflows or Prompts; the Up and Down arrows (or J and K) move in the list that has the focus and Enter opens the item. Cmd/Ctrl+S saves, anywhere: every changed file of the change on a change's page, the workflow on a workflow's page, the prompt on a prompt's page. The browser's own Back and Forward move between pages, and Cmd or Ctrl and a click opens a page in a new browser tab.

### A change's page

A click on a change opens its page (`#/<key>/changes/<id>`, or `…/changes/archive/<dir>` for an archived one):

- The header gives the change's place: its project (then Archive for an archived change), each a link, then the change's ID in mono.
- The tabs under the header are the change's files, each named by its file: its Markdown files (`spec.md`, `design.md`, `notes.md`, then the others by name), then `change.yaml`; an archived change has no `change.yaml` tab (its tasks are in the panel) unless it has no Markdown file, when its tasks fill the page and the panel keeps Details. Each tab has its own address. A file with unsaved changes shows a dot after its name.
- Under the tabs, the change's description is the page's title (none when it has none or it only repeats the ID: the ID then stands once, in the header's path), at the same place on every tab, at most three lines: Show more under a longer one shows it whole; the file scrolls under it. Below the file, a line gives the file's name, its number of lines and whether it is saved.
- A Markdown file is shown formatted and edited where it is read: see [Editing a change](#editing-a-change). Raw HTML is not rendered, and only `http:`, `https:` and `mailto:` links are links; Cmd or Ctrl and a click opens one.
- Documents are set larger than the rest of the dashboard: 17px text on 24px lines in a column at most 36rem wide (about 65 characters), on the page's left edge, the change's title aligned with it; their headings are never larger than the title (22px): 22, 19 and 17px at full weight, with more room above than under them and a rule over each section (h2). Code blocks and tables keep the same column. A fenced code block shows as a block with its language and a Copy button in its head and no fences; its lines never wrap, and a line wider than the column scrolls sideways in the block; a click on it shows its source to edit. Fenced code in Go, TypeScript, TSX, JavaScript, JSX, JSON, YAML, shell (`sh`, `bash`) or diff is coloured; other code is shown plain. A table's header row is tinted, and a table wider than the column scrolls sideways in its own box. A document with three or more headings has an outline, "On this page", at the right of its text while the page has room for it: a click on a heading scrolls to it, and the section being read is marked.
- The panel at the right is a stack of cards that scroll together: the status and the progress, the **Tasks** (see below), **Details** (the description only when the title does not show it, "Same as the ID" when it only repeats the ID; then project, ID, last change or archive date) and, for a member of a series, **Series**, which lists its members, the change shown marked, and opens them. While the panel is not shown, the header gives the status and the progress before its button.
- A task shows its number, then its lead (its text up to its first colon or semicolon, its first sentence, or the part before its first parenthesis or comma) in full weight, and the rest under it. The next task to do is marked Next and shown whole; another task shows at most three lines of its detail, with Show more when they cut it. Done tasks fold under "N done".
- An archived change is read-only.

### Workflows

The Workflows page lists every workflow file of the home in one table: the global ones (`~/.theway/workflows/`, which apply to all projects) and each project's own (`projects/<key>/workflows/`).

- Each row is one line: its status icon (a green check when the file is valid, the red Invalid mark when it has errors), the workflow's description, then its name in mono (its name alone when it has no description), a `default` chip for the default one and `N errors` when it has errors (the errors are on the workflow's page); then its number of steps, where its steps run (`agents`, `session` or `mixed`), and what it applies to (All projects, or `<project> only`), a column hidden under 1024px wide. A cell too narrow for its text cuts it at the column's edge. A global file is checked with the global folders only; a project's file as that project resolves it.
- The row of column titles stays at the top of the list while it scrolls. The Up and Down arrows (or J and K) move between the rows once one has the focus, and Enter opens it.
- The search keeps the files whose name or description holds the text. The filters are **Applies to**, **Runs on**, **Default**, **Uses prompt** (the workflows whose steps, on-fails or values use a prompt) and **Status** (Valid or Has errors): see [Filters](#filters). A click on a column's title (Workflow, Steps, Runs on, Applies to) sorts the list by it; a second click reverses it, a third drops it.
- Drag the edge of a column's header (the short mark between two titles) to resize it; a double-click on the edge puts it back. When the columns are wider than the page, the table scrolls sideways.

A click on a row opens the workflow's page. Its header gives its path, Workflows › `<name>` in mono, and at its right the button that hides or shows the panel; under it, its views: **Editor**, **YAML** and **History**, each with its own address, a dot after the shown view's name while the workflow has unsaved changes. Under the views, the workflow's description is the page's title (none when it has none: its name then stands once, in the header's path), on every view.

- **Editor** draws the file as a column of numbered cards on a dotted canvas, joined by lines: Inputs (its input, with its description and `required`, or its inputs' names), then one card per step with its number, what its prompt does (whole, the card as tall as its lines), the step's name in mono and where it runs (`session`, `agents · <model>`, then `matrix · N`). A step's on-fail card stands level at its right, dashed, joined by a dashed line marked "on fail · tries N". A card named by an error has a red border and an `N errors` badge; the selected card has a blue border. Drag the canvas to pan, scroll to move, Ctrl or Cmd and scroll (or pinch) to zoom from 50% to 200%. A workflow opens at 100% (one too large for the canvas shows its top and its left). A toolbar strip above the canvas has Undo and Redo at its left, and zoom out, the zoom, zoom in and Fit at its right. Fit zooms out until the workflow fits, to 50% at most; with the focus on the canvas, Cmd or Ctrl and `0` fits, and `=` or `-` zooms. While part of the workflow is out of view and the room at the right of the drawing holds it, a minimap at the bottom right shows where you are. Tab moves through the cards and their buttons, Enter or Space selects a card, Escape clears the selection. The selected card is kept in the page's address (`?step=inputs`, `?step=3`, `?step=3-on-fail`), so a reload or a copied link opens it selected. A file whose YAML does not parse, or that is not a `theway.workflow/v1beta1` map, cannot be drawn: the tab says why and links to YAML.
- **YAML** shows the file in a code editor (Geist Mono, 14px on 20px lines at a 1280px-wide window, line numbers at the left), each error underlined in red with a red dot beside its line; hovering the underline or the dot gives the error. Ctrl or Cmd and F opens the search above the code: Next, Previous, All, Match case, Regexp and By word, and on an editable file Replace and Replace all. You can edit it: see [Editing a file](#editing-a-file).
- **History** lists the versions the dashboard kept: see [History](#history).
- The errors stand in a strip under the views, and in the panel's **Problems** card; a click on one selects its card on Editor, or puts the cursor on its line on YAML.
- The panel at the right is one column of cards that scroll together: first the workflow's status, Valid or `N errors`, with `default` at its right for the default workflow; **Problems** when the file has errors; then, with no card selected (or the Inputs card), **Workflow** and **Inputs**, which edit the workflow, and **Details** (Applies to, Steps, Runs on, the file's path with a button that copies it); for a selected step, **Step** (its keys, which edit it), **Prompt** and **Used by**. **Prompt** is read-only: Open prompt goes to the prompt's page, where it is edited; it gives the prompt's file, its header's description, model and inputs (each required, or its default, or optional, with its description), then its body at the panel's size, at most 62 characters a line. **Used by** lists the workflows that use the prompt, where each uses it, `this workflow` for the page's own, and opens them. On YAML and History the cards show the same facts read-only, and on History the panel lists the versions. Cmd/Ctrl+S saves the workflow.

### Prompts

The Prompts page lists every prompt file of the home the same way. A Step prompt has a header (even one with errors), a Reference file has none.

- Each row is one line, as on Workflows: its status icon, the prompt's description then its name in mono (its name alone when it has no description) and `N errors` when it has errors; then its kind, its model, the workflows that use it (as a step, an on-fail, or a value: the first, then `+N`, which lists every use), and what it applies to. Under 1024px wide the Model and Applies to columns are hidden, so the list never scrolls sideways; every column sorts and resizes as on Workflows; the row of column titles stays at the top, and the arrows (or J and K) move between the rows. A prompt's errors are its header's and those the workflows that use it report about it.
- The filters are **Kind**, **Applies to**, **Model** (None for a prompt that sets none), **Used by** (No workflow for a prompt none uses) and **Status**: see [Filters](#filters).

A click on a row opens the prompt's page. Its header gives its path (Prompts › its name in mono) and the panel's button, and its views as tabs; under them, its description is the page's title (none when it has none: its name then stands once, in the header's path), on every view. **Prompt** shows the file as a document, set and edited as a change's Markdown files are (see [Editing a change](#editing-a-change)), its header between its `---` lines shown as its source in mono; **History** lists its versions. The panel at the right is one column of cards: its status (Valid or `N errors`), **Problems** while the prompt has errors (a click on an error that names a line opens the Prompt tab with the cursor on it), **Versions** on History, **Details** (its kind, model, what it applies to and its file path, with a button that copies it; its description too when it has none to be the title), **Inputs** (each required, optional or with its default, and its description) and **Used by**, the workflows that use it, each with the step that uses it, opening the workflow's page.

### Editing a file

A prompt's Prompt tab, a workflow's YAML tab and its Editor tab's fields are editable. What you type is a draft that lives on the file's page:

- 400ms after your last keystroke, the dashboard checks the draft as `theway workflow` would read it, without writing anything. The errors show in the strip under the views (on their lines too in a workflow's YAML), as `N errors` in the panel's first card (in the header while the panel is not shown) and in its Problems card; the Editor tab and the panel follow the draft. When the check cannot run (the server stopped), a notice says so and the errors are cleared until the next check.
- Two workflows of one context that both set `default: true` are reported as `theway workflow` reports them, on the line of the `default` key: both global files when both are global, only the project's file when a project's file and a global one both set it.
- The line under the file gives its name and its number of lines. While the draft differs from the file, it says "Unsaved · Cmd/Ctrl+S to save" with Discard, and Cmd/Ctrl+S saves. Saving is never automatic. Ctrl or Cmd and Z undoes, Ctrl or Cmd, Shift and Z redoes; the draft stays while you move between the page's tabs.
- Save waits for the check of the current draft and asks once when it has errors ("Save anyway"): the file is still written, since your own editor could write the same text. "Saved" shows in the line under the file until the next edit.
- Save is refused when the file changed on disk since the page loaded it: a notice offers Reload, which drops the draft and loads the file. A save that fails otherwise shows the server's error. Neither drops your draft.
- Leaving the page with unsaved changes (a link, the sidebar, Back) asks first: Keep editing, Discard, or Save and leave. Moving between the tabs of the same file does not ask. Closing or reloading the browser tab gets the browser's own prompt.
- Writes go through the file's folder with a temporary file and a rename, so an interrupted write never leaves a truncated file.

Every request that is not a read must come from the dashboard's own page: an `Origin` of `http://127.0.0.1:<port>` or `http://localhost:<port>` and the `X-Theway-Token` header holding the token the server makes when it starts and puts in the page, else `403 {"error":"forbidden"}`. It must be `application/json` (`415`), at most 1 MiB (`413`), and valid JSON with its fields (`400`). The server writes only `~/.theway/workflows/`, `~/.theway/prompts/`, the same two folders of a project, `~/.theway/history/`, `~/.theway/dashboard.json`, the `change.yaml` and Markdown files of a project's active change folders, and, when it starts, `projects/<key>/root` of the start project when it claims that folder. `~/.theway/dashboard.json` holds the pins, groups, recents and dismissed suggestions.

### Editing a workflow

A workflow's Editor tab edits the file too. Every edit changes the same draft as the YAML tab, so the unsaved line, the check, Save, Discard and History work the same way, and the YAML tab always shows the text the canvas made:

- **Add a step**: the round "+" on each line between two cards, or the one under the last card, opens a step picker in the panel, and a dashed card marks where the step goes in. The picker lists each prompt by what it does, its name in mono after it. Search by name or description, move with the arrow keys and press Enter, or click a prompt: the step goes in at that place with `uses: prompts/<name>.md` and, under `with`, each input the prompt requires (`${{ inputs.<name> }}` when the workflow declares an input of that name, else `""`, which the check reports until you set it). Escape or Close leaves the picker. A project's workflow lists that project's prompts first, then the global ones it does not replace.
- **Move or remove a step**: the "…" menu at the top right of a step card has Move up, Move down and Remove step. Cards are not dragged: the order changes only through this menu.
- **Edit a step**: select its card. Its **Step** card shows its keys as rows, each named after its key: Uses (the prompt's file, a link to its page) with Change prompt in the card's header (another prompt: the `with` keys it declares are kept, its required inputs added, the others removed), Runs on (`runs-on`), Model (`model`), under With one field per input of its prompt (named in mono, `required` under the name), Matrix (`matrix`: a switch, then its key and its values, one per line), On fail (`on-fail`) with its own inputs, On fail model (`on-fail.model`) and Tries (`tries`), then Remove step. Choosing the first option of a select ("Workflow's", "Prompt's", None) removes the key. Selecting an on-fail card opens its step's card at On fail.
- **Edit the workflow**: with no card or the Inputs card selected, the **Workflow** card edits `description`, `runs-on` and `default`, and the **Inputs** card the inputs (Add input in its header, then for each its name with a button that removes it, `type`, `description`, `required`, `default`). An empty name, or one another input has, is not written.
- Each error stands under the field it names, or at the top of its card.
- Undo and Redo in the canvas toolbar (or Ctrl or Cmd and Z on the YAML tab) undo the canvas's edits and the YAML tab's alike; the keystrokes typed in one field undo together.
- Each edit writes the whole file again with the `yaml` package: values and comments are kept (a comment goes with the step or key it belongs to when that is removed), and so are blank lines and the quoting of each value. The layout may change on lines you did not touch, the values staying the same: a `>-` text is written on one line, indentation becomes two spaces, a comment on the line of a key whose value is a block moves to the next line, and a final line break is added.
- A value a field cannot show (a `tries` out of 1 to 10, a list where text is expected, a matrix that is not one key with a list of strings) leaves that field disabled: edit it on the YAML tab. A file that uses YAML anchors is drawn read-only, and a file that cannot be drawn is fixed on the YAML tab.

### Editing a change

The page of an active change edits its tasks, its description and its files where they are shown. Every edit changes a draft the page holds, one per file; nothing is written until you save: Cmd/Ctrl+S writes every changed file of the change. A file tab with unsaved changes shows a dot, and the line under the file says "Unsaved" with Discard, which drops that file's draft after asking.

- **Markdown files** are edited where they are read: the text is formatted, and the Markdown syntax shows only on the lines the cursor is on. A paragraph written over several lines reads as one, except the paragraph the cursor is in, which shows its lines as written. Tables are drawn as tables until you click one, which shows its source. The checkboxes of task lists tick; each flips one character of its line. Ctrl or Cmd and B, I, E and K make bold, italic, code and a link.
- **Markdown fields**: a task's text, the description and a workflow's descriptions are edited the way a Markdown file is, in the same editor at the panel's size: formatted where you type, with the same keys (Ctrl or Cmd and B, I, E and K; Z to undo, Shift and Z to redo). What you type goes into the draft at once, like a file's text, so the line under the file says "Unsaved", Cmd/Ctrl+S saves it, Discard drops it and leaving the page asks first. Enter starts a new line (the description stays on one line). Escape, or a click elsewhere, closes a task's or the description's field. A text the file cannot hold (an empty task, an empty description) shows why under the field and is not written.
- **Tasks**, in the panel: tick a task's checkbox, click its text (or press Enter on its row) to change it, or click "Add a task" at the bottom (or Add a task below in a row's menu) and type: the task is added as soon as its text is not empty. Each row's "…" menu has Edit, Move up, Move down, Add a task below and Delete; a task also moves by dragging its handle, or with Alt and the Up or Down arrow while its row has the focus. Delete shows "Task N deleted" with Undo. A change keeps at least one task.
- **Description**: it is the page's title; click the title to change it. A change with no description, or one that only repeats its ID, has no title: its description is in the panel's Details ("Same as the ID"), where a click changes it.
- **`change.yaml`**: its tab shows the file in the code editor, its errors listed and marked on their lines. The task list, the description and the text are one draft, so undo in the editor undoes the list's edits too. While the draft does not pass the check, the panel's Tasks show its issues.
- The status, the progress and the next task follow the draft before you save.
- Each task edit loads `change.yaml`, changes it and prints it again as [`task done`](#task-done) does: values, comments and line endings are kept, a comment above a task moves and is removed with it, and the layout of other lines may change as described there.
- Save is refused when the file changed on disk since the page loaded it, for example when an agent ran `theway task done`: a notice offers Reload, which drops that file's draft and loads the file. Leaving the change page with unsaved changes asks first; Save there writes every changed file.
- Do not add, move or remove tasks while a workflow runs on the change: agents address tasks by their number.

### Creating a file

The Workflows page's "New workflow" button and the Prompts page's "New prompt" open one dialog:

- **Name**: lowercase letters and digits, in words joined by single hyphens, not taken where the file would be written.
- **Applies to**: All projects (the home's folder), or One project (that project's folder, created when missing). A project's file of the name of a global file replaces the global one for that project; the dialog says so.
- **Start from**: Empty, or a copy of any file of that kind, written unchanged.
- **Description**, for Empty only. An Empty workflow is `version: theway.workflow/v1beta1`, its description, `runs-on: agents` and `steps: []`, so the page then reports that its steps are missing; an Empty prompt is a header with its description and `model: opus`, and an empty body.

On Create the new file's page opens.

### History

Each time the dashboard saves or restores a file, it keeps the text it replaces as a version, under `~/.theway/history/global/<kind>/<name>/` for a global file and `~/.theway/history/projects/<key>/<kind>/<name>/` for a project's, one file per version named by its UTC time and the start of its SHA-256. A file keeps its 20 newest versions. Only the dashboard writes there; deleting the folder only drops the versions. A save of the same text keeps nothing.

The History tab of a workflow's and a prompt's page lists, in the panel's **Versions** card, Current (the file as saved), then each version by its date and time in your time zone with the lines it added and removed; the selected one is on the blue tint. A bar above the code names the selected version and its lines, with Show changes, Unified and Split, and Restore. Selecting a version shows its difference from the file as saved (not your draft), unchanged stretches collapsed, in one column (Unified) or side by side (Split); the browser remembers the layout. Turning off Show changes shows the version's text alone. Restore writes the version as the file, after asking, and keeps the replaced text as a version, so a restore can itself be undone; it drops unsaved changes.

## authority

```bash
theway authority
```

Prints the authority whole, without trailing blank lines. A file that is empty or holds only whitespace counts as missing.

- When `.shipped.json` lists `standards/authority.md`, it prints `<home>/standards/authority.md`, else the shipped `<home>/standards/authority.default.md`. When neither can be printed, it exits 1:

  ```text
  theway: no <home>/standards/authority.md; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins
  ```

- When `.shipped.json` does not list it, `authority.md` is your own standard (see [`standards`](#standards)), and it prints `<home>/standards/authority.default.md` only. When that cannot be printed, it exits 1:

  ```text
  theway: no <home>/standards/authority.default.md; run npx --yes @pixelfactoryio/theway@latest install, then /reload-plugins
  ```

The commands that spawn agents quote its output verbatim in every agent prompt, and `/theway:workflow`, `/theway:document` and `/theway:archive` follow it in the session.

## validate-id

```bash
theway validate-id <id>
theway validate-id <id> --series
```

Checks a [change ID](./concepts/changes.mdx#change-ids). It exits 0 when the ID is valid. Otherwise it exits 1 and prints one line on stderr:

```text
theway: invalid change id '<id>': <reason>
```

Every ID must be lowercase kebab-case (`[a-z0-9]` segments joined by single hyphens) and start with `add-`, `update-`, `refactor-`, `remove-` or `fix-`. An ID with uppercase letters is rejected with `uppercase letters are not allowed; use lowercase kebab-case`, one with underscores with `underscores are not allowed; use kebab-case (-)`; any other start is rejected with:

```text
theway: invalid change id '<id>': must start with a verb prefix: add-, update-, refactor-, remove- or fix-
```

- **Without `--series`** (a standalone change): the ID must not end in a one- or two-digit number.
- **With `--series`** (a series member): the ID must end in a two-digit ordinal from `01`, such as `add-user-auth-01`. Letter suffixes, `-00` and double ordinals are rejected.

`/theway:engineering`, with or without `--light`, runs it before it writes a standalone change folder; [`next-id`](#next-id) validates the members of a series.

## next-id

```bash
theway next-id <series-id>
theway next-id <series-id> --count <n>
```

Prints the next `<n>` free member IDs of a [series](./concepts/changes.mdx#series), one per line (`--count` defaults to 1):

```text
add-user-auth-04
add-user-auth-05
```

- A trailing `-NN` is removed from `<series-id>` first, so `add-user-auth-07` gives the same IDs as `add-user-auth`. The rest must fit the [`validate-id`](#validate-id) format and must not end in a one- or two-digit number; when it is invalid, it exits 1 with a `theway: invalid change id '<id>': <reason>` line, `<id>` being the series ID without its ordinal, for example:

  ```text
  theway: invalid change id 'add-thing-01': ends in a number (-01); a series id cannot end in a number
  ```

- It counts the folders `<home>/projects/<key>/changes/<series-id>-NN` and the archived `<home>/projects/<key>/changes/archive/YYYY-MM-DD-<series-id>-NN`, and continues after the highest `NN`, or from `01` when there is none.
- A `--count` that is not a positive integer is rejected with `error: option '--count <n>' argument '<value>' is invalid. must be a positive integer`. When the last ID would be past `-99`, it exits 1:

  ```text
  theway: series <series-id> would go past -99
  ```

`/theway:engineering` runs it to name the members of a new series.
