---
title: How it works
description: Engineering, then develop or workflow, then archive.
---

A change goes through three commands.

```text
/theway:engineering <request>        writes spec.md and tasks.md
  or /theway:engineering-light <request>   writes a short spec for a small change
/theway:develop <change-id>          implements the tasks inline
  or /theway:workflow <change-id>   implements them through a workflow of agents and a PR
/theway:archive <change-id>          moves the finished change to the archive
```

## 1. Engineering

[`/theway:engineering`](./commands/engineering.mdx) runs `theway context` for the config and the [standards](./concepts/standards.mdx), reads the [TAMM framework](./concepts/tamm.mdx), picks a [change ID](./concepts/changes.mdx) and validates it with `theway validate-id`, or, for a series, gets the member IDs from `theway next-id`. It investigates the code and the open questions, then writes `spec.md` and `tasks.md` from the templates, and `design.md` when the change needs API contracts, data models or diagrams. Two critic agents then review the spec and tasks for gaps, unless `review_rounds` is `0` or a question is already open; without the Agent tool, it runs both reviews itself. It verifies each finding and fixes every confirmed gap it can settle from facts, then stops if a finding needs your decision.

A `fix-` change uses the fix template for `spec.md`, and the command reproduces the bug before it writes anything. When the bug cannot be reproduced, may already be covered by another active change, or turns out to be intended behavior, it stops and asks you, and writes no change folder.

For a small change with nothing to decide, [`/theway:engineering-light`](./commands/engineering-light.mdx) writes a short spec (`**Mode:** light`) and 1 to 3 tasks, and one grounding critic reviews them. When it finds a decision, a contract change, a Medium or High risk or a series, it sends you to `/theway:engineering`.

It writes the change files only under `<home>/<project>/changes/<change-id>/` (`<home>` is the folder `theway path` prints, `~/.theway` by default); throwaway probes write to a temporary directory created with `mktemp -d`. If a question is still open, it reports the review and the question, then stops: the spec is not ready until it is answered.

## 2. Develop

Both develop commands read `standards/develop.md`, the standards `theway context` lists, the change's `spec.md`, `tasks.md` and `design.md`, and `docs/architecture/coding-standards.md` when it exists; `/theway:workflow` also reads `standards/spec-review.md` and resolves its [workflow](./concepts/workflows.mdx) with `theway workflow`, while `/theway:develop` reads no config key. Both treat the spec as the contract. When the code contradicts the spec, the work stops and comes back to you with the options.

- [`/theway:develop`](./commands/develop.mdx) implements the tasks inline in the current session, ticks each one in `tasks.md` and reports how each Success Criterion was verified.
- [`/theway:workflow`](./commands/workflow.mdx) runs the change through the steps of a [workflow](./concepts/workflows.mdx) file. The shipped `develop` workflow hands the change to an implementer agent, which commits on a local feature branch; reviewer agents, one per lens, review it locally, then the branch is pushed once and the PR opened. Review rounds and CI attempts are capped by the workflow's fields, filled from [`workflow.defaults`](./configuration.mdx#workflow); a workflow without a `pr` step pushes nothing. In a series, each PR is merged after you confirm it.

### Choosing between them

| | `develop` | `workflow` |
|---|---|---|
| Where the code is written | In your session | In agents |
| Branch and PR | Not part of the command | Branch created by the command; PR opened by the `pr` step after the local review, none without a `pr` step |
| Review | None built in | One reviewer agent per lens, up to `rounds` rounds per `review` step |
| CI | Run the CI commands locally | Polled on the PR, failures go to a fix agent, `ci_attempts` per change |
| Several changes | One change | A series, developed in order, each PR merged after you confirm it; without a `pr` step, stacked local branches and nothing merged |

Pick `develop` to watch and steer the work in your session. Pick `workflow` when the change should end as a reviewed, CI-green PR, or to run a whole series.

## 3. Archive

[`/theway:archive`](./commands/archive.mdx) moves a finished change to `<home>/<project>/changes/archive/YYYY-MM-DD-<change-id>/`. It runs only when you name the change and say to archive it. It refuses while a numbered task in `tasks.md` is open, unless you accept the open tasks and it runs with `--force`.

See the [Examples](./examples/full-change.mdx) section: one change from request to passing tests, then a light fix, an escalation, a workflow run, a series and standards.
