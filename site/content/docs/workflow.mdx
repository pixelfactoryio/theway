---
title: How it works
description: Engineering, then workflow, then archive.
---

A change goes through three commands.

```text
/theway:engineering <request>        writes spec.md and tasks.md
  or /theway:engineering --light <request>   writes a short spec for a small change
/theway:workflow <change-id>         implements the tasks inline, in your session
  or /theway:workflow --workflow agents <change-id>   implements them through agents and a PR
/theway:archive <change-id>          moves the finished change to the archive
```

## 1. Engineering

[`/theway:engineering`](./commands/engineering.mdx) runs `theway context` for the config and the [standards](./concepts/standards.mdx), reads the [TAMM framework](./concepts/tamm.mdx), picks a [change ID](./concepts/changes.mdx) and validates it with `theway validate-id`, or, for a series, gets the member IDs from `theway next-id`. It investigates the code and the open questions, then writes `spec.md` and `tasks.md` from the templates, and `design.md` when the change needs API contracts, data models or diagrams. Two critic agents then review the spec and tasks for gaps, unless `engineering.review.rounds` is `0` or a question is already open; without the Agent tool, it runs both reviews itself. It verifies each finding and fixes every confirmed gap it can settle from facts, then stops if a finding needs your decision.

A `fix-` change uses the fix template for `spec.md`, and the command reproduces the bug before it writes anything. When the bug cannot be reproduced, may already be covered by another active change, or turns out to be intended behavior, it stops and asks you, and writes no change folder.

For a small change with nothing to decide, [`/theway:engineering --light`](./commands/engineering.mdx#light) writes a short spec (`**Mode:** light`) and 1 to 3 tasks, and one grounding critic reviews them. When it finds a decision, a contract change, a Medium or High risk or a series, it sends you to `/theway:engineering` without `--light`.

It writes the change files only under `<home>/projects/<key>/changes/<change-id>/` (`<home>` is the folder `theway path` prints, `~/.theway` by default); throwaway probes write to a temporary directory created with `mktemp -d`. If a question is still open, it reports the review and the question, then stops: the spec is not ready until it is answered.

## 2. Workflow

[`/theway:workflow`](./commands/workflow.mdx) runs the change through the steps of a [workflow](./concepts/workflows.mdx) file. It reads `standards/develop.md`, `standards/spec-review.md`, the standards `theway context` lists, the change's `spec.md`, `tasks.md` and `design.md`, and `docs/architecture/coding-standards.md` when it exists, and resolves the workflow with `theway workflow`, its fields filled from [`workflow.defaults`](./configuration.mdx#workflow). The spec is the contract: when the code contradicts it, the work stops and comes back to you with the options.

Each step runs inline, in your session, or through agents in the plugin workflow `theway:run-pipeline`, as its `agents` field says. theway ships two workflows:

- **`develop`**, the default: one inline `implement` step. Your session implements the tasks, ticks each one in `tasks.md` and reports how each Success Criterion was verified. Nothing is committed: the change stays in your working tree.
- **`agents`:** an implementer agent commits on a local feature branch; reviewer agents, one per lens, review it locally; then the branch is pushed once, the PR opened and CI driven to green. Review rounds and CI attempts are capped by the workflow's fields. In a series, each PR is merged after you confirm it.

### Choosing between them

| | `develop` | `agents` |
|---|---|---|
| Where the code is written | In your session | In agents |
| Branch and PR | No branch, nothing committed | Branch created by the command; PR opened by the `pr` step after the local review |
| Review | None built in | One reviewer agent per lens, up to `rounds` rounds per `review` step |
| CI | Run the CI commands locally | Polled on the PR, failures go to a fix agent, `ci_attempts` per change |
| Several changes | One change | A series, developed in order, each PR merged after you confirm it |

Use `develop` to watch and steer the work in your session. Use `--workflow agents` when the change should end as a reviewed, CI-green PR, or to run a whole series. Between the two, your own workflow can mix them, for example an inline `implement` followed by a `review` and a `pr` through agents.

## 3. Archive

[`/theway:archive`](./commands/archive.mdx) moves a finished change to `<home>/projects/<key>/changes/archive/YYYY-MM-DD-<change-id>/`. It runs only when you name the change and say to archive it. It refuses while a numbered task in `tasks.md` is open, unless you accept the open tasks and it runs with `--force`.

See the [Examples](./examples/full-change.mdx) section: one change from request to passing tests, then a light fix, an escalation, a workflow run, a series and standards.
