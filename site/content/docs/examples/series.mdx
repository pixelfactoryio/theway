---
title: A series
description: "One request split into three changes: member IDs from `theway next-id`, one review across them, and one PR per member, merged in order."
---

This is an illustrative run on the sample project `my-api`. It adds user authentication as a [series](../concepts/changes.mdx#series) of three changes, each built on the one before.

## The request

```text
/theway:engineering add-user-auth as a series: password storage, the login endpoint, docs
```

## The member IDs

The request asks for a series, so `add-user-auth` is the series ID. The command asked the CLI for three member IDs, on a home with no `add-user-auth` folder yet:

```text
$ theway next-id add-user-auth --count 3
add-user-auth-01
add-user-auth-02
add-user-auth-03
```

It assigned them in dependency order:

| Member | Change |
|---|---|
| `add-user-auth-01` | Password storage: a `users` record with an scrypt hash from `node:crypto`, no new dependency |
| `add-user-auth-02` | `POST /login`, checking the password against the stored hash |
| `add-user-auth-03` | README: how to create a user and log in |

Each member is its own change folder, with its `spec.md` and its `change.yaml` (see [Series](../concepts/changes.mdx#series)).

## The review

The `spec-review` step's two critics covered the three members together. The triage confirmed three findings, `fix-spec` fixed them and the triage's second round checked each fix. The run's report, with the full reports of the failed triage round and of the last step:

```text
Workflow: engineering (/home/you/.theway/workflows/engineering.yaml)
- 1.scaffold: pass (inline)
- 2.spec-review[prompts/grounding.md]: pass
- 2.spec-review[prompts/implementability.md]: pass
- 3.spec-triage: fail
- 3.fix-spec: pass
- 3.spec-triage (round 2): pass

3.spec-triage: fail
0 confirmed: add-user-auth-02 names a verifyPassword helper that -01 does not export. fixable.
1 confirmed, settled: add-user-auth-02 does not say what POST /login returns on success. -02 returns 200 with a JSON body: every my-api route answers through send(status, body) with JSON (send(200, { ok: true }) in src/app.js), and -02's Out of Scope excludes sessions and tokens. fixable.
2 confirmed: -03 has a task to review the README wording, which is not repository work. fixable.

3.spec-triage (round 2): pass
0 resolved: -01 task 2 now exports verifyPassword(password, hash).
1 resolved: -02's spec.md says POST /login returns 200 with a JSON body.
2 resolved: the -03 task to review the README wording is removed.
```

## The agents run

```text
/theway:workflow --workflow agents add-user-auth-01 add-user-auth-02 add-user-auth-03
```

The default `develop` workflow opens no PR, so a series runs with a workflow that does, here the shipped `agents`; with one that opens none, the series stops after its first change. The members run in order, each from the synced `main`. After each run succeeds, the command asks before merging the PR it opened:

```text
add-user-auth-01: PR #13 https://github.com/example/my-api/pull/13, CI green (1 of 2 attempts), 2 files changed, +55 -0
Merge PR #13? (yes / no)
```

On `yes`, it squash-merged PR #13, synced `main`, and created `add-user-auth-02`'s branch from it. PR #14 and PR #15 went the same way. Any other answer would have stopped the run, with the later members not started.

## The list

Each implementer ticked its tasks with `theway task done`, so each member's `change.yaml` has its three tasks done:

```text

```
