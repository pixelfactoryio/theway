This is an illustrative run on the sample project `my-api`. It takes the `add-rate-limiting` change of the [full change](./full-change.mdx), from the same spec and tasks, and runs it with `/theway:develop-workflow` instead of `/theway:develop`.

## The request

```text
/theway:develop-workflow add-rate-limiting
```

The config is the default: one review round, two CI attempts, `open_pr: true`.

## Implement

The command synced `main`, created the branch `add-rate-limiting` and spawned one implementer, as the nine tasks build on each other. The implementer followed `develop.md`, committed locally with the `feat` type of an `add-` change, and ran `npm test` (10 tests, 10 pass). The orchestrator, not the agent, ticked the tasks in `tasks.md`.

## Review locally

Before anything was pushed, reviewer agents tried to refute the branch diff against the spec. They reported three findings, triaged as:

- `0` `confirmed`: the close test only checks that `close` completes, not that the sweep timer is cleared.
- `1` `confirmed`: per-IP counting is tested on the limiter only; no HTTP test sends from two addresses.
- `2` `false_positive`: "`Retry-After` can be `0` in the window's last millisecond". Refuted: the header is `max(1, ceil((resetAt - now) / 1000))`.

One fix agent added both tests, in a commit of type `test` since it changes only tests, and re-ran `npm test` (12 tests, 12 pass). The fix check then read the fix commit and answered `resolved` for findings 0 and 1.

## Open the PR and drive CI

The branch was pushed once and PR #12 opened, titled `feat: add per-ip rate limiting`. CI went green on attempt 1. With a single change, there is no merge question: the run stops with the PR ready for your validation.
