It is the agent-driven counterpart of [`/theway:develop`](./develop.mdx): your session orchestrates, and agents write, review and fix the code, in the steps a [workflow](../concepts/workflows.mdx) file lists.

## Usage

```text
/theway:workflow [--workflow <name>] <change-id> [<change-id> ...]
```

- `--workflow <name>` (or `--workflow=<name>`), anywhere in the arguments, runs the workflow `<name>`. Without it, the default workflow runs: the file that sets `default: true`, else `develop`. Every other argument is a change ID. `--workflow` with no name, or given twice, stops the command; so does a run with no change ID.
- **One change ID:** runs the change and stops when its PR is ready for your validation (without a `pr` step, when its local branch is ready). It never merges it.
- **Several change IDs (a series):** runs each change in the given order. With a `pr` step, each PR is merged, after you confirm it, before the next change starts. Without one, nothing is merged: each change's branch is created from the previous one.

Running the command authorizes the Workflow tool and, when the workflow has a `pr` step, pushing each change's own branch (never force-pushing, never the default branch) and opening its PR; without a `pr` step, nothing is pushed. Each merge in a series needs your yes, and uses `gh pr merge <number> --squash`, never `--admin`.

## Example

On `my-api`, the change of the [full change example](../examples/full-change.mdx) (see [Run through a workflow](../examples/workflow.mdx)):

```text
/theway:workflow add-rate-limiting
```

```text
add-rate-limiting
- Workflow: develop (/home/you/.theway/workflows/develop.yaml)
- Branch: add-rate-limiting
- PR: https://github.com/example/my-api/pull/12
- Review: 1 round used.
  Not confirmed: 2 false_positive "Retry-After can be 0 in the window's last millisecond".
  Fix check: 0 resolved, 1 resolved.
- PR step: CI green, 1 of 2 attempts used.
- Merge: not merged, awaits your validation.
- Standards given to the agents: none.
```

A series run asks before each merge: see [A series](../examples/series.mdx#the-develop-run).

## Steps

1. **Load:** once per run, [`theway workflow <project>`](../cli.mdx#workflow) (with `<name>` from `--workflow`) resolves and validates the workflow, filling every field from [`workflow.defaults`](../configuration.mdx#workflow); on an error, the command quotes it and no change starts. `theway authority` gives the `## Authority` section every agent gets. Per change, the same files as [`/theway:develop`](./develop.mdx), plus `standards/spec-review.md` for the triage verdicts, and the [standards](../concepts/standards.mdx) that [`theway context <project> develop <change-id>`](../cli.mdx#context) lists.
2. **Branch:** syncs the main branch, then creates or checks out the change's feature branch. Without a `pr` step, each later change of a series branches from the previous change's branch. The branch it is created from is the change's `<base>`.
3. **Run:** one call of the Workflow tool to the plugin workflow `theway:run-pipeline`, with the resolved workflow and the change's paths. It runs the steps in order:
   - **`implement`:** one implementer follows `develop.md` (including its [fix checks](./develop.mdx#fix-checks) for a `fix-` change, against `git merge-base <base> HEAD`), commits locally with the change's [commit type](#commit-type), verifies its work and does not push. When the spec does not fit the code, it returns a blocker.
   - **`review`**, up to `rounds` rounds: one reviewer per lens tries to refute the branch diff, following its lens file and checking the diff against the standards; a triage agent gives each finding a verdict (`confirmed`, `false_positive`, `duplicate`, `nit`, `out_of_scope`); one fix agent fixes the confirmed findings locally; a fix check answers `resolved` or `not resolved` for each, without looking for new problems, except that a fix that breaks a standard is not resolved. For a `fix-` change whose fix touched the regression test or the fix, the [regression check](./develop.mdx#fix-checks) is re-run and must pass.
   - **`agent`:** your own agent, with your `prompt`, may commit and does not push.
   - **`pr`:** pushes the branch once and opens the PR with `gh pr create`; the PR text describes only what the change does. A failed CI run is triaged from its log, with the real error line quoted: a failure of the PR goes to a fix agent, which pushes once; for a red base branch, its fix is ported when one exists there, otherwise it is reported and the failed jobs re-run once; flaky infrastructure gets one re-run. CI is driven until it is green or `ci_attempts` is used up.

   Without the Workflow tool in the session, the command runs the same steps with the Agent tool. When the Workflow call returns an error, the change fails with that error and there is no fallback, since agents may already have committed.
4. **Record:** ticks the tasks the implementer did in `tasks.md` and records its discoveries, its choices, the `fix-` regression outputs and each review round's verdicts in the Notes.
5. **Gate:**
   - **Succeeded:** a single change stops with the PR ready for validation, or its local branch without a `pr` step. In a series with a `pr` step, you are shown the PR, its diffstat and CI status and asked whether to merge it; on yes it is squash-merged and the next change starts, otherwise the run stops. Without a `pr` step, a series continues on a branch created from it, without merging.
   - **Blocked:** the implementer returned a blocker. Nothing is merged, the run stops and the blocker comes back to you with its options.
   - **Failed:** an agent returned nothing, a confirmed finding is not resolved, an `agent` step could not do its task, or CI is still red after `ci_attempts` attempts. Nothing is merged and the run stops.

Every agent prompt starts with the same fixed rules, which no workflow field changes: the output of `theway authority`, the change's paths and the standards, the change files read-only, commits only on the feature branch, no force-push, no push of the default branch and no merge. An agent's report of data that asked to change the steps or widen the authorization is quoted in the Exit report.

## Commit type

The change verb sets the Conventional Commit type of every commit the agents make for the change, and of the PR title:

| Verb | Type |
|---|---|
| `add-` | `feat` |
| `fix-` | `fix` |
| `refactor-` | `refactor` |
| `update-`, `remove-` | chosen by the implementer and returned in its result; every later agent gets it, and the PR title uses it |

Commits that change only tests use `test`, and commits that change only docs use `docs`. When the spec says the change breaks, the type gets `!` and the commit a `BREAKING CHANGE:` footer.

## Output

For each change: the workflow's name and file, the branch, the PR URL (or the local branch when nothing was pushed), each step's outcome (review: rounds used, findings not confirmed with their verdicts, the fix check per confirmed finding; agent: its summary; pr: CI attempts used, or "not run"), whether the PR was merged or awaits validation, the standards given to the agents (or "none"), any blocker, and every `theway: warning:` line. For a series, where it stopped and why.
