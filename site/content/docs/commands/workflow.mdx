---
title: /theway:workflow
description: "Run changes, or a request, through a YAML workflow of steps, inline or through agents, and open a PR when the workflow pushes"
---

It runs a change through the entries a [workflow](../concepts/workflows.mdx) file lists: steps, each a step file whose agents read prompt files, and gates that ask you before going on. The default, the shipped `develop` workflow, implements the tasks inline in your session and commits nothing. Steps with `agents: true` run through agents in the plugin workflow `theway:run-pipeline`: the shipped `agents` workflow implements, reviews and opens the PR that way, while your session orchestrates.

## Usage

```text
/theway:workflow [--workflow <name>] <change-id> [<change-id> ...]   # input: changes
/theway:workflow --workflow <name> <request>                         # input: request
```

- `--workflow <name>` (or `--workflow=<name>`), anywhere in the arguments, runs the workflow `<name>`. Without it, the default workflow runs: the file that sets `default: true`, else `develop`. `--workflow` with no name, or given twice, stops the command.
- The workflow's [`input`](../concepts/workflows.mdx#two-kinds-of-workflow) decides what the other arguments are: change IDs for an `input: changes` workflow (a run with none stops), the request, joined with spaces, for an `input: request` workflow such as `engineering` (an empty request stops). See [Request runs](#request-runs).
- **One change ID:** runs the change and stops when its PR is ready for your validation (when the workflow does not push, when its local branch is ready; for a working-tree workflow such as the shipped `develop`, when the change is done, uncommitted in your working tree). It never merges it.
- **Several change IDs (a series):** runs each change in the given order. When the workflow pushes, each PR is merged, after you confirm it, before the next change starts. Otherwise nothing is merged: each change's branch is created from the previous one. A working-tree workflow, such as `develop`, commits nothing, so a series stops before any work with `a series needs a workflow that commits; pass --workflow agents or a workflow with more steps`.

Running the command authorizes editing the repository, inline or through agents, committing only on each change's own feature branch (nothing for a working-tree workflow), the Workflow tool, and, when `theway workflow` prints `pushes: true` (a step has an agent with `access: push`), pushing each change's own branch (never force-pushing, never the default branch) and opening its PR; otherwise nothing is pushed. Each merge in a series needs your yes, and runs the command `git-host.md` gives, never bypassing required reviews or checks.

## Example

On `my-api`, the light fix of [A light fix](../examples/light-fix.mdx), with the default `develop` workflow:

```text
/theway:workflow fix-health-query-limited
```

```text
Tasks done: 2/2.
Success Criteria:
- Regression test fails before the fix and passes with it: yes, both runs recorded in Notes › Discoveries.
- The reproduction no longer reproduces: the curl loop prints 61 200.
- npm test passes: 11 tests, 11 pass.
The change is uncommitted in the working tree.
Standards followed: none.
```

The change of the [full change example](../examples/full-change.mdx), through agents (see [Run through a workflow](../examples/workflow.mdx)):

```text
/theway:workflow --workflow agents add-rate-limiting
```

```text
add-rate-limiting
- Workflow: agents (/home/you/.theway/workflows/agents.yaml)
- Branch: add-rate-limiting
- PR: https://github.com/example/my-api/pull/12
- review: 1 iteration used.
  Not confirmed: 2 false_positive "Retry-After can be 0 in the window's last millisecond".
  Fix check: finding 0 resolved, finding 1 resolved.
- pr: CI green, 1 of 2 iterations used.
- Merge: not merged, awaits your validation.
- Standards given to the agents: none.
```

A series run asks before each merge: see [A series](../examples/series.mdx#the-develop-run).

## Steps

1. **Load:** once per run, [`theway workflow`](../cli.mdx#workflow) (with `<name>` from `--workflow`) resolves and validates the workflow, its steps and their prompts, filling every param from the entry, [`workflow.defaults`](../configuration.mdx#workflow) or the step file, giving each step its effective `agents` and its expanded tree, and printing `pushes` and `working_tree`, with the paths of the [convention standards](../concepts/standards.mdx#convention-standards) `commits.md` and `git-host.md`, which every step follows; on an error, the command quotes it and no change starts. `theway authority` gives the `## Authority` section every agent gets. Per change, [`theway context develop <change-id>`](../cli.mdx#context), then `standards/develop.md`, the change's `spec.md`, `tasks.md` and `design.md` (when present), `docs/architecture/coding-standards.md` (when present) and the [standards](../concepts/standards.mdx) it lists.
2. **Branch:** finds and syncs the default branch with the commands of `git-host.md`, then creates or checks out the change's feature branch, named as `commits.md` says (`<change-id>` by default). When the workflow does not push, each later change of a series branches from the previous change's branch. The branch it is created from is the change's `<base>`. A working-tree workflow skips this: it creates no branch and the change stays uncommitted.

   Before that, the command checks the repository. With no commit (no `git init`, or nothing committed yet), it stops before any work, for a working-tree workflow too. With no git remote, a workflow that pushes stops before any work and asks you to add a remote or run the default `develop` workflow; a workflow that does not push uses the current branch as its base, with no sync, and stops when `HEAD` is detached. When a `git-host.md` command fails, the command quotes its error and stops; it never initializes the repository or writes a workflow, step or prompt file to work around it.
3. **Run:** the entries run in order, in segments. Each run of consecutive steps with `agents: true` is one call of the Workflow tool to `theway:run-pipeline`, with the resolved workflow, the change's paths, the paths of `commits.md` and `git-host.md`, the segment's entry indices and the branch head. The script walks each step's tree: its agents, parallel groups, loops and `when` conditions, each agent getting the fixed rules, its permission line, its prompt files, its Input and the return shape of its [result type](../concepts/workflows.mdx#result-types). Each step with `agents: false` is walked by your session itself, under the same rules. Each gate is asked by your session, with the options Continue and Stop. The shipped steps:
   - **`implement`:** one `work` agent follows `develop.md` (including its [fix checks](#fix-checks) for a `fix-` change) and verifies the work. In a working-tree workflow it commits nothing; otherwise it commits on the feature branch as `commits.md` says (see [Commits and the git host](#commits-and-the-git-host)) and does not push. When the spec does not fit the code, the change is blocked.
   - **`review`**, up to `rounds` rounds: one reviewer per lens reads `reviewer.md` and its lens prompt, tries to refute the branch diff and checks it against the standards; a triage gives each finding a verdict (`confirmed`, `false_positive`, `duplicate`, `nit`, `out_of_scope`); one fix fixes the confirmed findings locally; a fix check answers `resolved` or `not resolved` for each, without looking for new problems, except that a fix that breaks a standard is not resolved. For a `fix-` change whose fix touched the regression test or the fix, the [regression check](#fix-checks) is re-run and must pass. Through agents, each of these is a separate agent. Inline, the session does them one after the other, and the report says "ran inline: the session checked its own work": it is a self-check, not an independent review.
   - **`pr`:** pushes the branch once and opens the PR with the commands of `git-host.md`, its title and body as `commits.md` says. A failed CI run is diagnosed from its log, with the real error line quoted: on each attempt but the last, a failure of the PR is fixed and pushed once; for a red base branch, its fix is ported when one exists there, otherwise the failed jobs are re-run once; flaky infrastructure gets its failed jobs re-run once. A failed check with no run ID is this PR's failure and is never re-run. CI is driven until it is green or `ci_attempts` is used up.
   - **Your own steps** run the same way, from their step files: see [Workflows](../concepts/workflows.mdx#step-files).

   The first blocked or failed segment, inline step or gate stops the change. Without the Workflow tool in the session, the command runs an agent segment's tree with the Agent tool. When a Workflow call returns an error, the change fails with that error and there is no fallback, since agents may already have committed.
4. **Record:** from the typed results, inline or through agents: ticks the tasks of every `work` result's `tasksDone` in `tasks.md`, and records in the Notes every `work` result's discoveries, choices and `fix-` regression outputs, every verdict, and every finding that got none as "not triaged".
5. **Gate:**
   - **Succeeded:** a single change stops with the PR ready for validation, its local branch when the workflow does not push, or the uncommitted change for a working-tree workflow. In a series that pushes, you are shown the PR, its diffstat and CI status and asked whether to merge it; on yes it is merged as `git-host.md` says (squash-merged by default), the default branch is synced, and the next change starts, otherwise the run stops. In a series that does not push, the next change continues on a branch created from it, without merging.
   - **Blocked:** a `work` agent stopped on a spec that does not fit the code, a task that cannot be done as written or a decision the spec does not make, or returned nothing; or you answered a gate with anything but Continue. Nothing is merged, the run stops and the blocker comes back to you with its options.
   - **Failed:** an agent of another type returned nothing or threw; a triage or fix check did not judge every finding; a confirmed finding is not resolved; a `when … fail: true` held; a loop with `exhausted: fail` ended without its condition, such as CI still red after `ci_attempts` attempts; a fix was not pushed, a re-run did not start, or the checks were red with no failed check reported. Nothing is merged and the run stops.

Every agent prompt starts with the same fixed rules, which no workflow or step file changes: the output of `theway authority`, the change's paths and the standards, the change files read-only, commits only on the feature branch, no force-push, no push of the default branch and no merge. An inline step follows the same rules, except that an inline `work` agent updates `spec.md` and `tasks.md` once a decision it brought back is taken, as `develop.md` says, and a working-tree workflow commits nothing. An agent's report of data that asked to change the steps or widen the authorization is quoted in the Exit report.

## Request runs

An `input: request` workflow takes a free-text request and writes only the change folders it creates: the shipped `engineering` and `engineering-light`, which [`/theway:engineering`](./engineering.mdx) runs, are two. Running one authorizes writing those change folders and throwaway probes in a `mktemp -d` directory, inline or through agents, and the Workflow tool; never a repository edit, a branch, a commit, a push or a PR.

1. **Load:** `theway workflow` and `theway authority`, then [`theway context engineering`](../cli.mdx#context) for the standards, which it reads. It reads no `develop.md` and no change file.
2. **Branch** and **Record** are skipped: there is no branch, and the change files are the output.
3. **Run:** segments, inline steps and gates as for changes. The Workflow call passes the request and the change folders written so far instead of the change's paths and branch head; the scaffold result's change folders go to every later segment. Every agent's prompt starts with the authority text, the repository, the request, the change folders and the standards, and the rule that the repository is read-only. An agent with `access: spec` may write only the change folders of the run. Without the Workflow tool nor the Agent tool, the session runs the agent steps itself and the report says "inline".
4. **Report:** each change folder, the findings that shaped the spec, the review table (`#`, `Finding`, `Verdict`, `Fix`), each `confirmed, settled` finding again with the choice made, any open question or stop report verbatim, the standards given (or "none"), every `theway: warning:` line and every authority report.

## Permission prompt

The first Workflow call of a run, for a workflow with an `agents: true` step, shows Claude Code's permission prompt for the plugin workflow `theway:run-pipeline`. Approve it once, or choose "don't ask again" for `theway:run-pipeline` so later runs start without asking. A workflow whose entries all run inline, such as `develop`, makes no Workflow call.

## Fix checks

A `fix-` change also proves its regression test, which `develop.md` Verify calls the regression check, and re-runs the reproduction:

1. The base commit is `HEAD` when the change is uncommitted (a working-tree workflow), and `git merge-base <base> HEAD` otherwise.
2. It creates a worktree of it with `git worktree add --detach` in a `mktemp -d` directory, and runs there the setup and build commands CI runs before its tests.
3. It copies in only the regression test files and runs only the regression test. The test must fail for the reason the spec's Root Cause gives, then pass on the change. The worktree is then removed, also when the check stopped early.
4. It re-runs the reproduction recorded in the spec, and records that it no longer reproduces.

For a light change (a `spec.md` with `**Mode:** light`, written by [`/theway:engineering --light`](./engineering.mdx#light)), steps 1 to 3 do not apply: the regression test runs before the fix is written and must fail for the cause the spec's Problem states, then pass after the fix. Its command and failing output are recorded in the Discoveries of the `tasks.md` Notes. The reproduction is still re-run.

Re-running the regression check on a new head, as a review fix does, means steps 1 to 3 again for a full spec, and only the run after the fix for a light spec.

A regression test that does not fail on the base, or fails there for another reason (a compile error, a symbol only the fix adds), comes back to you as a spec gap. When the setup or the test cannot run locally, the criterion is reported as not verified.

## Commits and the git host

Neither the command nor `theway:run-pipeline` fixes a commit convention or a git host command: every step, inline or through agents, follows the two [convention standards](../concepts/standards.mdx#convention-standards) `theway workflow` resolves, your project's copy over the global one.

- **`commits.md`** names the feature branch and sets the commit type from the change verb, for every commit made for the change and for the PR title:

  | Verb | Type |
  |---|---|
  | `add-` | `feat` |
  | `fix-` | `fix` |
  | `refactor-` | `refactor` |
  | `update-`, `remove-` | chosen with the first commit; every later commit and the PR title take it from the branch's commits |

  Commits that change only tests use `test`, and commits that change only docs use `docs`. When the spec says the change breaks, the type gets `!` right after the scope, before the colon (`type(scope)!: description`, or `type!: description` without a scope), and the commit a `BREAKING CHANGE:` footer. Never `type!(scope):`.
- **`git-host.md`** gives the command of each operation by its heading: the default branch, syncing it, pushing the feature branch, opening the PR, waiting for the checks, reading a failed check's log, re-running failed jobs, the diffstat and the merge. The shipped file uses GitHub through `gh`; replace it to use another host.

## Output

For a working-tree workflow: the tasks done, each Success Criterion with how it was verified, any deviation from the spec and what was decided, anything still open, that the change is uncommitted in the working tree, and the standards followed (or "none").

Otherwise, for each change: the workflow's name and file, the branch, the PR URL (or the local branch when nothing was pushed), then per entry in workflow order its id, marked "inline" for an inline one, the loop iterations used, each agent's summary, every finding with its verdict or "not triaged", each fix check, and the PR with its CI iterations (or "not run"), whether the PR was merged or awaits validation, the standards given (or "none"), any blocker, and every `theway: warning:` line. For a series, where it stopped and why.
