The light path of [`/theway:engineering`](./engineering.mdx), for a small change with nothing to decide: a known cause, a local change, no contract that others rely on. It writes a short spec and 1 to 3 tasks, and one critic reviews them. The code comes later, from [`/theway:develop`](./develop.mdx) or [`/theway:develop-workflow`](./develop-workflow.mdx), as for any change.

## Usage

```text
/theway:engineering-light <request>
```

Use it when you already know what changes and why. When the change needs a decision, a contract change or a risk analysis, use `/theway:engineering`: this command sends you there itself.

## Steps

1. **Load config and standards:** the same files and keys as `/theway:engineering`: `~/.theway/config.yaml`, `data/standards/tamm-framework.md`, the opt-in standards that are enabled, `engineering.review_rounds` and `engineering.models.critic`.
2. **Pick the change ID** from the request, with the same [verbs](../concepts/changes.mdx#change-ids), and validate it with `theway validate-id <change-id>`. A light change is never a series member.
3. **Investigate:** read the code involved and check how it behaves today. For a `fix-` change, it reproduces the bug first and has the same three stop outcomes as `/theway:engineering` (not reproduced, possibly already covered, works as intended); after a stop, run `/theway:engineering-light` again with the new information.
4. **Escalate** when the investigation finds a decision to make, a public contract change, a TAMM risk at Medium or High, or a request for a series: it writes no change file and tells you to run `/theway:engineering` with the original request.
5. **Generate the documents:**
   - `~/.theway/templates/light-spec-template.md` produces `spec.md`, with `**Mode:** light` under its title;
   - `~/.theway/templates/tasks-template.md` produces `tasks.md`, without phases: 1 to 3 numbered tasks, then the Notes section. In a `fix-` change, task 1 writes the regression test.

   No `design.md`.
6. **Review:** one grounding critic, for one round (`engineering.review_rounds: 0` skips it), on `engineering.models.critic`. It checks the spec's claims about the code against the code and the official docs, and for a `fix-` change re-runs the reproduction. The command verifies each finding and fixes the confirmed `fixable` ones. A confirmed `decision` escalates: the light files stay, and it tells you to run `/theway:engineering <change-id>: <original request>`, which writes over them.

## Output

Everything is written under `~/.theway/<project>/changes/<change-id>/`:

- `spec.md`: `**Mode:** light`, then Problem, Evidence, Change and Success Criteria.
  - Problem says what is wrong or missing; for a `fix-` change, also the cause, with file and line evidence.
  - Evidence holds the findings; for a `fix-` change, the reproduction (command, observed output, expected result).
  - Change lists each file and what changes in it, and ends with "Nothing else changes.": it is the change's scope.
  - For a `fix-` change, the first two Success Criteria are always the same: the regression test fails before the fix and passes with it, and the reproduction no longer reproduces.
- `tasks.md`: 1 to 3 numbered tasks and a Notes section.

It reports the change folder, the findings that shaped the spec and the review outcome, in the same table as `/theway:engineering`. An escalation reports what was found and the command to run.

## Downstream

The develop commands read `**Mode:** light`:
- [`/theway:develop`](./develop.mdx#fix-checks) proves a light `fix-` change's regression test without the base-commit worktree: the test runs before the fix and fails, then runs after it and passes.
- [`/theway:develop-workflow`](./develop-workflow.mdx) runs at most one local review round, and its reviewers check the diff against the Change section.
