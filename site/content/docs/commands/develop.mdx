title: /theway:develop
description: Implement a change's tasks in the current session and tick them off
---

The spec is the contract: the work follows it and ends with a report on each Success Criterion.

## Usage

```text
/theway:develop <change-id>
```

The change ID can also come from the request, for example "develop the add-redis-cache change". The command asks only when none is given.

## Example

On `my-api`, the light fix of [A light fix](../examples/light-fix.mdx):

```text
/theway:develop fix-health-query-limited
```

```text
Tasks done: 2/2.
Success Criteria:
- Regression test fails before the fix and passes with it: yes, both runs recorded in Notes › Discoveries.
- The reproduction no longer reproduces: the curl loop prints 61 200.
- npm test passes: 11 tests, 11 pass.
Standards followed: none.
```

## Steps

1. **Load context:** it runs [`theway context <project> develop <change-id>`](../cli.mdx#context), then reads these paths directly:
   - `<home>/standards/develop.md` (`<home>` is the folder `theway path` prints, `~/.theway` by default)
   - `<home>/<project>/changes/<change-id>/spec.md`
   - `<home>/<project>/changes/<change-id>/tasks.md`
   - `<home>/<project>/changes/<change-id>/design.md`, when present
   - `docs/architecture/coding-standards.md`, when present
   - the [standards](../concepts/standards.mdx) its `standards` lists: the enabled standards, shipped opt-in or yours; each applies to every phase unless its `applies_to` narrows it
2. **Implement and verify**, following `develop.md`:
   - Read only this change's folder: never other changes or `changes/archive/`, so no task from another change ends up in this one.
   - Work through the numbered tasks in order, following the codebase's patterns, and write the tests with the code they cover.
   - Follow the standards. When one contradicts the spec, stop and bring it back.
   - Tick each task (`- [x] N.`) once it is done, and record what the next person needs in the Notes section of `tasks.md`.
   - When the code contradicts the spec, a task cannot be done as written, or a decision is missing, stop and bring back what was found and the options. Once decided, `spec.md` and `tasks.md` are updated, then the work continues. A light spec has no Hardpoints table, so a Medium or High risk it did not foresee comes back to you as a blocker.
   - Run the project's tests and build, and the commands its CI runs where they can run locally. Then check each Success Criterion.

## Fix checks

A `fix-` change also proves its regression test, which `develop.md` Verify calls the regression check, and re-runs the reproduction:

1. The base commit is `HEAD`, since the change is uncommitted. (`/theway:develop-workflow` uses `git merge-base <base> HEAD`.)
2. It creates a worktree of it with `git worktree add --detach` in a `mktemp -d` directory, and runs there the setup and build commands CI runs before its tests.
3. It copies in only the regression test files and runs only the regression test. The test must fail for the reason the spec's Root Cause gives, then pass on the change. The worktree is then removed, also when the check stopped early.
4. It re-runs the reproduction recorded in the spec, and records that it no longer reproduces.

For a light change (a `spec.md` with `**Mode:** light`, written by [`/theway:engineering-light`](./engineering-light.mdx)), steps 1 to 3 do not apply: the regression test runs before the fix is written and must fail for the cause the spec's Problem states, then pass after the fix. Its command and failing output are recorded in the Discoveries of the `tasks.md` Notes. The reproduction is still re-run.

Re-running the regression check on a new head, as `/theway:develop-workflow` does after a review fix, means steps 1 to 3 again for a full spec, and only the run after the fix for a light spec.

A regression test that does not fail on the base, or fails there for another reason (a compile error, a symbol only the fix adds), comes back to you as a spec gap. When the setup or the test cannot run locally, the criterion is reported as not verified.

## Output

The code changes in your working tree, an updated `tasks.md`, and a report: the tasks done, each Success Criterion with how it was verified, any deviation from the spec and what was decided, the standards followed (or "none"), and anything still open.
