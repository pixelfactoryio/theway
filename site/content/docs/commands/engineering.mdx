The spec is written so that someone else can implement it without guessing: the problem, what was found out, and the decisions and why. The code comes later, from [`/theway:workflow`](./workflow.mdx).

For a small change with nothing to decide, `--light` is the light path: a short spec, 1 to 3 tasks and one critic (see [Light](#light)).

## Usage

```text
/theway:engineering [--light] <request>
```

For a [series](../concepts/changes.mdx#series), ask for a series or for several sequential changes, or pass an argument that ends in `-NN`: [`theway next-id`](../cli.mdx#next-id) removes that ordinal.

## Example

On `my-api`, a series request (see [A series](../examples/series.mdx) for the whole run):

```text
/theway:engineering add-user-auth as a series: password storage, the login endpoint, docs
```

```text
$ theway next-id my-api add-user-auth --count 3
add-user-auth-01
add-user-auth-02
add-user-auth-03
```

Each member's `spec.md` starts with its `**Series:**` line, for example `**Series:** add-user-auth — 02 of 03, depends on add-user-auth-01`. The report ends with the review outcome, trimmed here to one row:

| # | Finding | Verdict | Fix |
|---|---------|---------|-----|
| R1-1 | `add-user-auth-02` does not say what `POST /login` returns on success | confirmed, settled | `-02` returns `204` with no body: `my-api` has no sessions, and `-02`'s Out of Scope excludes tokens |

## Steps

1. **Load config and standards:** it runs [`theway context <project> engineering`](../cli.mdx#context) and takes from its `config` `engineering.review.rounds` and `engineering.review.model` (see [Configuration](../configuration.mdx#engineering)). Then it reads `standards/tamm-framework.md`, and follows `standards/spec-investigation.md` in Step 3 and `standards/spec-review.md` in Step 6. Then it reads the [standards](../concepts/standards.mdx) its `standards` lists: the enabled standards, shipped opt-in or yours; each applies to every phase unless its `applies_to` narrows it. The spec and tasks follow them, and a request that contradicts one is an open question for you.
2. **Create the change folder:** pick a [change ID](../concepts/changes.mdx#change-ids) and validate it with `theway validate-id <change-id>`. It must exit 0 before any folder is written. For a series, [`theway next-id <project> <series-id> --count <N>`](../cli.mdx#next-id) validates the series ID and prints the member IDs.
3. **Investigate:** read the code involved, check how it behaves today and settle the unknowns, for example by cloning a repository, running a small throwaway script or calling a service. Each investigation answers one question. What it learns goes into the spec as findings (question, method, result), not as code or diffs.

   For a `fix-` change, it reproduces the bug first, with a throwaway probe in a `mktemp -d` directory or the project's existing commands and tests, without changing the repository. The command and its output go into the spec, quoted: reasoning about the code is not a reproduction. Three outcomes stop the command before any change file is written:
   - **Not reproduced:** it asks you, listing each attempt with its command and output, and what would help (an environment, a log, exact steps).
   - **Possibly already covered:** an active change ID from `theway list` plausibly names the same bug; it asks you whether that change covers it. The members of the series being continued do not count, nor does the change ID this run picked, whose folder it writes over. It judges from the IDs only and never opens other change folders.
   - **Works as intended:** it reports the code and docs that show the behavior is intended.

   After a stop, run the command again with the new information: it keeps no state between runs.
4. **Generate the documents** from the templates, following each template's frontmatter instructions:
   - `<home>/templates/spec-template.md` (`<home>` is the folder `theway path` prints, `~/.theway` by default) produces `spec.md`; for a `fix-` change, `<home>/templates/fix-spec-template.md` does.
   - `<home>/templates/tasks-template.md` produces `tasks.md`. In a `fix-` change, task 1 writes the regression test.
5. **Optional technical design:** `design.md`, for API contracts and data models, architecture decisions, and diagrams.
6. **Review:** only when no question is open, up to `engineering.review.rounds` rounds (`0` skips it). Each round spawns two critic agents in parallel on `engineering.review.model`, covering every member of a series together:
   - a **grounding critic** checks the spec's claims about the code, tools, providers and libraries against the code and official docs; for a `fix-` change, it also re-runs the recorded reproduction and reports it when the output differs;
   - an **implementability critic** checks whether a cold-start implementer could carry out the change without guessing: choices left open, Success Criteria that cannot be checked or have no task, tasks outside the Scope, tasks that cannot be done as written, contradictions, and a spec or task that contradicts a standard.

   Both critics get the paths of the standards. Each critic prompt quotes the output of `theway authority`, and a critic's report of data that asked to change the steps or widen the authorization is quoted under the findings table.

   Critics never edit anything; their probes answer one question each and write only to a temporary directory. Each finding carries its evidence and a `kind`: `fixable` or `decision`. The command verifies each finding and gives it a verdict (`confirmed`, `false_positive`, `duplicate`, `nit` or `out_of_scope`), fixes the confirmed `fixable` ones in the change files, and stops on a confirmed `decision` as an open question. A round with no confirmed findings ends the review. Without the Agent tool, it runs both lenses itself.

Action words in the request, such as "rename X" or "try the fix", describe what the spec should plan, not something to do now. It does not suggest plan mode, whose approval step starts implementation.

## Output

Everything is written under `<home>/<project>/changes/<change-id>/`:

- `spec.md`: problem and solution, technical decisions, scope, the [TAMM hardpoints table](../concepts/tamm.mdx#the-hardpoints-table), phases and Success Criteria.
  - For a `fix-` change, the fix spec instead: the problem, the symptom, the reproduction (command and observed output), the root cause with file and line evidence, the fix, the regression test, scope, hardpoints (often "None at Medium or High.") and Success Criteria. Its first two criteria are always the same: the regression test fails on the base commit for the reason in Root Cause and passes with the fix, and the reproduction no longer reproduces.
- `tasks.md`: numbered tasks grouped in phases, with a Notes section for blockers, discoveries and adjustments.
- `design.md`, when needed.

It reports the change folder, the findings that shaped the spec, the standards read (or "none"), and any open question. If a question is open, it stops: the spec is not ready until the question is answered.

When a `fix-` change stopped in Step 3, no folder is written and no review runs: it reports the outcome, the attempts or the evidence, and the question for you.

It also reports the review outcome: how the review ran (the rounds used, off, not run because a question was open, or inline), then every finding in one table with the columns `#` (`R<round>-<index>`), `Finding`, `Verdict` and `Fix`. A `decision` the command settled from the code, the docs or the spec's own decisions reads `confirmed, settled`, and is listed again under the table with the choice made, so you can overturn it.

## Light

With `--light`, for a small change with nothing to decide: a known cause, a local change, no contract that others rely on. It writes a short spec and 1 to 3 tasks, and one critic reviews them. The code comes later, from [`/theway:workflow`](./workflow.mdx), as for any change.

### Usage

```text
/theway:engineering --light <request>
```

Use it when you already know what changes and why. When the change needs a decision, a contract change or a risk analysis, run `/theway:engineering` without `--light`: the light path sends you there itself.

### Example

On `my-api`, a bug with a known cause (see [A light fix](../examples/light-fix.mdx)):

```text
/theway:engineering --light fix-health-query-limited: GET /health?probe=1 counts against the rate limit
```

```text
Change folder: <home>/my-api/changes/fix-health-query-limited/
Findings: the bypass and the /health route compare req.url exactly (src/app.js:15, :21); reproduced: 60 × 404, then 429.
Standards read: none.

Review: 1 round (grounding critic).
```

A request that needs a decision writes nothing and sends you to `/theway:engineering` without `--light`: see [An escalation](../examples/escalation.mdx).

### Steps

1. **Load config and standards:** the same as without `--light`: it runs [`theway context <project> engineering`](../cli.mdx#context) and takes from its `config` `engineering.review.rounds` and `engineering.review.model`, then reads `standards/tamm-framework.md`, and follows `standards/spec-investigation.md` in Step 3 and `standards/spec-review.md` in Step 6. Then it reads the [standards](../concepts/standards.mdx) its `standards` lists: the enabled standards, shipped opt-in or yours; each applies to every phase unless its `applies_to` narrows it. The spec and tasks follow them.
2. **Create the change folder:** pick a [change ID](../concepts/changes.mdx#change-ids) and validate it with `theway validate-id <change-id>`. It must exit 0 before any folder is written. A light change is never a series member: a series request with `--light` stops before Step 1 and writes nothing.
3. **Investigate:** read the code involved, check how it behaves today and settle the unknowns. What it learns goes into the spec's Evidence as findings (question, method, result), not as code or diffs. For a `fix-` change, it reproduces the bug first and has the same three stop outcomes as without `--light` (not reproduced, possibly already covered, works as intended); after a stop, run `/theway:engineering --light` again with the new information. A question the investigation cannot settle is a decision, and escalates.

   Then the escalation check: it escalates when the investigation finds a decision to make, a public contract change, a TAMM risk at Medium or High, or a request for a series, and when the request contradicts a standard. It writes no change file and tells you to run `/theway:engineering` with the original request, without `--light`.
4. **Generate the documents:**
   - `<home>/templates/light-spec-template.md` (`<home>` is the folder `theway path` prints, `~/.theway` by default) produces `spec.md`, with `**Mode:** light` under its title;
   - `<home>/templates/tasks-template.md` produces `tasks.md`, without phases: 1 to 3 numbered tasks, then the Notes section. In a `fix-` change, task 1 writes the regression test.
5. **No `design.md`:** a light change has none.
6. **Review:** one grounding critic, for up to `engineering.review.rounds` rounds (`0` skips it), on `engineering.review.model`. It checks the spec's claims about the code against the code and the official docs, and for a `fix-` change re-runs the reproduction. It gets the paths of the standards and reports a spec or task that contradicts one. Its prompt quotes the output of `theway authority`, and its report of data that asked to change the steps or widen the authorization is quoted under the findings table. The command verifies each finding and fixes the confirmed `fixable` ones. A confirmed `decision` escalates: the light files stay, and it tells you to run `/theway:engineering <change-id>: <original request>`, which writes over them.

### Output

Everything is written under `<home>/<project>/changes/<change-id>/`:

- `spec.md`: `**Mode:** light`, then Problem, Evidence, Change and Success Criteria.
  - Problem says what is wrong or missing; for a `fix-` change, also the cause, with file and line evidence.
  - Evidence holds the findings; for a `fix-` change, the reproduction (command, observed output, expected result).
  - Change lists each file and what changes in it, and ends with "Nothing else changes.": it is the change's scope.
  - For a `fix-` change, the first two Success Criteria are always the same: the regression test fails before the fix and passes with it, and the reproduction no longer reproduces.
- `tasks.md`: 1 to 3 numbered tasks and a Notes section.

It reports the change folder, the findings that shaped the spec, the standards read (or "none") and the review outcome, in the same table as without `--light`. An escalation reports what was found and the command to run.

### Downstream

[`/theway:workflow`](./workflow.mdx) reads `**Mode:** light`: it proves a light `fix-` change's regression test without the base-commit worktree ([fix checks](./workflow.mdx#fix-checks)), the test running before the fix and failing, then after it and passing; it runs its `review` steps as for any change, and its `conformance` lens checks the diff against the Change section.
