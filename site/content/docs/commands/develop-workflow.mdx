description: Implement changes through agents, review them locally, then open a PR and drive CI to green
---

It is the agent-driven counterpart of [`/theway:develop`](./develop.mdx): your session orchestrates, and agents write, review and fix the code.

## Usage

```text
/theway:develop-workflow <change-id> [<change-id> ...]
```

- **One change ID:** develops the change and stops when its PR is ready for your validation (with `workflow.open_pr: false`, when its local branch is ready). It never merges it.
- **Several change IDs (a series):** develops each change in the given order. With `workflow.open_pr` true, each PR is merged, after you confirm it, before the next change starts. With `false`, nothing is merged: each change's branch is created from the previous one.

Running the command authorizes pushing each change's own branch (never force-pushing) and opening its PR. Each merge in a series needs your yes, and uses a normal squash merge, never `--admin`.

## Steps

The steps run once per change ID, in order.

1. **Load context:** the same files as [`/theway:develop`](./develop.mdx). From the config, it takes `workflow.review_rounds` (default 1), `workflow.ci_attempts` (default 2), `workflow.open_pr` (default `true`) and the agent models in `workflow.models`. See [Configuration](../configuration.mdx#workflow).
2. **Branch:** syncs the main branch, then creates or checks out the change's feature branch. In a series with `workflow.open_pr: false`, each later change's branch is created from the previous change's branch.
3. **Implement:** orchestrates agents with the Workflow tool, or with Agent-tool fan-out when that is unavailable. One implementer per change by default; parallel implementers, each in its own worktree, only for large independent parts that touch different files. The implementer follows `develop.md`, commits locally with Conventional Commits and verifies its work, including the CI's commands that can run locally. It does not push. When the spec does not fit the code, it returns a blocker instead of redesigning.
4. **Review locally**, for up to `review_rounds` rounds, before anything is pushed:
   1. Reviewer agents try to refute the branch diff against `spec.md` (each Success Criterion, the scope) and for correctness, edge cases and conventions.
   2. Each finding is triaged as `confirmed`, `false_positive`, `duplicate`, `nit` or `out_of_scope`. Only confirmed findings are fixed.
   3. One fix agent fixes the confirmed findings locally.
   4. A fix-check agent answers `resolved` or `not resolved` for each confirmed finding.

   With `review_rounds: 0`, this step is skipped.
5. **Open the PR and drive CI** (skipped with [`workflow.open_pr: false`](../configuration.mdx#workflow)): pushes the branch once and opens the PR with `gh pr create`; the PR text describes only what the change does. A failed CI run is triaged from its log, with the real error line quoted. A failure of the PR goes to a fix agent, which pushes once; a red base branch or flaky infrastructure gets one re-run of the failed jobs. CI is driven until it is green or `ci_attempts` is used up.
6. **Gate:**
   - **Succeeded:** a single change stops with the PR ready for validation. In a series, you are shown the PR, its diffstat and CI status and asked whether to merge it; on yes it is squash-merged and the next change starts, otherwise the run stops. With `workflow.open_pr: false`, a single change stops with its local branch, and a series continues on a branch created from it, without merging.
   - **Blocked:** an implementer returned a blocker. Nothing is merged, the run stops and the blocker comes back to you with its options.
   - **Failed:** a confirmed finding is not resolved, or CI is still red after `ci_attempts` attempts. Nothing is merged and the run stops.

Each agent role runs on the model set in [`workflow.models`](../configuration.mdx#workflowmodels): by default implementers, reviewers, fix agents and the fix check on `opus`, CI polling and log fetching on `sonnet`. When implementers are on `opus`, `sonnet` is allowed for them on mechanical tasks. `haiku` is never used.

## Output

For each change: the branch, the PR URL (or the local branch when nothing was pushed), the review outcome (rounds used, findings not fixed with their verdicts, the fix check per confirmed finding), the CI status and attempts used ("not run" when nothing was pushed), whether the PR was merged or awaits validation, and any blocker. For a series, where it stopped and why.
